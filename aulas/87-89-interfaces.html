Resumo

Uma interface é "bem parecida com a classe abstrata", mas a principal diferença é que ela não é uma classe. Ela nasceu para ser um contrato: diz o que quem a implementa precisa saber fazer, sem dizer como. Até o Java 7, todos os métodos de uma interface eram abstratos. A partir do Java 8, ela também pode ter métodos default e static com corpo. E uma classe pode implementar várias interfaces, coisa que não dá com extends.

87 · O contrato e o implements

public interface DataLoader {
    public abstract void load();     // "public abstract" é redundante: void load(); é igual
}

public class DatabaseLoader implements DataLoader {   // implements, não extends
    @Override
    public void load() {
        System.out.println("Carregando dados do banco de dados");
    }
}

public class FileLoader implements DataLoader {
    @Override
    public void load() {
        System.out.println("Carregando dados de um arquivo");
    }
}

new DatabaseLoader().load();   // Carregando dados do banco de dados
new FileLoader().load();       // Carregando dados de um arquivo
  • Cria-se com public interface DataLoader (um "carregador de dados"; o William usa nomes em inglês, que é o comum no mercado).
  • Todo método de interface é, por padrão, public abstract. Escrever os dois é redundante: na vida real você vai ver só void load();. Na aula ele escreve para fixar.
  • Método abstrato na interface segue a mesma regra: sem corpo, termina com ;.
  • Interface não pode ser final: o contrato existe para ser implementado.
  • A classe usa implements (não extends) e é obrigada a implementar os métodos abstratos, como na classe abstrata.
  • Não faria sentido um DataLoader concreto: você carrega do banco ou de um arquivo. Cada classe dá a sua implementação. Interfaces "fazem muito mais sentido" com polimorfismo (aulas 90–94).

88 · Várias interfaces e métodos default

public interface DataRemover {
    public abstract void remove();
}

public class DatabaseLoader implements DataLoader, DataRemover {   // várias, separadas por vírgula
    @Override public void load()   { System.out.println("Carregando dados do banco de dados"); }
    @Override public void remove() { System.out.println("Removendo dados do banco de dados"); }
}

public interface DataLoader {
    public abstract void load();

    public default void checkPermission() {           // Java 8+: método com corpo
        System.out.println("Fazendo checagem de permissões");
    }
}
  • Uma classe pode implementar quantas interfaces quiser (implements DataLoader, DataRemover), ao contrário do extends, que aceita uma classe só. É uma das diferenças entre classe abstrata e interface.
  • Por que o default existe: adicionar um método abstrato numa interface quebra todas as classes que a implementam. Com duas classes, tudo bem. Mas a interface Collection existe desde o Java 1.2 e é usada no planeta inteiro. Para evoluir a linguagem sem quebrar o código de ninguém (compatibilidade com versões anteriores), o Java 8 trouxe os métodos default, como o removeIf da Collection.
  • Método default tem corpo e não é obrigatório implementar. fileLoader.checkPermission() imprime "Fazendo checagem de permissões" direto da interface.
  • A classe pode sobrescrever o default se quiser: DatabaseLoader passa a imprimir "Checando permissões no banco de dados" e FileLoader "Checando permissões no arquivo".
  • O método default também é public por padrão, então escrever public é redundante.

89 · Modificador na sobrescrita, constantes e static

public interface DataLoader {
    public static final int MAX_DATA_SIZE = 10;          // todo atributo é constante

    public static void retrieveMaxDataSize() {          // Java 8+: método estático
        System.out.println("Dentro do retrieveMaxDataSize na interface");
    }
}

public class DatabaseLoader implements DataLoader, DataRemover {
    // private -> default -> protected -> public
    public static void retrieveMaxDataSize() {          // NÃO é sobrescrita (@Override dá erro)
        System.out.println("Dentro do retrieveMaxDataSize na classe DatabaseLoader");
    }
}

DataLoader.retrieveMaxDataSize();      // ... na interface
DatabaseLoader.retrieveMaxDataSize();  // ... na classe DatabaseLoader
  • Não dá new DataLoader(), mas dá para usar a interface como tipo da variável. Isso é polimorfismo. As classes anônimas, que parecem um new de interface, vêm lá na frente.
  • Regra da sobrescrita (cai em prova e entrevista): o modificador de acesso nunca pode ser mais restritivo que o original. Do mais restritivo ao mais liberal: private → default (de pacote, sem palavra) → protected → public.
  • Como os métodos da interface são public, tirar o public do checkPermission no DatabaseLoader não compila: ele viraria "de pacote", mais restritivo. Numa classe abstrata com método protected, a sobrescrita pode ser protected ou public, nunca default ou private.
  • Todo atributo de interface é public static final (constante): int MAX_DATA_SIZE = 10; já é tudo isso.
  • Método static em interface (Java 8+) pertence à interface e nunca é sobrescrito. A classe pode ter um estático de mesmo nome, mas são dois métodos independentes: cada um se chama pelo seu nome de tipo.
  • O William fecha dizendo que praticamente todo framework usa interfaces: programação orientada a interface desacopla o código e melhora a manutenção.

Atenção

  • Classe implements interface; interface extends interface. Extra: uma interface pode estender várias outras (interface Repo extends DataLoader, DataRemover).
  • Extra: extends vem antes de implements: class Gerente extends Funcionario implements DataLoader, DataRemover.
  • Extra: o estático da interface não é herdado. FileLoader.retrieveMaxDataSize() não compila (o FileLoader não tem o próprio). Só DataLoader.retrieveMaxDataSize().
  • Extra: dois default com o mesmo nome em duas interfaces implementadas geram erro de compilação. A classe precisa sobrescrever e pode escolher um com DataLoader.super.checkPermission();.
  • Extra: classe abstrata que implementa interface não é obrigada a implementar os métodos. A regra da "primeira classe concreta" das aulas 84–86 vale aqui também.
  • Extra: diferença-chave em relação à classe abstrata: a interface não tem estado (atributos de instância) nem construtor. Só constantes.

Paralelo com PHP

  • Base igual: interface DataLoader { public function load(): void; } e class DatabaseLoader implements DataLoader, DataRemover. Todos os métodos de interface são public também no PHP.
  • Constantes: const MAX_DATA_SIZE = 10; na interface, acessada com DataLoader::MAX_DATA_SIZE, igual ao public static final.
  • Não existe default no PHP: interface do PHP não tem corpo de método. O papel do default costuma ficar com uma trait (use ChecaPermissao;) ou uma classe abstrata base.
  • Laravel é construído sobre interfaces: os Illuminate\Contracts\... (Cache\Repository, Queue\ShouldQueue...). No service container, $this->app->bind(DataLoader::class, DatabaseLoader::class) faz quem pede DataLoader no construtor receber a implementação. É a "programação orientada a interface" de que o William fala, e é o que o Spring faz em Java.
  • ShouldQueue é uma interface sem métodos (interface de marcação). Em Java, Serializable é o equivalente clássico.

Glossário

  • Interface: tipo que define um contrato (métodos) sem ser classe; não pode ser instanciada.
  • implements: palavra usada pela classe para assumir o contrato de uma ou mais interfaces.
  • Método default: método de interface com corpo (Java 8+), herdado por quem implementa e opcionalmente sobrescrito.
  • Método estático de interface: pertence à interface, chamado por DataLoader.metodo(), nunca sobrescrito.
  • Compatibilidade retroativa: evoluir a linguagem sem quebrar código antigo; o motivo do default.
  • Modificador de acesso default: sem palavra nenhuma, visível só no pacote. Não confundir com o método default de interface.
  • Programação orientada a interface: depender do contrato (DataLoader), não da implementação (DatabaseLoader), para desacoplar o código.
