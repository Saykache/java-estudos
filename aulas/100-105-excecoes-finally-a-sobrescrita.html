Resumo

O bloco fecha o assunto de exceções com as ferramentas do dia a dia: finally para código que precisa rodar sempre (liberar recursos), vários catch e a regra de ordem, o multi-catch com |, o try-with-resources, que fecha os recursos sozinho, exceções customizadas para regras do seu negócio e, para prova e entrevista, as regras de throws na sobrescrita.

100 · finally: roda sempre

private static String abreConexao() {
    try {
        System.out.println("Abrindo arquivo");
        System.out.println("Escrevendo dados no arquivo");
        return "conexão aberta";
    } catch (Exception e) {
        e.printStackTrace();
    } finally {
        System.out.println("Fechando recurso liberado pelo SO");   // roda ANTES do return chegar a quem chamou
    }
    return null;
}

private static void abreConexao2() {       // try + finally, sem catch
    try {
        System.out.println("Abrindo arquivo");
        System.out.println("Escrevendo dados no arquivo");
        throw new RuntimeException();
    } finally {
        System.out.println("Fechando recurso liberado pelo SO");   // fecha, mas a exceção segue para o main
    }
}
  • Recursos externos (arquivo, conexão com banco) são pedidos ao sistema operacional ou ao SGBD e precisam ser fechados. Imagine o sistema do Enem com milhões de acessos deixando conexões abertas: em algum momento a memória acaba e a aplicação para.
  • Se o "fechar" estiver no fim do try e uma exceção acontecer antes, ele nunca roda.
  • O bloco finally sempre é executado: com sucesso, com exceção, e até quando o try tem return. Nesse caso ele roda antes de o valor voltar para quem chamou.
  • O return null no fim é necessário porque o return do try pode não ser alcançado.
  • try sozinho não compila. Ele precisa de catch, de finally ou dos dois. try/finally sem catch existe, mas o William diz que nunca viu em produção: serve quando você não trata a exceção mas precisa fechar o recurso, e a exceção continua subindo.

101 · Vários catch: do mais específico ao mais genérico

try {
    throw new RuntimeException();
} catch (ArrayIndexOutOfBoundsException e) {
    System.out.println("Dentro do ArrayIndexOutOfBoundsException");
} catch (IndexOutOfBoundsException e) {          // mãe da de cima: tem que vir DEPOIS
    System.out.println("Dentro do IndexOutOfBoundsException");
} catch (IllegalArgumentException e) {
    System.out.println("Dentro do IllegalArgumentException");
} catch (ArithmeticException e) {
    System.out.println("Dentro do ArithmeticException");
} catch (RuntimeException e) {                   // a mais genérica no fim
    System.out.println("Dentro do RuntimeException");
}
// Dentro do RuntimeException

private static void talvezLanceException() throws SQLException, FileNotFoundException { }

try {
    talvezLanceException();
} catch (SQLException e) {                       // as duas são checked: as duas precisam de catch
    e.printStackTrace();
} catch (FileNotFoundException e) {              // linhas de herança diferentes: ordem livre
    e.printStackTrace();
}
  • Por que ter vários: exceções diferentes merecem tratamentos diferentes. No HTTP, por exemplo, um erro 4xx é do cliente e um 5xx é do servidor.
  • O Java testa os catch de cima para baixo e entra no primeiro compatível, pela regra do polimorfismo. Um ArrayIndexOutOfBoundsException também "é um" IndexOutOfBoundsException, mas cai no primeiro que aparecer.
  • Se nenhum catch servir, a exceção sobe. Um catch (RuntimeException e) no fim pega "o que der e vier".
  • A mais genérica sempre por último. Com RuntimeException no topo, os catch abaixo nunca seriam alcançados, e o compilador acusa erro.
  • throws aceita várias exceções separadas por vírgula. Se forem de linhas de herança diferentes (SQLException, FileNotFoundException), a ordem dos catch não importa, mas cada checked precisa ser tratada. Também dá para pegar as duas com uma mãe comum (catch (Exception e)).

102 · Multi-catch em linha: |

try {
    throw new RuntimeException();
} catch (ArrayIndexOutOfBoundsException | IllegalArgumentException | ArithmeticException e) {
    System.out.println("Dentro do ArrayIndexOutOfBoundsException | IllegalArgumentException | ArithmeticException");
} catch (RuntimeException e) {
    System.out.println("Dentro do RuntimeException");
}

private static void talvezLanceException() throws SQLException, IOException { }

try {
    talvezLanceException();
} catch (IOException | SQLException e) {
    e.printStackTrace();
}
// catch (FileNotFoundException | IOException e)   ← NÃO compila: mesma linha de herança
  • Quando várias exceções recebem o mesmo tratamento, junte-as num catch só com |. É só uma sintaxe mais legível para o mesmo resultado.
  • Regra: as exceções do multi-catch não podem ser da mesma linha de herança (ArrayIndexOutOfBoundsException e IndexOutOfBoundsException, ou FileNotFoundException e IOException), em qualquer ordem. Seria redundante: a mãe já pega a filha.
  • Vantagem sobre catch (Exception e): você trata do mesmo jeito só as que espera, e ainda pode ter um catch genérico no fim para o imprevisto.
  • No multi-catch a variável e é implicitamente final: e = new ArithmeticException(); não compila. Com uma exceção só, compila (ninguém faz isso, mas cai em prova).
  • O Java adiciona sintaxes assim sem quebrar o código antigo (retrocompatibilidade). Por isso muitas vezes existem dois jeitos de fazer a mesma coisa.

103 · try-with-resources: o Java fecha para você

// Jeito antigo: "feio" (e a galera do Java sabe disso)
public static void lerArquivo2() {
    Reader reader = null;                                   // declarado fora para o finally enxergar
    try {
        reader = new BufferedReader(new FileReader("teste.txt"));
    } catch (FileNotFoundException e) {
        e.printStackTrace();
    } finally {
        try {
            if (reader != null) {                           // pode ser null se o new falhou
                reader.close();                             // close() também lança IOException
            }
        } catch (IOException exception) {
            exception.printStackTrace();
        }
    }
}

// Java 7+: try-with-resources
public class Leitor1 implements Closeable {
    @Override
    public void close() throws IOException {
        System.out.println("Fechando leitor 1");
    }
}
// Leitor2: igual, "Fechando leitor 2"

public static void lerArquivo() {
    try (Leitor1 leitor1 = new Leitor1();
         Leitor2 leitor2 = new Leitor2()) {                 // vários, separados por ;
        // usa os leitores
    } catch (IOException e) {
        // (trate de verdade: nunca deixe vazio)
    }
}
// Fechando leitor 2
// Fechando leitor 1
  • No jeito antigo, a variável precisa ser declarada fora do try (senão o finally não a enxerga), pode estar null, e o close() também lança uma checked. O resultado é um try dentro do finally.
  • Sintaxe: try (Tipo var = new Tipo()) { ... }. O objeto é declarado e instanciado nos parênteses, e o Java chama close() automaticamente no fim.
  • Regra: só entram objetos que implementam AutoCloseable ou Closeable (que estende AutoCloseable). É polimorfismo: o Java tem garantia de que existe um close() para chamar. Reader implementa Closeable.
  • Os recursos são fechados na ordem inversa da declaração: abriu 1, 2, 3, fecha 3, 2, 1. Isso importa quando um depende do outro (cadeia de conexões).
  • É o único try que pode ficar sem catch e sem finally. Mas se o close() lança uma checked (como aqui), você trata com catch ou declara throws. Um catch ou finally extra também é permitido.
  • Muito usado com banco de dados, onde se abre e fecha conexão o tempo todo, e tira do desenvolvedor a responsabilidade de lembrar de fechar.

104 · Exceção customizada

public class LoginInvalidoException extends Exception {   // extends Exception = checked
    public LoginInvalidoException() {
        super("Login inválido");                             // mensagem padrão
    }

    public LoginInvalidoException(String message) {
        super(message);
    }
}

private static void logar() throws LoginInvalidoException {
    Scanner teclado = new Scanner(System.in);
    String usernameDB = "Goku";
    String senhaDB = "ssj";
    System.out.println("Usuário");
    String usernameDigitado = teclado.nextLine();
    System.out.println("Senha");
    String senhaDigitada = teclado.nextLine();
    if (!usernameDB.equals(usernameDigitado) || !senhaDB.equals(senhaDigitada)) {
        throw new LoginInvalidoException("Usuário ou senha inválidos");
    }
    System.out.println("Usuário logado com sucesso");
}

public static void main(String[] args) {
    try {
        logar();
    } catch (LoginInvalidoException e) {                     // tratado: o programa não "trava"
        e.printStackTrace();
    }
}
  • Quando nenhuma exceção do Java expressa a regra do seu negócio (login inválido, saldo insuficiente), crie uma classe que estende uma exceção. Por convenção, o nome termina com Exception.
  • A escolha da mãe define o comportamento: extends Exception = checked (força quem chama a tratar); extends RuntimeException = unchecked (não força). O William quis forçar, então usou Exception.
  • Só o extends já basta. Os construtores são opcionais: um sem parâmetro com mensagem padrão (super("Login inválido")) e um que recebe a mensagem.
  • Na aula, "Goku" + "12" e "Goku" + "Ssj" dão exceção (equals diferencia maiúsculas). Só "Goku" + "ssj" loga.
  • Sistemas reais costumam ter várias exceções customizadas.

105 · throws na sobrescrita

public class Pessoa {
    public void salvar() throws LoginInvalidoException, IOException {
        System.out.println("Salvando pessoa");
    }
}

public class Funcionario extends Pessoa {
    @Override
    public void salvar() throws LoginInvalidoException, FileNotFoundException {   // mais específica: OK
        System.out.println("salvando funcionário");
    }
}

try {
    funcionario.salvar();
} catch (LoginInvalidoException | FileNotFoundException e) {   // pela variável Funcionario, só essas
    e.printStackTrace();
}

Ao sobrescrever, o método da subclasse pode:

  • não declarar nenhuma exceção (a implementação pode nem lançar);
  • declarar algumas ou todas as checked do original;
  • declarar versões mais específicas (filhas): FileNotFoundException no lugar de IOException;
  • declarar qualquer unchecked (ArithmeticException...), porque elas não obrigam tratamento.

E não pode:

  • declarar uma checked mais genérica (mãe): se o original lança FileNotFoundException, a sobrescrita não pode lançar IOException;
  • declarar uma checked nova, que o original não declara (ex.: Exception).

O motivo é o polimorfismo: quem usa uma variável Pessoa só se preparou para as exceções de Pessoa.salvar(). A subclasse não pode surpreendê-lo com uma checked que ele não trata. O William avisa que isso cai em prova de certificação e entrevista.

Atenção

  • Ordem dos catch: filha antes da mãe. Mãe antes da filha não compila (código inalcançável).
  • Multi-catch: nada da mesma linha de herança, e a variável é implicitamente final.
  • try-with-resources: só AutoCloseable/Closeable, fecha na ordem inversa, e o close() roda antes do catch/finally.
  • Extra: nunca dê return dentro do finally. Ele sobrescreve o return do try e engole a exceção lançada.
  • Extra: o finally não roda com System.exit() (a JVM termina na hora).
  • Extra: se o corpo e o close() lançarem exceção no try-with-resources, a do corpo vence e a do close() fica em e.getSuppressed().
  • Extra: Java 9+ aceita uma variável já existente (efetivamente final) nos parênteses: try (leitor1) { ... }.
  • Extra: dê à exceção customizada um construtor com causa: public LoginInvalidoException(String msg, Throwable cause) { super(msg, cause); }.

Paralelo com PHP

  • finally existe igual (PHP 5.5+), inclusive a pegadinha do return no finally.
  • Multi-catch: catch (InvalidArgumentException | DomainException $e), desde o PHP 7.1.
  • Não existe try-with-resources no PHP. Recursos (fopen, PDO) são liberados quando a última referência some ou no fim da requisição. Quando importa, faz-se fclose() no finally. O parente mais próximo no Laravel é DB::transaction(function () { ... }), que faz commit ou rollback sozinho mesmo com exceção.
  • Exceção customizada: class LoginInvalidoException extends Exception. No Laravel, ela pode ter os métodos report() e render($request), e o Handler os usa para logar e devolver a resposta (por exemplo, um 401).
  • Regras de sobrescrita com throws: não existem no PHP, porque não há checked exceptions. O equivalente é a regra de assinatura compatível (tipos de parâmetro e retorno), que o PHP 8 verifica.

Glossário

  • finally: bloco que sempre roda ao sair do try, com ou sem exceção.
  • Recurso: algo externo pedido ao SO ou a outro sistema (arquivo, conexão) que precisa ser fechado.
  • Multi-catch: um catch para várias exceções, separadas por |.
  • try-with-resources: try (recurso), que chama close() automaticamente.
  • AutoCloseable / Closeable: interfaces com o método close(), exigidas pelo try-with-resources.
  • Exceção customizada: classe sua que estende Exception (checked) ou RuntimeException (unchecked).
  • Código inalcançável: código que o compilador prova que nunca roda (ex.: catch de filha depois da mãe); é erro de compilação.
  • Exceção suprimida (extra): exceção do close() guardada em getSuppressed() quando o corpo já tinha falhado.
