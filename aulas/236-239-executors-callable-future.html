Resumo

Criar uma new Thread para cada tarefa é o jeito de "mais baixo nível". O problema: se cada requisição de usuário criar uma thread, mil usuários são mil threads, cada uma um objeto com memória e processamento próprios, e a aplicação vai para o espaço. O framework Executor resolve isso com um objetivo: desacoplar a submissão das tarefas da execução. Você entrega tarefas a um pool de threads reaproveitáveis, e o executor decide quando e em qual thread cada uma roda. Depois vêm as tarefas agendadas, as tarefas que devolvem resultado (Callable) e o Future, a "promessa" de um resultado que ainda vai chegar.

ExecutorService pool = Executors.newFixedThreadPool(4);   // 236 · pool com 4 threads
pool.execute(runnable);                                    // 236 · entrega a tarefa (sem start!)
scheduler.scheduleAtFixedRate(r, 1, 5, TimeUnit.SECONDS);  // 237 · repete a cada 5 s
Future<String> f = pool.submit(callable);                 // 238 · tarefa com retorno
f.get(3, TimeUnit.SECONDS);                                // 239 · espera o resultado, com limite
pool.shutdown();                                           // não aceita mais tarefas

236 · Executors pt 01: thread pools

class Printer implements Runnable {
    private final int num;
    public Printer(int num) { this.num = num; }

    @Override
    public void run() {
        System.out.printf("%s inicio: %d%n", Thread.currentThread().getName(), num);
        try {
            TimeUnit.SECONDS.sleep(3);
        } catch (InterruptedException e) {
            e.printStackTrace();
        }
        System.out.printf("%s finalizou%n", Thread.currentThread().getName());
    }
}

public class ExecutorsTest01 {
    public static void main(String[] args) {
        //submission of tasks is decoupled of the execution
//      ExecutorService executorService = Executors.newFixedThreadPool(Runtime.getRuntime().availableProcessors());
//      ExecutorService executorService = Executors.newSingleThreadExecutor();
        ExecutorService executorService = Executors.newCachedThreadPool();
        executorService.execute(new Printer(1));
        executorService.execute(new Printer(2));
        // ... até new Printer(6)
        executorService.shutdown();
        System.out.println("Programa finalizado");
    }
}
  • Você não chama mais start(): executorService.execute(runnable) entrega a tarefa, e o executor decide quando rodar. Isso dá flexibilidade: com start(), "já era, não tem mais o que fazer".
  • Executors.newFixedThreadPool(4): número fixo de threads. Com 6 tarefas e 4 threads, as 4 primeiras rodam, e quando uma termina, a mesma thread pega a tarefa 5 (pool-1-thread-1 inicio: 5). Com 500 tarefas continuariam sendo 4 threads, e isso é ótimo para um sistema que precisa escalar: o número de threads não explode com o número de usuários.
  • Quantas threads? Uma referência é Runtime.getRuntime().availableProcessors(): a máquina do professor tem 4 núcleos com hyper-threading, então 8 processadores lógicos. Mas "não é uma matemática muito precisa": o sistema roda milhares de threads com só 8 processadores.
  • newSingleThreadExecutor(): uma thread só, e as tarefas são executadas uma depois da outra, na ordem.
  • newCachedThreadPool(): cria threads conforme a necessidade e reaproveita as que estiverem livres; uma thread ociosa por 60 segundos é encerrada e removida do cache. Com 6 tarefas simultâneas, cria 6 threads.
  • shutdown() não interrompe nada: só avisa que o executor não aceita novas tarefas e deve encerrar quando as atuais terminarem. Por isso "Programa finalizado" aparece antes dos "finalizou". Sem shutdown(), o programa não termina: as threads do pool continuam vivas esperando trabalho.
  • Para esperar tudo terminar, o professor mostrou (sem deixar no repositório) um laço while (!executorService.isTerminated()) {}, que ele mesmo chama de gambiarra: ele fica girando e gastando CPU. Extra: o jeito certo é executorService.awaitTermination(1, TimeUnit.MINUTES), que bloqueia sem gastar CPU.

237 · ScheduledExecutorService

"Como executar uma tarefa a cada 5 segundos? Ou daqui a um dia? Ou uma vez por dia?" O ScheduledExecutorService é o seu melhor amigo.

public class ScheduledThreadPoolTest01 {
    private static final ScheduledExecutorService executor = Executors.newScheduledThreadPool(1);
    private static final DateTimeFormatter formatter = DateTimeFormatter.ofPattern("HH:mm:ss");

    private static void beeper() {
        Runnable r = () -> {
            System.out.println(LocalTime.now().format(formatter) + " beep");
            try {
                TimeUnit.SECONDS.sleep(5);                 // a tarefa demora 5 s
            } catch (InterruptedException e) {
                e.printStackTrace();
            }
        };
//      executor.schedule(r, 5, TimeUnit.SECONDS);         // uma vez, daqui a 5 s
        ScheduledFuture<?> scheduleWithFixedDelay = executor.scheduleWithFixedDelay(r, 1, 5, TimeUnit.SECONDS);
//      ScheduledFuture<?> scheduleWithFixedDelay = executor.scheduleAtFixedRate(r, 1, 5, TimeUnit.SECONDS);
        executor.schedule(() -> {
            System.out.println("Cancelando o scheduleWithFixedDelay");
            scheduleWithFixedDelay.cancel(false);
            executor.shutdown();
        }, 20, TimeUnit.SECONDS);
    }

    public static void main(String[] args) {
        System.out.println(LocalTime.now().format(formatter));
        beeper();
    }
}
  • schedule(tarefa, atraso, unidade): executa uma vez depois do atraso. Mesmo assim o programa não termina sozinho: falta o shutdown().
  • scheduleAtFixedRate(r, 1, 5, SECONDS): começa depois de 1 s e repete a cada 5 s contados a partir do início de cada execução (ritmo fixo). Se a tarefa dorme 3 s, a próxima começa 2 s depois dela terminar; se dorme 5 s, começa logo em seguida.
  • scheduleWithFixedDelay(r, 1, 5, SECONDS): espera 5 s depois que a execução anterior termina. Com a tarefa dormindo 5 s, os beeps saem de 10 em 10 segundos (5 de tarefa + 5 de intervalo).
  • O professor trocou os dois na explicação e depois corrigiu no próprio vídeo ("esquece o que eu falei") e admitiu que é difícil de lembrar. O resumo: rate é um ritmo fixo de relógio, delay é um intervalo de descanso entre uma execução e outra.
  • Parar uma repetição: os métodos devolvem um ScheduledFuture<?>; cancel(false) cancela as próximas execuções mas deixa a atual terminar (cancel(true) interromperia). O cancelamento foi agendado para 20 s depois, e o shutdown() vai junto, senão o programa continua vivo.
  • Uma lembrança do professor: um colega mandou um programa que, depois de 20 segundos, mostrava a foto da menina do Exorcista. Dá para fazer algo parecido com um schedule.

238 · Executors pt 03: Callable

Runnable tem void run(): não devolve nada e não pode lançar exceção checked. O "irmão" Callable<V> tem V call() throws Exception: devolve um valor (o tipo vem do generics) e pode lançar exceção. Ele trabalha em parceria com o ExecutorService.

class RandomNumberCallable implements Callable<String> {
    @Override
    public String call() throws Exception {
        int num = ThreadLocalRandom.current().nextInt(1, 11);   // 1 a 10
        for (int i = 0; i < num; i++) {
            System.out.printf("%s executando uma tarefa callable...%n", Thread.currentThread().getName());
        }
        return String.format("%s finished and the random number is %d", Thread.currentThread().getName(), num);
    }
}

public class CallableTest01 {
    public static void main(String[] args) throws ExecutionException, InterruptedException {
        RandomNumberCallable randomNumberCallable = new RandomNumberCallable();
        ExecutorService executorService = Executors.newFixedThreadPool(2);
        Future<String> future = executorService.submit(randomNumberCallable);   // submit, não execute
        String s = future.get();              // a main ESPERA aqui até o call() terminar
        System.out.printf("Program finished %s", s);
        executorService.shutdown();
    }
}
  • ThreadLocalRandom.current().nextInt(1, 11) × Math.random(): o Math.random() usa um gerador compartilhado e sincronizado, então várias threads disputam o lock. O ThreadLocalRandom tem um gerador por thread, sem disputa, e é o preferido em código concorrente.
  • submit(callable) devolve um Future<V>: "a resposta vem no futuro". Sem o get(), a main passa direto (o "Program finished" apareceria antes do resultado).
  • future.get() bloqueia a thread que chamou até o resultado ficar pronto. Lança InterruptedException (a espera foi interrompida) e ExecutionException (o call() lançou exceção, que vem como causa). No exemplo, elas foram jogadas no throws do main.
  • Dica: dentro de tarefas de um executor, evite wait/notify, porque você não sabe quando nem em qual thread a tarefa vai rodar.

239 · Executors pt 04: Future e programação assíncrona

  • Síncrono: uma thread faz tudo, do começo ao fim, em ordem. Foi tudo o que fizemos até as aulas de threads.
  • Assíncrono: uma thread principal continua trabalhando enquanto outra faz algo demorado. Exemplo: uma tela com o botão "consultar cotação do dólar". Se a mesma thread que desenha a tela for ao servidor remoto buscar a cotação, a tela congela até a resposta chegar. Com uma thread para a interface e outra para a requisição, a tela continua respondendo.
public class FutureTest01 {
    public static void main(String[] args) throws ExecutionException, InterruptedException, TimeoutException {
        ExecutorService executorService = Executors.newSingleThreadExecutor();
        Future<Double> dollarRequest = executorService.submit(() -> {   // lambda de Callable
            TimeUnit.SECONDS.sleep(15);    // simula um servidor lento (ou fora do ar)
            return 4.35D;
        });
        System.out.println(doSomething());                              // a main trabalha enquanto isso
        Double dollarResponse = dollarRequest.get(3, TimeUnit.SECONDS); // espera no máximo 3 s
        System.out.println("Dollar: " + dollarResponse);
        executorService.shutdown();
    }

    private static long doSomething() {
        System.out.println(Thread.currentThread().getName());          // main
        long sum = 0;
        for (int i = 0; i < 1_000_000; i++) sum += i;
        return sum;                                                      // 499999500000
    }
}
// main
// 499999500000
// Exception in thread "main" java.util.concurrent.TimeoutException
  • A lambda vira Callable (e não Runnable) porque retorna um valor e pode lançar a InterruptedException do sleep sem try/catch. Na dúvida, o professor sugere escrever primeiro a classe anônima e depois deixar o IntelliJ converter para lambda.
  • Enquanto a outra thread "consulta o servidor", a main faz a soma: as duas coisas acontecem ao mesmo tempo.
  • get() sem tempo pode travar para sempre se o servidor estiver fora do ar. Em requisições assíncronas, sempre defina um timeout: get(3, TimeUnit.SECONDS) desiste depois de 3 s e lança TimeoutException. Aí você trata, por exemplo com "não foi possível obter a cotação do dólar, tente novamente mais tarde".
  • Assíncrono ≠ parallel stream: o parallel stream divide uma tarefa entre vários núcleos para terminar antes. A programação assíncrona serve para não deixar uma thread parada esperando: enquanto uma espera o servidor, outra continua trabalhando, e os recursos da máquina ficam ocupados de forma útil.

Atenção

  • Sem shutdown(), o programa não termina: as threads do pool continuam vivas esperando tarefas.
  • shutdown() não espera nem interrompe: só fecha a porta para novas tarefas. Para esperar, use awaitTermination (extra). shutdownNow() tenta interromper as tarefas em execução e devolve as que nem começaram.
  • Correção no FutureTest01: quando o get(3, SECONDS) lança TimeoutException, o main sai pela exceção e o shutdown() nunca é chamado, então o programa fica pendurado depois da exceção. A tarefa ainda roda por 15 s, e a thread do pool continua viva depois dela. Coloque o shutdown() num finally e, no timeout, cancele a tarefa com dollarRequest.cancel(true).
  • execute(Runnable) × submit(...): execute não devolve nada; submit aceita Runnable ou Callable e devolve um Future.
  • Extra: exceção dentro de uma tarefa enviada com submit não aparece sozinha: ela fica guardada no Future e só surge como ExecutionException quando alguém chama get(). Se ninguém chamar, o erro passa em silêncio.
  • scheduleAtFixedRate × scheduleWithFixedDelay: ritmo contado do início × intervalo contado do fim.
  • Extra: tarefa agendada que lança exceção para de repetir sem aviso. Envolva o corpo da tarefa em try/catch.
  • Extra: newCachedThreadPool não tem limite: com muitas tarefas lentas ao mesmo tempo, ele cria muitas threads. Para cargas imprevisíveis, prefira um pool fixo.

Paralelo com PHP

  • Pool de threads ≈ workers de fila: php artisan queue:work rodando em N processos (ou o Horizon com maxProcesses) é um newFixedThreadPool(N): um número fixo de "trabalhadores" que pegam jobs de uma fila. O dispatch(new EnviarEmail(...)) é o execute: quem despacha não espera a execução. O Horizon com balance => 'auto' lembra o cached pool, que cresce e diminui conforme a demanda.
  • ScheduledExecutorService ≈ agendador do Laravel: Schedule::job(...)->everyFiveSeconds() / ->daily() no routes/console.php, disparado pelo cron com schedule:run (ou schedule:work). O ->withoutOverlapping() evita que uma execução comece antes da anterior terminar, uma preocupação parecida com a do fixed delay.
  • Callable/Future ≈ esperar um resultado: Concurrency::run([fn() => ..., fn() => ...]) (Laravel 11+) roda closures em paralelo e devolve os resultados, como vários submit seguidos de get(). Com o Guzzle, $client->getAsync($url) devolve uma promise e ->wait() é o get().
  • Timeout sempre: Http::timeout(3)->get(...) do Laravel é o get(3, SECONDS). A lição da aula 239 vale igual em PHP: nunca espere um serviço externo sem limite.

package academy.devdojo.maratonajava.javacore.ZZGconcorrencia.test;

import java.util.*;
import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicInteger;

public class ExecutorsPraticaTest01 {
    public static void main(String[] args) throws Exception {
        ExecutorService pool = Executors.newFixedThreadPool(2);
        try {
            // 236/238 · várias tarefas com retorno
            List<Future<Integer>> futures = new ArrayList<>();
            for (int i = 1; i <= 4; i++) {
                int n = i;
                futures.add(pool.submit(() -> n * n));          // Callable<Integer>
            }
            List<Integer> quadrados = new ArrayList<>();
            for (Future<Integer> f : futures) quadrados.add(f.get());
            System.out.println(quadrados);                                    // ?

            // quantas threads diferentes trabalharam?
            Set<String> nomes = ConcurrentHashMap.newKeySet();
            List<Callable<String>> tarefas = new ArrayList<>();
            for (int i = 0; i < 6; i++) {
                tarefas.add(() -> {
                    nomes.add(Thread.currentThread().getName());
                    TimeUnit.MILLISECONDS.sleep(100);
                    return "ok";
                });
            }
            pool.invokeAll(tarefas);                          // espera todas
            System.out.println("threads usadas: " + nomes.size());           // ?

            // 238 · exceção dentro do call()
            Future<String> comErro = pool.submit(() -> {
                if (true) throw new IllegalStateException("servidor recusou");
                return "nunca";
            });
            try {
                comErro.get();
            } catch (ExecutionException e) {
                System.out.println("ExecutionException causada por: " + e.getCause().getMessage()); // ?
            }

            // 239 · timeout e cancel
            Future<Double> dolar = pool.submit(() -> {
                TimeUnit.SECONDS.sleep(5);
                return 4.35;
            });
            System.out.println("pronto? " + dolar.isDone());                   // ?
            try {
                dolar.get(300, TimeUnit.MILLISECONDS);
            } catch (TimeoutException e) {
                System.out.println("TimeoutException: tente mais tarde");     // ?
                dolar.cancel(true);
            }
            System.out.println("cancelado? " + dolar.isCancelled());           // ?
        } finally {
            pool.shutdown();                                  // no finally: sempre roda
        }
        System.out.println("terminou? " + pool.awaitTermination(2, TimeUnit.SECONDS)); // ?

        // 237 · agendamento
        ScheduledExecutorService agenda = Executors.newScheduledThreadPool(1);
        ScheduledFuture<String> umaVez = agenda.schedule(() -> "executou depois de 200 ms", 200, TimeUnit.MILLISECONDS);
        System.out.println(umaVez.get());                                     // ?
        AtomicInteger beeps = new AtomicInteger();
        ScheduledFuture<?> repetindo = agenda.scheduleAtFixedRate(beeps::incrementAndGet, 0, 100, TimeUnit.MILLISECONDS);
        TimeUnit.MILLISECONDS.sleep(550);
        repetindo.cancel(false);
        agenda.shutdown();
        System.out.println("beeps: " + beeps.get());                           // ?
    }
}
EOF

Glossário

  • Executor/ExecutorService: serviço que recebe tarefas e as executa em threads que ele gerencia.
  • Thread pool: conjunto de threads reaproveitadas para executar várias tarefas.
  • Executors: classe com métodos-fábrica para criar pools (newFixedThreadPool, newCachedThreadPool...).
  • shutdown: para de aceitar tarefas e encerra quando as atuais terminarem.
  • ScheduledExecutorService: executor que roda tarefas com atraso ou periodicamente.
  • Fixed rate: período contado do início de cada execução.
  • Fixed delay: intervalo contado do fim de cada execução.
  • Callable<V>: tarefa que devolve V e pode lançar exceção (call()).
  • Future<V>: representa um resultado que ficará pronto no futuro (get, isDone, cancel).
  • ExecutionException: embrulha a exceção lançada dentro da tarefa.
  • TimeoutException: o get com tempo limite desistiu de esperar.
  • Síncrono × assíncrono: esperar cada coisa terminar × seguir trabalhando enquanto outra thread espera.
  • ThreadLocalRandom: gerador de aleatórios com uma instância por thread, sem disputa.
