Resumo

Você já usa generics desde as coleções (List<String>). Agora vem o porquê e o como. Generics deixam uma classe ou um método trabalhar com um tipo que só é definido na hora do uso, com checagem em tempo de compilação. Por causa da compatibilidade com código antigo, o tipo é apagado depois de compilar (type erasure). Isso explica as regras dos wildcards (? extends, ? super). No fim, você cria as suas classes genéricas (RentalService<T>) e os seus métodos genéricos (<T> List<T> metodo(T t)).

183 · Por que generics e o type erasure

// Até o Java 1.4: lista de Object, qualquer coisa entra
List lista = new ArrayList();
lista.add("Midoriya");
lista.add(1L);
for (Object o : lista) {
    if (o instanceof String) { ... } else if (o instanceof Long) { ... }   // instanceof para tudo
}

// Java 5+: o COMPILADOR garante o tipo
List<String> lista = new ArrayList<>();
lista.add("Midoriya");
lista.add("Midoriya");

// Mas depois de compilado o tipo SOME (type erasure). Um método com List "crua" burla:
private static void add(List lista, Consumidor consumidor) {   // sem <>
    lista.add(consumidor);                                     // compila (só um aviso)
}
add(lista, new Consumidor("Midoriya"));                        // roda sem erro...
for (String o : lista) { System.out.println(o); }             // ...ClassCastException AQUI, bem depois
for (Object o : lista) { System.out.println(o); }             // com Object imprime tudo (inclusive o Consumidor)
  • Sem generics, a lista aceitava qualquer Object. Para usar, era um instanceof para cada tipo possível (imagine 60 ou 70 classes). "Se você der liberdade, alguém vai fazer besteira."
  • Generics são uma checagem do compilador. O Java precisava manter compatibilidade com bilhões de linhas antigas. Por isso o tipo só existe em tempo de compilação e é apagado no bytecode: a JVM enxerga só uma List. Isso se chama type erasure.
  • A consequência: usando tipos "crus" (sem <>), dá para enfiar um Consumidor numa List<String>. Não há erro na hora. A ClassCastException só aparece quando alguém lê o elemento como String. Por isso: sempre declare o tipo.

184 · Arrays × List: por que List<Cachorro> não é List<Animal>

abstract class Animal { public abstract void consulta(); }
class Cachorro extends Animal { public void consulta() { System.out.println("Consultando doguinho"); } }
class Gato extends Animal { public void consulta() { System.out.println("Consultando Gato"); } }

// ARRAYS: aceitam o subtipo (polimorfismo)...
private static void printConsulta(Animal[] animals) {
    for (Animal animal : animals) animal.consulta();
    // animals[1] = new Gato();      ← compila, mas num Cachorro[] dá ArrayStoreException (em execução)
}
printConsulta(new Cachorro[]{new Cachorro(), new Cachorro()});   // OK
printConsulta(new Gato[]{new Gato(), new Gato()});               // OK

// LISTAS: NÃO aceitam
private static void printConsulta(List<Animal> animals) { ... animals.add(new Cachorro()); }
List<Cachorro> cachorros = List.of(new Cachorro(), new Cachorro());
// printConsulta(cachorros);         ← NÃO compila
  • Um array sabe seu tipo em tempo de execução. Se você tentar pôr um Gato num Cachorro[] recebido como Animal[], a JVM percebe e lança ArrayStoreException. Por isso o Java deixa passar Cachorro[] onde se espera Animal[].
  • Uma lista não sabe (type erasure): em execução é só uma List. Se List<Cachorro> fosse aceita como List<Animal>, o método poderia fazer animals.add(new Gato()) e ninguém perceberia. Então o compilador proíbe: numa lista, o parâmetro tem que ser exatamente o tipo declarado.
  • Dentro de uma List<Animal> de verdade você pode adicionar Cachorro e Gato, como Animal a = new Gato(). O problema é só aceitar a lista de um subtipo como parâmetro.

185 · Wildcards: ? extends e ? super

// Aceita List<Animal>, List<Cachorro>, List<Gato>... → só LEITURA
private static void printConsulta(List<? extends Animal> animals) {
    for (Animal animal : animals) animal.consulta();   // ler como Animal: seguro
    // animals.add(new Cachorro());                   ← NÃO compila
}

// Aceita List<Animal> e List<Object> → pode ESCREVER Animal e subtipos
private static void printConsultaAnimal(List<? super Animal> animals) {
    animals.add(new Cachorro());                      // OK
    animals.add(new Gato());                          // OK
    // Animal a = animals.get(0);                     ← NÃO compila: só dá para ler como Object
}

printConsulta(cachorros);                     // OK
printConsulta(gatos);                         // OK
printConsultaAnimal(new ArrayList<Animal>());  // OK
// printConsultaAnimal(cachorros);            ← NÃO compila (Cachorro é subclasse, não super)
  • ? é o coringa (wildcard).
  • List<? extends Animal>: "uma lista de algum tipo que é Animal ou filho". Você lê tudo como Animal, mas não pode adicionar. Se a lista for de Cachorro, um Gato estragaria tudo, e o compilador não sabe qual é. É um contrato de somente leitura.
  • A palavra é sempre extends, mesmo para interface: List<? extends Comparable>. Nunca implements.
  • List<? super Animal>: "uma lista de Animal ou de um pai dele" (Animal, Object). Aqui pode adicionar Animal e qualquer filho, porque qualquer que seja a lista, ela aceita um Animal. Em troca, ao ler você só tem garantia de Object (e precisaria de instanceof).
  • Resumo extra (PECS, "Producer Extends, Consumer Super"): se a lista fornece dados para você (leitura), use extends. Se ela recebe dados (escrita), use super.

186 · O problema: duas classes quase iguais

public class CarroRentavelService {
    private List<Carro> carrosDisponiveis = new ArrayList<>(List.of(new Carro("BMW"), new Carro("Fusca")));

    public Carro buscarCarroDisponivel() {
        System.out.println("Buscando carro disponivel....");
        Carro carro = carrosDisponiveis.remove(0);
        System.out.println("Alugando carro: " + carro);
        System.out.println("Carros disponíveis para alugar:");
        System.out.println(carrosDisponiveis);
        return carro;
    }

    public void retornarCarroAlugado(Carro carro) {
        System.out.println("Devolvendo carro " + carro);
        carrosDisponiveis.add(carro);
        System.out.println("Carros disponíveis para alugar: ");
        System.out.println(carrosDisponiveis);
    }
}
// BarcoRentavelService: a MESMA classe trocando Carro por Barco (Lancha, Canoa)
  • Um sistema de aluguel: o ArrayList faz o papel do "banco de dados" dos carros disponíveis. Ele é criado a partir de List.of, que é imutável, porque o remove/add precisam alterar a lista.
  • Para alugar barcos, o William copiou a classe e usou o find/replace da IDE (Ctrl+R, com "diferenciar maiúsculas") para trocar Carro por Barco. Linha por linha é a mesma classe: só muda o tipo. É justamente o que os generics resolvem.

187 · Classe genérica: RentalService<T>

public class RentalService<T> {                   // T = um tipo definido por quem usar a classe
    private List<T> objetosDisponiveis;

    public RentalService(List<T> objetosDisponiveis) {   // a lista vem de fora (banco, arquivo...)
        this.objetosDisponiveis = objetosDisponiveis;
    }

    public T buscarObjetoDisponivel() {
        System.out.println("Buscando objeto disponivel....");
        T t = objetosDisponiveis.remove(0);
        System.out.println("Alugando objeto: " + t);
        System.out.println("Objetos disponíveis para alugar:");
        System.out.println(objetosDisponiveis);
        return t;
    }

    public void retornarObjetoAlugado(T t) {
        System.out.println("Devolvendo objeto " + t);
        objetosDisponiveis.add(t);
        System.out.println("Objetos disponíveis para alugar: ");
        System.out.println(objetosDisponiveis);
    }
}

RentalService<Carro> rentalServiceCarro = new RentalService<>(carrosDisponiveis);
Carro carro = rentalServiceCarro.buscarObjetoDisponivel();     // devolve Carro, sem cast
rentalServiceCarro.retornarObjetoAlugado(carro);

RentalService<Barco> rentalServiceBarco = new RentalService<>(barcosDisponiveis);
Barco barco = rentalServiceBarco.buscarObjetoDisponivel();     // a MESMA classe, agora para Barco
  • class RentalService<T> declara um parâmetro de tipo. Dentro da classe, T é usado onde antes estava Carro. Quem cria o objeto decide o que é T, e o compilador troca T por Carro (ou Barco) em todo lugar. O Ctrl+P no construtor já mostra "pede uma List<Carro>".
  • A letra é convenção: T (type), E (element, nas coleções), K/V (key/value, no Map). Dá para usar vários: class Par<K, V>.
  • A lista deixou de ser criada dentro da classe: agora vem pelo construtor. Criar objeto de um tipo genérico (new T()) não é possível, justamente por causa do erasure.
  • Uma classe substitui duas, três, quatro. Os frameworks (Spring, Hibernate) usam isso o tempo todo, como o JpaRepository<Entidade, Id>. O William avisa: no começo de um sistema você quase não precisa, mas quando o mesmo código começa a se repetir para tipos diferentes, é hora de generalizar. E com cuidado, porque generics demais deixam o código difícil de ler.

188 · Método genérico

private static <T> List<T> criarArrayComUmObjeto(T t) {   // <T> entre o modificador e o retorno
    return List.of(t);
}
List<Barco> barcoList = criarArrayComUmObjeto(new Barco("Canoa Marota"));   // T inferido: Barco
System.out.println(barcoList);                                               // [Barco{nome='Canoa Marota'}]

// Com restrição (bounded type): só aceita tipos Comparable
private static <T extends Comparable<T>> List<T> criarArrayComUmObjeto(T t) { return List.of(t); }
// criarArrayComUmObjeto(new Barco("x"));   ← NÃO compila: Barco não é Comparable

// Também dá para ter vários tipos e usá-los em atributos e construtores:
// class Exemplo<T, X, Y> { private T t; private X x; ... }
  • Quando só um método precisa ser genérico, não é preciso tornar a classe genérica: declare <T> antes do tipo de retorno (depois de public/private/static).
  • Na chamada nada muda: o compilador infere o T pelo argumento (aqui, Barco).
  • <T extends Comparable<T>> restringe T a tipos comparáveis. Assim o compilador deixa você chamar t.compareTo(...) e barra quem não é.
  • Você já viu isso sem perceber: List.of(E... e) e Collections.sort(List<T>) com <T extends Comparable<? super T>> são métodos genéricos com wildcard. "Começa a ficar bem complicado", mas agora você consegue ler.

Atenção

  • Generics = checagem em compilação. Em execução o tipo não existe (type erasure). Nunca use tipos crus (List sem <>).
  • List<Cachorro> não é uma List<Animal> (generics são "invariantes"). Arrays aceitam, mas pagam com ArrayStoreException em execução.
  • ? extends: lê, não escreve. ? super: escreve, lê só como Object.
  • Extra: por causa do erasure, não dá para fazer new T(), new T[10] nem obj instanceof List<String>. Generics também não aceitam primitivos: RentalService<int> não existe, use Integer.
  • Extra: List<?> (coringa sem limite) aceita lista de qualquer coisa, e é só leitura como Object. List<Object> é diferente: só aceita exatamente List<Object>.

Paralelo com PHP

  • O PHP não tem generics na linguagem. array e Collection aceitam qualquer coisa, como a List crua do Java 1.4. Um erro de tipo só aparece em execução, quando alguém usa o elemento, igual à ClassCastException tardia da aula 183.
  • O equivalente vem da análise estática: PHPStan/Psalm leem docblocks como @template T, @param list<T> $itens e @return T. É a mesma ideia do Java (checagem antes de rodar), só que feita por uma ferramenta, não pelo compilador. O Laravel já anota assim: Collection<TKey, TValue>, @extends Factory<User>.
  • O RentalService<T> no PHP seria uma classe com @template T e os métodos anotados com T. Ou, mais comum no Laravel, uma classe base de repositório recebendo o nome do Model (protected string $model = Carro::class). Funciona, mas sem garantia de tipo em lugar nenhum.
  • Variância: no PHP 7.4+ a sobrescrita aceita retornos covariantes e parâmetros contravariantes (a mesma lógica de "ler é extends, escrever é super"), mas só em assinaturas de métodos, não em coleções.

import academy.devdojo.maratonajava.javacore.Zgenerics.dominio.Barco;

public class GenericsTest01 {
    @SuppressWarnings({"rawtypes", "unchecked"})
    private static void add(List lista, Object o) { lista.add(o); }       // tipo cru: burla o compilador

    private static void printConsulta(List<? extends Animal> animals) {

        System.out.println(nomes.size());                   // ?

            for (String n : nomes) System.out.println(n.toUpperCase());   // ?
        } catch (ClassCastException e) {
            System.out.println("ClassCastException ao LER");
        }

        printConsulta(List.of(new Cachorro(), new Cachorro()));   // ?
        printConsulta(List.of(new Gato()));                       // ?
        List<Object> objetos = new ArrayList<>();
        adicionaAnimais(objetos);                                 // List<Object> é "super" de Animal
        System.out.println(objetos.size());                       // ?

        RentalService<Carro> carros = new RentalService<>(new ArrayList<>(List.of(new Carro("BMW"), new Carro("Fusca"))));

        List<Barco> barcoList = criarArrayComUmObjeto(new Barco("Canoa Marota"));
        System.out.println(barcoList);                            // ?
        System.out.println(maior("Goku", "Vegeta") + " " + maior(3, 7));   // ?
    }
}

Glossário

  • Generics: parâmetros de tipo em classes e métodos, checados em compilação.
  • Type erasure: o apagamento do tipo genérico no bytecode, por compatibilidade.
  • Tipo cru (raw type): usar a classe genérica sem <> (List); desliga a checagem.
  • Parâmetro de tipo: o T declarado em class X<T> ou <T> void m().
  • Wildcard (?): coringa que representa "algum tipo".
  • ? extends X (limite superior): X ou subtipos; só leitura.
  • ? super X (limite inferior): X ou supertipos; permite adicionar X.
  • Bounded type: <T extends Comparable<T>>, um tipo genérico com restrição.
  • Inferência de tipo: o compilador deduz o T pelos argumentos ou pela atribuição.
  • ArrayStoreException: erro ao guardar num array um objeto incompatível com o tipo real dele.
