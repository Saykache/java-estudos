Resumo

Com a conexão pronta, o bloco faz o CRUD da tabela producer com a forma mais simples do JDBC, o Statement: você monta o texto do SQL e manda executar. O código vai sendo organizado em camadas (domínio, repositório, serviço), ganha Lombok para acabar com getters/builders escritos na mão e Log4j 2 no lugar do System.out.println. O professor avisa que esta forma é a introdução: montar SQL concatenando texto tem problemas graves, resolvidos com PreparedStatement nas aulas 268–269.

try (Connection conn = ConnectionFactory.getConnection();

}
try (Connection conn = ConnectionFactory.getConnection();
     Statement stmt = conn.createStatement();
     ResultSet rs = stmt.executeQuery("SELECT id, name FROM anime_store.producer")) { // 261
    while (rs.next()) { rs.getInt("id"); rs.getString("name"); }

257 · Inserindo dados com Statement

public class ConnectionFactory {
    public static Connection getConnection() throws SQLException {       // agora devolve a conexão
        String url = "jdbc:mysql://localhost:3306/anime_store";
        String username = "root";
        String password = "root";
        return DriverManager.getConnection(url, username, password);
    }
}

public class ProducerRepository {
    public static void save(Producer producer) {
        String sql = "INSERT INTO `anime_store`.`producer` (`name`) VALUES ('%s');".formatted(producer.getName());
        try (Connection conn = ConnectionFactory.getConnection();
             Statement stmt = conn.createStatement()) {
            int rowsAffected = stmt.executeUpdate(sql);
            System.out.println(rowsAffected);                              // 1
        } catch (SQLException e) {
            e.printStackTrace();
        }
    }
}

Producer producer = Producer.ProducerBuilder.builder().name("NHK").build();
ProducerRepository.save(producer);
  • Domínio (pacote dominio): a classe Producer representa a tabela producer: id e name. Um builder (aula 246) cria os objetos.
  • Repositório (pacote repository): a classe que conversa com o banco. O nome vem do mundo Spring; o padrão parecido é o DAO (Data Access Object). Métodos static, porque não usam nenhum atributo.
  • Não lembra o SQL? O Workbench gera: clique com o botão direito na tabela, Select Rows, digite um valor novo, Apply, copie o SQL que ele mostra e cancele.
  • conn.createStatement() cria o objeto que envia comandos ao banco. executeUpdate(sql) serve para tudo que altera o banco (INSERT, UPDATE, DELETE) e devolve o número de linhas afetadas.
  • Conexão e Statement precisam ser fechados. Os dois são AutoCloseable, então vão no try-with-resources (aula 103) e fecham sozinhos, na ordem inversa. Por isso o getConnection passou a lançar a SQLException em vez de devolver null: se chegou no try, a conexão existe.
  • "...('%s');".formatted(valor) (Java 15) é o String.format chamado direto na String. Para conferir o SQL montado, o professor usa o debug (breakpoint e Shift+F9).

258 · Lombok e Log4J2

Duas dependências que "vão ajudar bastante no dia a dia".

<dependency>
    <groupId>org.projectlombok</groupId>
    <artifactId>lombok</artifactId>
    <version>1.18.20</version>
    <scope>provided</scope>          <!-- só na compilação -->
</dependency>
<dependency>
    <groupId>org.apache.logging.log4j</groupId>
    <artifactId>log4j-core</artifactId>
    <version>2.14.1</version>          <!-- VULNERÁVEL: veja o Atenção -->
</dependency>

@Value                 // classe final, atributos private final, getters, equals/hashCode/toString, construtor
@Builder               // Producer.builder().id(1).name("NHK").build()
public final class Producer {
    private final Integer id;
    private final String name;
}
  • Lombok gera código na compilação a partir de anotações: @Getter, @Setter, @ToString, @EqualsAndHashCode, @Data, @Value (classe imutável), @Builder... O site projectlombok.org tem um vídeo de 4 minutos. No IntelliJ é preciso ligar Settings, Build, Compiler, Annotation Processors, Enable annotation processing.
  • O Producer de 58 linhas virou 4. Para provar, o professor abre o .class compilado em target/classes: estão lá o construtor, getId(), getName(), equals, hashCode, toString e o builder(). Com @Value, o private final dos atributos é redundante (o IntelliJ avisa), mas ele deixa escrito para quem está começando.
  • O builder gerado muda a chamada: Producer.builder() em vez de Producer.ProducerBuilder.builder().
  • Algumas empresas não gostam de Lombok. Para quem está aprendendo, se a empresa permite, "não tem por que não usar".

Log: em ambiente corporativo você nunca usa System.out.println. É ruim para o desempenho e não diz quando, em qual thread nem com que gravidade a mensagem aconteceu. O @Log4j2 do Lombok cria o atributo log, e é preciso o Log4j 2 no pom.xml e um arquivo de configuração em src/main/resources/log4j2.xml:

<Configuration status="INFO">
    <Appenders>
        <Console name="LogToConsole" target="SYSTEM_OUT">
            <PatternLayout pattern="%d{HH:mm:ss.SSS} [%t] %-5level %logger{1.} - %msg%n"/>
        </Console>
    </Appenders>
    <Loggers>
        <!-- avoid duplicated logs with additivity=false -->
        <Logger name="academy.devdojo" level="info" additivity="false">
            <AppenderRef ref="LogToConsole"/>
        </Logger>
        <Root level="error">
            <AppenderRef ref="LogToConsole"/>
        </Root>
    </Loggers>
</Configuration>

@Log4j2
public class ProducerRepository {
    ...
    log.info("Inserted producer in the database, rows affected '{}'", rowsAffected);
}
// 14:32:05.123 [main] INFO  a.d.m.j.Z.r.ProducerRepository - Inserted producer in the database, rows affected '1'
  • Padrão da linha: %d hora, [%t] thread, %-5level nível, %logger classe, %msg mensagem. Na aula 259, %logger{36} virou %logger{1.}, que abrevia cada pacote para uma letra (a.d.m.j.Z.r.ProducerRepository), porque os nomes de classe já costumam ser únicos.
  • {} é o marcador: log.info("... '{}'", valor) troca o {} pelo argumento (o professor gosta de pôr entre aspas simples para destacar o que é valor).
  • Níveis, do mais detalhado ao mais grave: trace, debug, info, warn, error, fatal. O level="info" do logger mostra info para cima. Trocando para debug, aparece muito mais coisa. Em produção geralmente fica info e sem debug, que pode conter dados sensíveis. Localmente, debug ajuda.
  • Em produção muitas vezes você não tem acesso ao código em execução, só ao log. Por isso mensagens informativas ("inserido produtor X, linhas afetadas 1") valem ouro.
  • Existem outras bibliotecas (Logback, SLF4J), cada uma com seu arquivo de configuração.

259 · Deletando dados e a camada de serviço

public static void delete(int id) {
    String sql = "DELETE FROM `anime_store`.`producer` WHERE (`id` = '%d');".formatted(id);
    try (Connection conn = ConnectionFactory.getConnection();
         Statement stmt = conn.createStatement()) {
        int rowsAffected = stmt.executeUpdate(sql);
        log.info("Deleted producer '{}' from the database, rows affected '{}' ", id, rowsAffected);
    } catch (SQLException e) {
        log.error("Error while trying to delete producer '{}'", id, e);   // a exceção vai por último
    }
}

public class ProducerService {                       // regras de negócio
    public static void save(Producer producer) { ProducerRepository.save(producer); }
    public static void delete(int id) {
        if (id <= 0) throw new IllegalArgumentException("Invalid value for id");
        ProducerRepository.delete(id);
    }
}

// no main: ProducerService.delete(5);   (não mais o repositório direto)
  • O e.printStackTrace() virou log.error("mensagem '{}'", valor, e). Passando a exceção como último argumento, o Log4j imprime a pilha junto.
  • Camadas: Producer é o domínio (a tabela), ProducerRepository fala com o banco, ProducerService tem as regras de negócio (id não pode ser ≤ 0, porque a chave auto incrementada nunca é negativa) e o main faz o papel da tela (a view). O professor compara com o MVC. A vantagem: mudanças no repositório não obrigam a mexer em quem chama, desde que o "contrato" (os métodos) se mantenha.
  • O auto increment não reaproveita ids apagados: depois de deletar o 11, o próximo inserido é o 12. "É normal, não precisa se preocupar."

public static void update(Producer producer) {
    String sql = "UPDATE `anime_store`.`producer` SET `name` = '%s ' WHERE (`id` = '%d');"
            .formatted(producer.getName(), producer.getId());
    ...
    log.info("Updated producer '{}', rows affected '{}' ", producer.getId(), rowsAffected);
}

public class ProducerService {
    public static void delete(Integer id) { requireValidId(id); ProducerRepository.delete(id); }
    public static void update(Producer producer) { requireValidId(producer.getId()); ProducerRepository.update(producer); }

    private static void requireValidId(Integer id) {            // regra reaproveitada
        if (id == null || id <= 0) throw new IllegalArgumentException("Invalid value for id");
    }
}

Producer producerToUpdate = Producer.builder().id(1).name("MADHOUSE").build();
ProducerService.update(producerToUpdate);
  • Normalmente o id nunca é alterado, só os outros campos (aqui, o name).
  • Nunca esqueça o WHERE. O professor conta o caso de um órgão público em que alguém rodou um UPDATE sem WHERE e alterou milhões de registros. A dica: comece a escrever já com o WHERE, porque "isso pode destruir uma empresa".
  • Não coloque dados que identificam pessoas no log (PII, personally identifiable information): nome, e-mail, CPF. Logue o id.
  • A validação repetida virou o método privado requireValidId, que também trata null (por isso int virou Integer).

261 · Buscando dados com ResultSet: findAll

public static List<Producer> findAll() {
    log.info("Finding all Producers");
    String sql = "SELECT id, name FROM anime_store.producer;";
    List<Producer> producers = new ArrayList<>();
    try (Connection conn = ConnectionFactory.getConnection();
         Statement stmt = conn.createStatement();
         ResultSet rs = stmt.executeQuery(sql)) {          // ResultSet também é fechado
        while (rs.next()) {                                 // avança o cursor; false no fim
            Producer producer = Producer
                    .builder()
                    .id(rs.getInt("id"))
                    .name(rs.getString("name"))
                    .build();
            producers.add(producer);
        }
    } catch (SQLException e) {
        log.error("Error while trying to find all producers", e);
    }
    return producers;                                       // lista vazia, nunca null
}

List<Producer> producers = ProducerService.findAll();
log.info("Producers found '{}'", producers);
// Producers found '[Producer(id=1, name=MADHOUSE), Producer(id=2, name=NHK), ...]'
  • executeQuery(sql) é para SELECT e devolve um ResultSet. executeUpdate é para o que altera.
  • O ResultSet tem um cursor que começa antes da primeira linha. Cada rs.next() avança uma linha e devolve true; no fim, false. Por isso o while (rs.next()), parecido com o Iterator (aula 174).
  • Lendo colunas: rs.getInt(...), rs.getString(...), getDouble, getDate... O argumento pode ser o índice (começando em 1, "como se já não fosse confuso o suficiente") ou o nome da coluna. O professor prefere o nome, por ser mais explícito, e por isso escreve SELECT id, name em vez de SELECT *. A IBM tem uma tabela de tipos SQL e seus equivalentes em Java (INT → int, VARCHAR → String...).
  • Cada linha vira um objeto e vai para a lista. O ArrayList aceita duplicados, então cuidado.
  • Retorne lista vazia, não null: "tratar nulo é um saco", e uma coleção vazia funciona em qualquer for.
  • Um SELECT sem filtro em produção pode trazer a tabela inteira. Use com cuidado.

262 · findByName

public static List<Producer> findAll() {
    log.info("Finding all Producers");
    return findByName("");                                  // LIKE '%%' = todos
}

public static List<Producer> findByName(String name) {
    log.info("Finding Producer by name");
    String sql = "SELECT * FROM anime_store.producer where name like '%%%s%%';"
            .formatted(name);                               // %% vira %, %s vira o nome
    ... // o mesmo while (rs.next()) do findAll
}

ProducerService.findByName("Mad");   // → '%Mad%' → Madhouse, MADHOUSE...
  • LIKE '%texto%': % é o curinga do SQL ("qualquer coisa"). '%%' casa com tudo.
  • No formatted, % é caractere especial, então para ter um % literal escreve-se %%: '%%%s%%' vira '%Mad%'. O professor tentou \% e concatenação antes de acertar.
  • Reaproveitamento: findAll virou findByName("") e o código do while ficou num lugar só.
  • Outra ideia citada: guardar os SQLs numa classe separada ou num arquivo de propriedades.

Atenção

  • SQL injection (extra, e o grande problema deste bloco): montar SQL com formatted/concatenação deixa o texto do usuário virar SQL. Um findByName("x' OR 1=1 -- ") gera ... like '%x' OR 1=1 -- %' e devolve todos os registros; algo como "'; DROP TABLE ..." pode ser pior. Um nome legítimo com apóstrofo (Kyoto's Animation) quebra o SQL com erro de sintaxe. A solução é o PreparedStatement com ?, das aulas 268–269, e em código real ele é obrigatório.
  • Correção: o UPDATE do repositório tem um espaço sobrando, SET `name` = '%s '. O nome é gravado como "MADHOUSE ", com espaço no fim, o que quebra comparações com =. O certo é '%s'.
  • Correção de segurança: Log4j 2.14.1 é vulnerável ao Log4Shell (CVE-2021-44228, descoberto em dezembro de 2021, meses depois da gravação). Uma mensagem de log com ${jndi:ldap://...} permitia a um atacante executar código no servidor. Use a versão 2.17.1 ou mais nova (a prática usa 2.24.x) e acrescente também log4j-api.
  • executeUpdate × executeQuery: o primeiro altera e devolve int (linhas afetadas); o segundo lê e devolve ResultSet.
  • Feche Connection, Statement e ResultSet, sempre com try-with-resources.
  • Índice de coluna começa em 1, não em 0.
  • Extra: '%d' com aspas no DELETE funciona no MySQL (ele converte o texto para número), mas o correto para número é sem aspas.
  • Extra: com Lombok, o IntelliJ precisa do plugin (já vem nas versões recentes) e do annotation processing ligado. No Maven, o Lombok no pom.xml já basta.

Paralelo com PHP

  • Statement ≈ $pdo->exec($sql) / $pdo->query($sql): exec devolve as linhas afetadas (o executeUpdate); query devolve um PDOStatement que você percorre com while ($row = $stmt->fetch()) (o while (rs.next())). E o mesmo alerta vale: "... VALUES ('$nome')" no PHP é a mesma injeção de SQL. O PHP também resolve com prepare + ?/:nome.
  • Camadas: o ProducerRepository é o que o Eloquent faz por você (Producer::create, ->update(), ->delete(), Producer::all(), where('name', 'like', "%$nome%")->get()), e o Query Builder já usa bindings, sem injeção. O ProducerService com requireValidId é o seu Service/Action ou as Form Requests de validação do Laravel.
  • Lombok ≈ o que o PHP 8 faz na linguagem: constructor promotion + readonly dão a classe imutável do @Value sem gerar código. Getters/setters mágicos lembram os accessors do Eloquent.
  • Log4j 2 ≈ Monolog (o Log::info('Inserted producer', ['rows' => $rows]) do Laravel): os mesmos níveis (debug, info, warning, error), canais (config/logging.php ≈ log4j2.xml) e contexto no lugar de {}.

package academy.devdojo.maratonajava.javacore.ZZIjdbc.repository;

import academy.devdojo.maratonajava.javacore.ZZIjdbc.conn.ConnectionFactory;
import academy.devdojo.maratonajava.javacore.ZZIjdbc.dominio.Producer;
import lombok.extern.log4j.Log4j2;

import java.sql.*;
import java.util.ArrayList;
import java.util.List;

@Log4j2
public class ProducerRepository {
    public static void save(Producer producer) {
        String sql = "INSERT INTO anime_store.producer (name) VALUES ('%s');".formatted(producer.getName());
        executeUpdate(sql, "Inserted producer", producer.getName());
    }

    public static void delete(int id) {
        executeUpdate("DELETE FROM anime_store.producer WHERE id = %d;".formatted(id), "Deleted producer", id);
    }

    public static void update(Producer producer) {         // sem o espaço sobrando do repositório
        String sql = "UPDATE anime_store.producer SET name = '%s' WHERE id = %d;"
                .formatted(producer.getName(), producer.getId());
        executeUpdate(sql, "Updated producer", producer.getId());
    }

    public static List<Producer> findAll() {
        return findByName("");
    }

    public static List<Producer> findByName(String name) {
        String sql = "SELECT id, name FROM anime_store.producer WHERE name LIKE '%%%s%%' ORDER BY id;".formatted(name);
        List<Producer> producers = new ArrayList<>();
        try (Connection conn = ConnectionFactory.getConnection();
             Statement stmt = conn.createStatement();
             ResultSet rs = stmt.executeQuery(sql)) {
            while (rs.next()) {
                producers.add(Producer.builder().id(rs.getInt("id")).name(rs.getString("name")).build());
            }
        } catch (SQLException e) {
            log.error("Error while trying to find producers by name", e);
        }
        return producers;
    }

    private static void executeUpdate(String sql, String message, Object value) {
        try (Connection conn = ConnectionFactory.getConnection();
             Statement stmt = conn.createStatement()) {
            int rowsAffected = stmt.executeUpdate(sql);
            log.info("{} '{}', rows affected '{}'", message, value, rowsAffected);
        } catch (SQLException e) {
            log.error("Error: {} '{}' - {}", message, value, e.getClass().getSimpleName());
        }
    }
}
EOF

Glossário

  • CRUD: Create, Read, Update, Delete, as quatro operações básicas.
  • Statement: objeto JDBC que executa um SQL em texto.
  • executeUpdate: executa INSERT/UPDATE/DELETE e devolve as linhas afetadas.
  • executeQuery: executa SELECT e devolve um ResultSet.
  • ResultSet: resultado de uma consulta, lido com um cursor (next()).
  • Repositório / DAO: camada que concentra o acesso ao banco.
  • Camada de serviço: onde ficam as regras de negócio, entre a tela e o repositório.
  • Lombok: biblioteca que gera código repetitivo em tempo de compilação por anotações.
  • Annotation processing: etapa do compilador que processa anotações e gera código.
  • Log4j 2: biblioteca de log da Apache; configurada por log4j2.xml.
  • Nível de log: gravidade da mensagem (trace, debug, info, warn, error, fatal).
  • PII: informação que identifica uma pessoa; não vai para o log.
  • SQL injection: ataque em que a entrada do usuário altera o SQL executado.
  • Log4Shell: falha crítica (CVE-2021-44228) do Log4j 2 até a 2.14.1.
