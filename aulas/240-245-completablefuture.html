Resumo

O cenário das seis aulas: consultar o preço de um produto em várias lojas, e cada consulta demora (um "servidor remoto" simulado com sleep). Feito uma por vez, 4 lojas × 2 s = 8 s; "com 30 lojas, você perdeu o cliente". O Future da aula 239 já permite consultar em paralelo, mas tem limites. O CompletableFuture (Java 8) é a versão completa: dispensa criar executor, tem join() sem exceção checked, pode ser completado manualmente e, principalmente, permite encadear etapas ("quando o preço chegar, monte o orçamento; quando o orçamento estiver pronto, aplique o desconto") e combinar vários resultados (allOf, anyOf).

CompletableFuture.supplyAsync(() -> service.getPriceSync(loja))   // 240 · roda em outra thread
        .thenApply(Quote::newQuote)                                // 244 · transforma o resultado
        .thenCompose(q -> CompletableFuture.supplyAsync(() -> service.applyDiscount(q))) // 244 · encadeia outra chamada assíncrona
        .thenAccept(System.out::println);                          // 245 · consome o resultado
CompletableFuture.allOf(futures).join();                           // 245 · espera todas
CompletableFuture.anyOf(futures).join();                           // 245 · espera a primeira

240 · CompletableFuture pt 01: get e join

public class StoreService {
    private static final ExecutorService ex = Executors.newCachedThreadPool();

    public double getPriceSync(String storeName) {                       // síncrono
        System.out.printf("Getting prices sync for store %s%n", storeName);
        return priceGenerator();
    }

    public Future<Double> getPricesAsyncFuture(String storeName) {       // com Future
        return ex.submit(this::priceGenerator);
    }

    public CompletableFuture<Double> getPricesAsyncCompletableFuture(String storeName) { // com CompletableFuture
        return CompletableFuture.supplyAsync(this::priceGenerator);
    }

    private double priceGenerator() {
        System.out.printf("%s generating price %n", Thread.currentThread().getName());
        delay();                                                         // sleep de 2 s
        return ThreadLocalRandom.current().nextInt(1, 500) * 10;
    }

    public static void shutdown() { ex.shutdown(); }
}
  • Síncrono: 4 chamadas de getPriceSync seguidas levam cerca de 8 s.
  • Com Future: é preciso ter um ExecutorService e lembrar do shutdown(). O StoreService ganhou um método estático shutdown(), porque não dá para desligar o executor dentro do método que envia a tarefa: ele pararia de aceitar as próximas. E a pegadinha: se você chamar get() logo depois de cada submit, continua levando 8 s, porque espera uma por vez. O certo é primeiro disparar as quatro e depois chamar os get(). Aí leva cerca de 2 s.
  • Com CompletableFuture.supplyAsync(supplier): recebe um Supplier (aula 200) e roda numa thread do ForkJoinPool comum (ForkJoinPool.commonPool-worker-1...), então não precisa criar nem desligar executor. Também cerca de 2 s.
  • join() × get(): os dois esperam o resultado, mas o join() não lança exceção checked (em caso de erro, lança CompletionException, que é unchecked), então não obriga o try/catch, e o código fica mais limpo.
  • Limitação do Future citada pelo professor: ele não pode ser completado manualmente. Se uma API não responde, você não tem como dizer "considere este valor". O CompletableFuture tem complete(valor) (e é daí que vem o nome).
  • O professor também corrigiu o FutureTest01 da aula 239: o get com timeout foi para um try/catch e o shutdown() para um finally, para o programa não ficar pendurado.

241 · CompletableFuture pt 02: cuidado com streams

List<String> stores = List.of("Store 1", "Store 2", "Store 3", "Store 4");

// ERRADO: um stream só → cerca de 8 s
List<Double> prices = stores.stream()
        .map(storeService::getPricesAsyncCompletableFuture)
        .map(CompletableFuture::join)
        .collect(Collectors.toList());

// CERTO: dois streams → cerca de 2 s
List<CompletableFuture<Double>> completableFutures = stores.stream()
        .map(storeService::getPricesAsyncCompletableFuture)
        .collect(Collectors.toList());                     // dispara TODAS primeiro
List<Double> prices = completableFutures.stream()
        .map(CompletableFuture::join)                      // depois espera
        .collect(Collectors.toList());

Por quê? As operações intermediárias do stream são lazy e processam um elemento de cada vez pelo pipeline inteiro: a "Store 1" é disparada e já cai no join, que espera 2 s; só então a "Store 2" é disparada, e assim por diante. Fica sequencial de novo. O collect no meio força disparar todas antes de começar a esperar, o mesmo truque do Future na aula 240. Vale igual para Future dentro de stream.

242 · CompletableFuture pt 03: executor e ThreadFactory

E se o serviço que você recebe só tem o método síncrono (o StoreServiceDeprecated, só com getPriceSync)? Você mesmo o torna assíncrono, embrulhando a chamada:

ExecutorService executor = Executors.newFixedThreadPool(10, r -> {   // ThreadFactory
    Thread thread = new Thread(r);
    thread.setDaemon(true);                // não segura o programa aberto
    return thread;
});

List<CompletableFuture<Double>> completableFutures = stores.stream()
        .map(s -> CompletableFuture.supplyAsync(() -> storeService.getPriceSync(s), executor)) // executor próprio
        .collect(Collectors.toList());
List<Double> prices = completableFutures.stream()
        .map(CompletableFuture::join)
        .collect(Collectors.toList());
executor.shutdown();
  • supplyAsync(supplier, executor): segundo argumento opcional para usar o seu executor no lugar do ForkJoinPool comum.
  • ThreadFactory: interface funcional (Thread newThread(Runnable r)) que os métodos de Executors aceitam para você decidir como as threads são criadas: nome, prioridade, daemon... Aqui as threads viram daemon, e o nome muda de pool-1-thread-1 para Thread-0.
  • Extra: por que um executor próprio? O pool comum tem availableProcessors() - 1 threads e é compartilhado com os parallel streams da aplicação inteira. Tarefas de I/O (esperando servidor) ocupam essas poucas threads à toa. Com 30 lojas, um pool com mais threads (e daemon, ou com shutdown) termina bem antes.

243 · Encadeando chamadas pt 01 (a partir do código)

Esta aula não tem legenda; a explicação sai do código. O cenário cresce: além do preço, cada loja devolve um código de desconto, e aplicar o desconto é outra chamada remota demorada.

public class Discount {
    public enum Code {
        NONE(0), SUPER_SAYAJIN(5), SUPER_SAYAJIN2(10), SUPER_SAYAJIN3(15);   // enum com atributo (aula 82)
        private final int percentage;
        Code(int percentage) { this.percentage = percentage; }
        public int getPercentage() { return percentage; }
    }
}

// storeName:price:discountCode
public final class Quote {                    // imutável (aula 233): final, atributos final, sem setters
    private final String store;
    private final double price;
    private final Discount.Code discountCode;

    private Quote(String store, double price, Discount.Code discountCode) { ... }  // construtor privado

    public static Quote newQuote(String value) {   // "fábrica" estática
        String[] values = value.split(":");
        return new Quote(values[0], Double.parseDouble(values[1]), Discount.Code.valueOf(values[2]));
    }
}

public class StoreServiceWithDiscount {
    public String getPriceSync(String storeName) {                    // 1 s
        double price = priceGenerator();
        Discount.Code discountCode = Discount.Code.values()[
                ThreadLocalRandom.current().nextInt(Discount.Code.values().length)];
        return String.format("%s:%.2f:%s", storeName, price, discountCode);  // "Store 1:1230.00:SUPER_SAYAJIN"
    }

    public String applyDiscount(Quote quote) {                         // mais 1 s
        delay();
        double discountValue = quote.getPrice() * (100 - quote.getDiscountCode().getPercentage()) / 100;
        return String.format("'%s' original price: '%.2f'. Applying discount code '%s'. Final price: '%.2f'",
                quote.getStore(), quote.getPrice(), quote.getDiscountCode(), discountValue);
    }
}

// versão síncrona: 4 lojas × (1 s + 1 s) ≈ 8 s
stores.stream()
        .map(service::getPriceSync)   //store:price:code
        .map(Quote::newQuote)
        .map(service::applyDiscount)
        .forEach(System.out::println);
  • A loja responde um texto no formato loja:preço:código, e Quote.newQuote o transforma num objeto com split(":"), Double.parseDouble e Discount.Code.valueOf (texto → constante do enum).
  • Enum aninhado com atributo (Discount.Code): cada constante carrega sua porcentagem. Code.values()[aleatório] sorteia um código.
  • Quote imutável, com construtor privado e um método estático que cria o objeto: um prenúncio das aulas de padrões de projeto (246+).
  • Desconto: preço × (100 − %) / 100. Com 1000 e SUPER_SAYAJIN2 (10%), 900.

244 · Encadeando chamadas pt 02: thenApply e thenCompose

List<CompletableFuture<String>> completableFutures = stores.stream()
        // Getting the price async storeName:price:discountCode
        .map(s -> CompletableFuture.supplyAsync(() -> service.getPriceSync(s)))
        // Instantiating a new Quote from the string generated by getPriceSync
        .map(cf -> cf.thenApply(Quote::newQuote))
        // Composing the first completable future
        .map(cf -> cf.thenCompose(quote -> CompletableFuture.supplyAsync(() -> service.applyDiscount(quote))))
        .collect(Collectors.toList());

completableFutures.stream()
        .map(CompletableFuture::join)
        .forEach(System.out::println);
// de ~8 s para ~2 s: cada loja ainda espera 1 s de preço + 1 s de desconto, mas as 4 em paralelo
  • thenApply(Function): quando o resultado chegar, transforma-o (String → Quote). É o map do CompletableFuture. Não há motivo para thenApplyAsync aqui: montar o Quote é rápido e depende do preço, então pode rodar na mesma thread.
  • thenCompose(Function que devolve outro CompletableFuture): quando o resultado chegar, dispara outra operação assíncrona e "achata" o resultado. Com thenApply aqui, o tipo seria CompletableFuture<CompletableFuture<String>>; o thenCompose devolve CompletableFuture<String>. É o flatMap do CompletableFuture (aula 206).
  • O desenho do professor: para cada loja, numa thread do pool, vem a tarefa 1 (getPriceSync), depois o thenApply (novo Quote), depois o thenCompose com a tarefa 2 (applyDiscount), e no fim o join devolve o preço com desconto. Isso acontece quatro vezes em paralelo.
  • E de novo: dois streams (collect antes do join), senão volta a ser sequencial.

245 · allOf e anyOf

Para simular o mundo real, o delay() virou aleatório: entre 200 e 2500 ms. Cada loja responde num tempo diferente.

var completableFutures = stores.stream()
        .map(s -> CompletableFuture.supplyAsync(() -> service.getPriceSync(s)))
        .map(cf -> cf.thenApply(Quote::newQuote))
        .map(cf -> cf.thenCompose(quote -> CompletableFuture.supplyAsync(() -> service.applyDiscount(quote))))
        .map(cf -> cf.thenAccept(store -> System.out.printf("%s finished in %d%n", store, (System.currentTimeMillis() - start))))
        .toArray(CompletableFuture[]::new);        // array de CompletableFuture

//      CompletableFuture<Void> voidCompletableFuture = CompletableFuture.allOf(completableFutures);
CompletableFuture<Object> voidCompletableFuture = CompletableFuture.anyOf(completableFutures);
voidCompletableFuture.join();
System.out.printf("Finished? %b%n", voidCompletableFuture.isDone());
  • thenAccept(Consumer): quando o resultado chegar, consome (imprime) e não devolve nada, por isso o tipo vira CompletableFuture<Void>. Cada loja imprime assim que termina, na ordem em que terminar, e não na ordem da lista.
  • toArray(CompletableFuture[]::new): allOf/anyOf recebem varargs (array), não lista. É uma referência a construtor de array (aula 200), e o IntelliJ reclama do tipo genérico "cru". O var (Java 10) evita escrever o tipo.
  • CompletableFuture.allOf(...): devolve um CompletableFuture<Void> que só completa quando todos completarem (mesmo que algum termine com exceção). Sem o join() nele, o main acaba e nada aparece, porque as threads do pool comum são daemon. O tempo total é o da loja mais lenta (cerca de 3,4 s no vídeo).
  • CompletableFuture.anyOf(...): completa assim que o primeiro completar, e devolve CompletableFuture<Object>. Uso: cotar o dólar em 5 fontes que dariam a mesma resposta e ficar com a mais rápida. No teste, só uma loja imprimiu e o programa acabou.
  • Com isso termina o bloco de concorrência.

Atenção

  • Dispare tudo antes de esperar: submit/supplyAsync de todas as tarefas primeiro, get/join depois. Num stream, isso significa dois streams com collect no meio.
  • supplyAsync sem executor usa o ForkJoinPool comum, cujas threads são daemon: se o main acabar sem join, as tarefas são abandonadas. E ele tem só núcleos − 1 threads (extra), então para muito I/O passe um executor próprio.
  • thenApply × thenCompose: a função do thenApply devolve um valor; a do thenCompose devolve outro CompletableFuture. Usar thenApply com uma função que devolve CompletableFuture gera CompletableFuture<CompletableFuture<T>>.
  • join() lança CompletionException (unchecked) se a tarefa falhou; get() lança ExecutionException (checked).
  • Extra: trate erros na corrente com exceptionally(e -> valorPadrao) ou handle((valor, erro) -> ...), senão uma loja fora do ar derruba o join do resultado inteiro.
  • Extra: anyOf não cancela os outros: as demais tarefas continuam rodando (no exemplo, só "somem" porque o programa acaba e as threads daemon morrem).
  • Extra: String.format("%.2f") depende do locale. Numa JVM em português, o getPriceSync gera "Store 1:1230,00:NONE", e o Double.parseDouble("1230,00") do Quote estoura NumberFormatException. Fixe o locale: String.format(Locale.US, "%s:%.2f:%s", ...). No WSL o padrão costuma ser inglês e funciona; num Windows em português, não.
  • Extra: CompletableFuture.orTimeout(3, SECONDS) (Java 9) e completeOnTimeout(valor, 3, SECONDS) trazem o "sempre use timeout" da aula 239 para a corrente.

Paralelo com PHP

  • CompletableFuture ≈ Promise: as promises do Guzzle ($client->getAsync($url)) e o Http::pool() do Laravel são a mesma ideia. ->then(fn($r) => ...) ≈ thenApply/thenCompose (se o then devolve outra promise, ela é "achatada", como no thenCompose); ->wait() ≈ join(); ->otherwise(...) ≈ exceptionally.
  • allOf ≈ Utils::all($promises)->wait() / Http::pool(fn($pool) => [...]), que dispara todas as requisições juntas e espera todas. anyOf ≈ Utils::any($promises): fica com a primeira resposta.
  • O mesmo erro de "disparar e esperar um por um": um foreach ($lojas as $l) { $precos[] = Http::get($l)->json(); } leva a soma dos tempos (os 8 s da aula 240). O Http::pool dispara todas juntas e leva o tempo da mais lenta (os ~2 s).
  • JavaScript, se você usa no front: fetch().then().then(), Promise.all e Promise.any/race são exatamente thenApply/thenCompose, allOf e anyOf.

import java.util.*;
import java.util.concurrent.*;
import java.util.stream.Collectors;

public class CompletableFuturePraticaTest01 {
    static int preco(String loja) {                 // "servidor lento": 300 ms
        dorme(300);
        return loja.length() * 100;
    }
    static void dorme(int ms) {
        try { TimeUnit.MILLISECONDS.sleep(ms); } catch (InterruptedException e) { throw new RuntimeException(e); }
    }

    public static void main(String[] args) {
        List<String> lojas = List.of("A", "BB", "CCC", "DDDD");
        ExecutorService executor = Executors.newFixedThreadPool(4, r -> {   // 242 · ThreadFactory
            Thread t = new Thread(r, "loja-thread");
            t.setDaemon(true);
            return t;
        });

        // 240 · síncrono × assíncrono
        long inicio = System.currentTimeMillis();
        List<Integer> sync = lojas.stream().map(CompletableFuturePraticaTest01::preco).collect(Collectors.toList());
        long tempoSync = System.currentTimeMillis() - inicio;

        inicio = System.currentTimeMillis();
        List<CompletableFuture<Integer>> cfs = lojas.stream()
                .map(l -> CompletableFuture.supplyAsync(() -> preco(l), executor))
                .collect(Collectors.toList());                                  // 241 · dispara todas
        List<Integer> async = cfs.stream().map(CompletableFuture::join).collect(Collectors.toList());
        long tempoAsync = System.currentTimeMillis() - inicio;
        System.out.println(sync + " " + async);                                             // ?
        System.out.println("assíncrono mais rápido? " + (tempoAsync < tempoSync));         // ?

        // 241 · o erro do stream único
        inicio = System.currentTimeMillis();
        lojas.stream()
                .map(l -> CompletableFuture.supplyAsync(() -> preco(l), executor))
                .map(CompletableFuture::join)
                .collect(Collectors.toList());
        System.out.println("stream único levou mais de 1 s? " + (System.currentTimeMillis() - inicio >= 1200)); // ?

        // 243–244 · thenApply + thenCompose

                    return String.format(Locale.US, "%s: %.2f -> %.2f", p[0], preco, finalPrice);
                }))
                .join();
        System.out.println(resultado);                                                    // ?

        // extra · erros
        int comFallback = CompletableFuture.supplyAsync(() -> {
                    if (true) throw new IllegalStateException("loja fora do ar");
                    return 1;
                })
                .exceptionally(e -> -1)
                .join();
        System.out.println("com exceptionally: " + comFallback);                          // ?
        try {
            CompletableFuture.supplyAsync(() -> { throw new IllegalStateException("loja fora do ar"); }).join();
        } catch (CompletionException e) {
            System.out.println(e.getClass().getSimpleName() + " / " + e.getCause().getMessage()); // ?
        }

        // 245 · allOf e anyOf
        CompletableFuture<String> lenta = CompletableFuture.supplyAsync(() -> { dorme(400); return "lenta"; }, executor);
        CompletableFuture<String> rapida = CompletableFuture.supplyAsync(() -> { dorme(50); return "rápida"; }, executor);
        CompletableFuture<String> media = CompletableFuture.supplyAsync(() -> { dorme(200); return "média"; }, executor);
        System.out.println("anyOf: " + CompletableFuture.anyOf(lenta, rapida, media).join());   // ?
        CompletableFuture.allOf(lenta, rapida, media).join();
        System.out.println("allOf: todas prontas? " + (lenta.isDone() && rapida.isDone() && media.isDone())); // ?

        // completar manualmente
        CompletableFuture<String> manual = new CompletableFuture<>();
        manual.complete("valor definido na mão");
        System.out.println(manual.join());                                                // ?

        executor.shutdown();
    }
}

Glossário

  • CompletableFuture<T>: Future que pode ser completado manualmente e encadeado com outras etapas.
  • supplyAsync: executa um Supplier em outra thread e devolve um CompletableFuture com o resultado.
  • runAsync (extra): o mesmo para um Runnable (sem resultado).
  • ForkJoinPool.commonPool(): pool padrão, compartilhado, com threads daemon.
  • join: espera e devolve o resultado; em erro, CompletionException (unchecked).
  • ThreadFactory: interface que cria as threads de um executor (nome, daemon, prioridade).
  • thenApply: transforma o resultado quando ele chegar (map).
  • thenCompose: encadeia outra operação assíncrona e achata o resultado (flatMap).
  • thenAccept: consome o resultado sem devolver nada.
  • allOf / anyOf: completa quando todos / o primeiro completarem.
  • exceptionally / handle (extra): tratam falhas dentro da corrente.
  • Método de fábrica estático: método static que cria objetos no lugar do construtor (Quote.newQuote).
