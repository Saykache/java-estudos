Resumo

Padrões de projeto (design patterns) são soluções padronizadas para problemas que milhares de desenvolvedores encontram no dia a dia. Não são bibliotecas: são formas de escrever o código. O bloco mostra quatro: Builder (criar objetos com muitos atributos de forma legível), Factory (esconder de quem usa como o objeto é criado), Singleton (garantir um único objeto compartilhado) e DTO (um objeto só para transportar dados).

Person p = Person.PersonBuilder.builder().firstName("William").lastName("Suane").build(); // 246 · Builder
Currency c = CurrencyFactory.newCurrency(Country.BRAZIL);                                   // 247 · Factory
AircraftSingletonEager a = AircraftSingletonEager.getINSTANCE();                            // 248–249 · Singleton
AircraftSingletonEnum.INSTANCE.bookSeat("1A");                                              // 250 · Singleton com enum
ReportDto dto = ReportDto.ReportDtoBuilder.builder().aircraftName("777")...build();         // 251 · DTO

246 · Builder

O problema: um construtor com muitos argumentos. Em new Person("William", "Suane", "ViradoNoJiraya", "william.suane@devdojo.academy"), o IntelliJ até mostra o nome de cada parâmetro, mas nem toda IDE faz isso, e uma semana depois ninguém lembra se o segundo é o sobrenome ou o nome do meio. Com 15 ou 20 atributos, pior ainda. O Builder organiza a criação para qualquer um conseguir ler.

public class Person {
    private String firstName;
    private String lastName;
    private String username;
    private String email;

    private Person(String firstName, String lastName, String username, String email) { // privado: força o builder
        this.firstName = firstName;
        this.lastName = lastName;
        this.username = username;
        this.email = email;
    }

    public static final class PersonBuilder {          // classe aninhada estática (aula 192)
        private String firstName;
        private String lastName;
        private String username;
        private String email;

        private PersonBuilder() { }
        public static PersonBuilder builder() { return new PersonBuilder(); }   // (aula 247)

        public PersonBuilder firstName(String firstName) {
            this.firstName = firstName;
            return this;                                // devolve o próprio builder
        }
        public PersonBuilder lastName(String lastName) { this.lastName = lastName; return this; }
        public PersonBuilder username(String username) { this.username = username; return this; }
        public PersonBuilder email(String email) { this.email = email; return this; }

        public Person build() {
            return new Person(firstName, lastName, username, email);
        }
    }
}

Person build = Person.PersonBuilder
        .builder()
        .firstName("William")
        .lastName("Suane")
        .username("ViradoNoJiraya")
        .email("william.suane@devdojo.academy")
        .build();
  • O construtor da Person fica privado, para obrigar o uso do builder. A classe aninhada acessa esse construtor privado.
  • O segredo está nos "setters" do builder: em vez de void, cada um devolve this, o próprio builder. Todas as chamadas trabalham no mesmo objeto na memória, e dá para encadear (fluent interface).
  • build() no fim cria o objeto de verdade. Dá para chamá-lo a qualquer momento, pulando os atributos que você não quer preencher (eles ficam null).
  • Não precisa escrever tudo isso na mão: o plugin Builder Generator do IntelliJ (Marketplace) gera o builder interno (opção inner builder, e dá para escolher prefixos como withFirstName).
  • Na aula 247, o construtor do PersonBuilder também ficou privado, e a criação passou pelo método estático builder(), que é uma pequena factory.

247 · Factory

O Factory desacopla a lógica de negócio da criação do objeto. Quem chama só pede "uma moeda para o Brasil" e não sabe (nem precisa saber) qual classe foi instanciada nem como.

public enum Country { BRAZIL, USA }

public interface Currency {
    String getSymbol();
}
class Real implements Currency {                 // sem public: só visível no pacote
    @Override public String getSymbol() { return "R$"; }
}
class UsDollar implements Currency {
    @Override public String getSymbol() { return "$"; }
}

public class CurrencyFactory {
    public static Currency newCurrency(Country country) {
        switch (country) {
            case USA:
                return new UsDollar();
            case BRAZIL:
                return new Real();
            default: throw new IllegalArgumentException("No currency found for this country");
        }
    }
}

Currency currency = CurrencyFactory.newCurrency(Country.BRAZIL);
System.out.println(currency.getSymbol());   // R$
  • Quem usa conhece só a interface Currency (polimorfismo, aula 90). Real e UsDollar nem são públicas.
  • Vantagem: se a regra de criação mudar (outra classe, validação, cache), você mexe só na fábrica, e quem chama continua igual. Com construtor espalhado pelo código, seria preciso alterar (ou sobrecarregar) em todo lugar. Resultado: baixo acoplamento e manutenção mais fácil.
  • A fábrica também pode impor regras: um builder(String firstName) que obrigue passar pelo menos o primeiro nome, por exemplo.
  • Extra: o que a aula mostra é a simple/static factory. O "Factory Method" do livro GoF é uma variação com herança (subclasses decidem o que criar). E o Quote.newQuote da aula 243 é o mesmo recurso: um método estático que cria o objeto.

248 · Singleton pt 01: eager initialization

Às vezes uma classe só pode ter um objeto, compartilhado por qualquer parte do código ou thread. Um exemplo clássico é o driver de conexão com o banco. O exemplo da aula é um avião: só existe um 787-900, e os assentos dele não podem ser vendidos duas vezes.

public final class Aircraft {
    private final Set<String> availableSeats = new HashSet<>();
    private final String name;
    public Aircraft(String name) { this.name = name; }
    {                                            // bloco de inicialização (aula 60)
        availableSeats.add("1A");
        availableSeats.add("1B");
    }
    public boolean bookSeat(String seat) {
        return availableSeats.remove(seat);      // true se estava livre
    }
}
// cada chamada faz new Aircraft("787-900") e bookSeat("1A") → true, true: o assento foi vendido duas vezes!

public final class AircraftSingletonEager {
    //Eager initialization
    private static final AircraftSingletonEager INSTANCE = new AircraftSingletonEager("787-900");
    private final Set<String> availableSeats = new HashSet<>();
    private final String name;

    private AircraftSingletonEager(String name) { this.name = name; }   // ninguém de fora dá new
    { availableSeats.add("1A"); availableSeats.add("1B"); }

    public static AircraftSingletonEager getINSTANCE() { return INSTANCE; }
    public boolean bookSeat(String seat) { return availableSeats.remove(seat); }
}

bookSeat("1A");   // true
bookSeat("1A");   // false: é o MESMO avião, o assento já foi vendido
AircraftTest01.bookSeat("1A");   // outra classe, mesmo endereço de memória impresso
  • Os três ingredientes: construtor privado (ninguém cria outro), atributo private static final com a única instância, e método estático que a devolve.
  • Eager ("guloso"): a instância é criada quando a classe é carregada, antes mesmo de alguém pedir. É simples e thread safe por natureza, porque a JVM garante que a inicialização estática acontece uma vez só.
  • O teste imprime o objeto em várias classes diferentes, e aparece sempre o mesmo endereço (AircraftSingletonEager@...).

249 · Singleton pt 02: lazy initialization

public final class AircraftSingletonLazy {
    private static AircraftSingletonLazy INSTANCE;        // não é mais final: começa null
    ...
    public static AircraftSingletonLazy getINSTANCE() {
        if (INSTANCE == null) {                            // 1ª checagem, sem lock (rápida)
            synchronized (AircraftSingletonLazy.class) {
                if (INSTANCE == null) {                    // 2ª checagem, com lock
                    INSTANCE = new AircraftSingletonLazy("787-900");
                }
            }
        }
        return INSTANCE;
    }
}
  • Lazy ("preguiçoso"): só cria a instância na primeira vez que alguém pede.
  • Com um if (INSTANCE == null) simples, duas threads podem ver null ao mesmo tempo e criar dois aviões (a condição de corrida da aula 224), e aí dois usuários compram o mesmo assento.
  • Colocar synchronized no método resolve, mas custa desempenho em toda chamada, para sempre, embora o problema só exista na primeira.
  • Double-checked locking: checa sem lock (o caso comum, instância já criada, fica rápido); se for null, sincroniza na classe e checa de novo, porque outra thread pode ter criado enquanto esta esperava o lock.
  • Reflection quebra o singleton: AircraftSingletonLazy.class.getDeclaredConstructor(String.class), setAccessible(true) e newInstance("787-900") criam um segundo objeto mesmo com o construtor privado. Reflection lê os metadados da classe em tempo de execução, é muito usada por frameworks e deixa o programa mais lento. "Se você vê alguém fazendo isso no código, levanta e dá um tapa na cabeça", e uma revisão de código (code review) deveria pegar.

250 · Singleton pt 03: com enum

public enum AircraftSingletonEnum {
    INSTANCE;
    private final Set<String> availableSeats;

    AircraftSingletonEnum() {                   // construtor de enum é sempre privado
        this.availableSeats = new HashSet<>();
        this.availableSeats.add("1A");
        this.availableSeats.add("1B");
    }

    public boolean bookSeat(String seat) {
        return availableSeats.remove(seat);
    }
}

AircraftSingletonEnum.INSTANCE.bookSeat("1A");   // true
AircraftSingletonEnum.INSTANCE.bookSeat("1A");   // false · o hashCode impresso é sempre o mesmo
  • Constantes de enum já são instâncias únicas criadas uma vez pela JVM (aula 80), então o singleton sai "de graça": código bem mais limpo, criação thread safe por padrão e reflection não consegue chamar o construtor de um enum (IllegalArgumentException: Cannot reflectively create enum objects).
  • Atenção, que o professor repete: "thread safe" aqui é só a criação do objeto. O bookSeat continua mexendo num HashSet comum, e duas threads podem remover o mesmo assento ao mesmo tempo. Em ambiente com várias threads, ele também precisa ser synchronized (ou usar uma coleção concorrente).
  • Extra: o enum também resiste à serialização (aula 159). Desserializar um singleton comum cria outro objeto; um enum, não. Por isso o livro Effective Java chama o enum de "a melhor forma de implementar um singleton".

251 · Data Transfer Object (DTO)

Um padrão "arquitetural de aplicações corporativas" (do catálogo Patterns of Enterprise Application Architecture, de Martin Fowler). O problema: uma API precisa receber o nome do avião, o país, a moeda e o nome da pessoa, dados que vêm de quatro entidades diferentes. Mandar os quatro objetos inteiros é mandar dados demais. O DTO é uma classe com só os atributos necessários, montada para a transferência.

public class ReportDto {                       // "Dto", não "DTO": siglas são tratadas como palavras
    private String aircraftName;
    private Country country;
    private Currency currency;
    private String personName;

    public static final class ReportDtoBuilder {
        ...                                     // gerado pelo plugin de builder
        public ReportDto build() {
            ReportDto reportDto = new ReportDto();
            reportDto.currency = this.currency;
            reportDto.aircraftName = this.aircraftName;
            reportDto.personName = this.personName;
            reportDto.country = this.country;
            return reportDto;
        }
    }
}

Aircraft aircraft = new Aircraft("777");
Country country = Country.BRAZIL;
Currency currency = CurrencyFactory.newCurrency(country);     // Factory
Person person = Person.PersonBuilder.builder()                 // Builder
        .firstName("William").lastName("Suane").build();
ReportDto reportDto = ReportDto.ReportDtoBuilder.builder()     // DTO com Builder
        .aircraftName(aircraft.getName())
        .country(country)
        .currency(currency)
        .personName(person.getFirstName())
        .build();
System.out.println(reportDto);
// ReportDto{aircraftName='777', country=BRAZIL, currency=...Real@1b6d3586, personName='William'}
  • Na vida real, esses dados vêm do banco (ou de outros serviços), e o DTO leva ao front-end, a outro serviço ou a uma API exatamente o que eles esperam: um objeto só, em vez de quatro.
  • O exemplo junta os padrões do bloco: Factory para a moeda, Builder para a pessoa e para o DTO.
  • O professor diz que o próprio Java é inconsistente na grafia (URL, HttpURLConnection), mas o recomendado é ReportDto.
  • Com isso termina o bloco de padrões. O próximo tema é banco de dados, com JDBC.

Atenção

  • Builder: o construtor da classe real deve ser privado, senão o builder vira opcional e o problema volta.
  • Singleton = construtor privado + instância estática + método estático de acesso. Esquecer o construtor privado deixa qualquer um dar new.
  • Correção: no double-checked locking, INSTANCE precisa ser volatile (private static volatile AircraftSingletonLazy INSTANCE;). Sem isso, pela forma como a JVM pode reordenar instruções, outra thread pode enxergar a referência antes de o objeto estar totalmente construído (com o Set ainda vazio, por exemplo). É por isso que o professor fala em possibilidade "bem reduzida" e não "zero": com volatile, é zero.
  • Extra: alternativa lazy sem lock: o holder idiom, uma classe aninhada estática private static class Holder { static final X INSTANCE = new X(); } e getInstance() devolvendo Holder.INSTANCE. A JVM só carrega o Holder na primeira chamada, e o carregamento de classe já é thread safe.
  • Reflection quebra singleton de classe; enum não.
  • Singleton thread safe ≠ métodos thread safe: o bookSeat ainda precisa de sincronização.
  • Extra: o currency do DTO sai como Real@1b6d3586 porque Real não sobrescreve toString (aula 76). Num DTO que vai para fora, prefira tipos simples: currencySymbol = currency.getSymbol().
  • Extra: o ReportDto não declara construtor, então ganha o construtor padrão público, e dá para criar um vazio sem o builder. Declare private ReportDto() {} se quiser forçar o builder.
  • Extra: singleton é considerado "antipadrão" por muitos quando vira estado global: dificulta testes (não dá para trocar a instância) e esconde dependências. Frameworks como o Spring resolvem isso com injeção de dependência, e o objeto continua único, mas é entregue pelo container.

Paralelo com PHP

  • Builder no Laravel está em todo lugar: o Query Builder (DB::table('users')->where(...)->orderBy(...)->get()), o Http::withToken(...)->timeout(3)->get(...), os Mailable e as Model Factories dos testes (User::factory()->count(3)->create()). Cada método devolve $this (ou uma cópia) e o último executa (o build()). No PHP 8 os named arguments (new Person(firstName: 'William', lastName: 'Suane')) resolvem parte do problema da legibilidade que motivou o Builder.
  • Factory: os Manager/driver() do Laravel são fábricas: Cache::store('redis'), Storage::disk('s3'), Mail::mailer('ses'). Você pede pelo nome e recebe uma implementação da interface (Illuminate\Contracts\Cache\Repository) sem saber a classe concreta. Métodos estáticos como Carbon::createFromFormat() também.
  • Singleton: no PHP o "para sempre" dura uma requisição (cada request começa do zero, salvo Octane). O padrão clássico existe (private function __construct() + private static ?self $instance + public static function getInstance()), mas no Laravel o jeito é o container: $this->app->singleton(PaymentGateway::class, fn() => new StripeGateway(...)). Várias Facades apontam para singletons do container. E não há o problema das threads.
  • DTO: no PHP 8+ é comum com constructor promotion e readonly (final class ReportDto { public function __construct(public readonly string $aircraftName, public readonly string $personName) {} }), ou com o pacote spatie/laravel-data. Os API Resources (JsonResource) fazem um papel parecido: escolhem só os campos que vão para o front.

package academy.devdojo.maratonajava.javacore.ZZHpadroesdeprojeto.test;

import java.lang.reflect.Constructor;
import java.util.HashSet;
import java.util.Set;

public class PadroesPraticaTest01 {
    // 246 · Builder
    static class Person {
        private final String firstName, lastName, username;
        private Person(String firstName, String lastName, String username) {
            this.firstName = firstName; this.lastName = lastName; this.username = username;
        }
        @Override public String toString() { return firstName + " " + lastName + " (" + username + ")"; }

        static final class PersonBuilder {
            private String firstName, lastName, username;
            private PersonBuilder() { }
            static PersonBuilder builder() { return new PersonBuilder(); }
            PersonBuilder firstName(String v) { this.firstName = v; return this; }
            PersonBuilder lastName(String v) { this.lastName = v; return this; }
            PersonBuilder username(String v) { this.username = v; return this; }
            Person build() { return new Person(firstName, lastName, username); }
        }
    }

    // 247 · Factory
    enum Country { BRAZIL, USA }
    interface Currency { String getSymbol(); }
    static Currency newCurrency(Country country) {
        switch (country) {
            case BRAZIL: return () -> "R$";          // Currency é interface funcional
            case USA: return () -> "$";
            default: throw new IllegalArgumentException("No currency found for this country");
        }
    }

    // 248 · sem singleton
    static class Aircraft {
        private final Set<String> seats = new HashSet<>(Set.of("1A", "1B"));
        boolean bookSeat(String seat) { return seats.remove(seat); }
    }

    // 248 · eager
    static final class Eager {
        private static final Eager INSTANCE = new Eager();
        private final Set<String> seats = new HashSet<>(Set.of("1A", "1B"));
        private Eager() { }
        static Eager getInstance() { return INSTANCE; }
        boolean bookSeat(String seat) { return seats.remove(seat); }
    }

    // 249 · lazy com double-checked locking (e volatile)
    static final class Lazy {
        private static volatile Lazy instance;
        private Lazy() { }
        static Lazy getInstance() {
            if (instance == null) {
                synchronized (Lazy.class) {
                    if (instance == null) instance = new Lazy();
                }
            }
            return instance;
        }
    }

    // 250 · enum
    enum AircraftEnum {
        INSTANCE;
        private final Set<String> seats = new HashSet<>(Set.of("1A", "1B"));
        synchronized boolean bookSeat(String seat) { return seats.remove(seat); }
    }

    // 251 · DTO
    static final class ReportDto {
        private String aircraftName, country, currencySymbol, personName;
        private ReportDto() { }
        @Override public String toString() {
            return "ReportDto{aircraftName='" + aircraftName + "', country=" + country
                    + ", currency=" + currencySymbol + ", personName='" + personName + "'}";
        }
    }

    public static void main(String[] args) throws Exception {
        Person person = Person.PersonBuilder.builder()
                .firstName("William").lastName("Suane").username("ViradoNoJiraya").build();
        System.out.println(person);                                                  // ?

        System.out.println(newCurrency(Country.BRAZIL).getSymbol() + " " + newCurrency(Country.USA).getSymbol()); // ?

        System.out.println(new Aircraft().bookSeat("1A") + " " + new Aircraft().bookSeat("1A"));   // ?
        System.out.println(Eager.getInstance().bookSeat("1A") + " " + Eager.getInstance().bookSeat("1A")); // ?
        System.out.println("mesmo objeto? " + (Eager.getInstance() == Eager.getInstance()));       // ?

        System.out.println("lazy mesmo objeto? " + (Lazy.getInstance() == Lazy.getInstance()));    // ?
        Constructor<Lazy> constructor = Lazy.class.getDeclaredConstructor();
        constructor.setAccessible(true);
        System.out.println("reflection criou outro? " + (constructor.newInstance() != Lazy.getInstance())); // ?

        System.out.println(AircraftEnum.INSTANCE.bookSeat("1A") + " " + AircraftEnum.INSTANCE.bookSeat("1A")); // ?
        try {
            Constructor<?> enumConstructor = AircraftEnum.class.getDeclaredConstructors()[0];
            enumConstructor.setAccessible(true);
            enumConstructor.newInstance("OUTRO", 1);
        } catch (IllegalArgumentException e) {
            System.out.println("enum: " + e.getMessage());                           // ?
        }

        ReportDto dto = new ReportDto();
        dto.aircraftName = "777";
        dto.country = Country.BRAZIL.name();
        dto.currencySymbol = newCurrency(Country.BRAZIL).getSymbol();
        dto.personName = person.firstName;
        System.out.println(dto);                                                     // ?
    }
}

Glossário

  • Padrão de projeto (design pattern): solução reutilizável e padronizada para um problema recorrente de design de código.
  • Builder: objeto auxiliar que monta outro passo a passo, com métodos encadeados e um build() final.
  • Fluent interface: métodos que devolvem this para permitir encadeamento.
  • Factory: método/classe responsável por criar objetos, escondendo a classe concreta.
  • Acoplamento: grau de dependência entre partes do código; baixo acoplamento facilita mudanças.
  • Singleton: classe com uma única instância, acessível globalmente.
  • Eager × lazy initialization: criar na carga da classe × criar no primeiro uso.
  • Double-checked locking: checar sem lock, travar e checar de novo antes de criar.
  • volatile: garante que todas as threads vejam a escrita mais recente de uma variável, sem reordenação perigosa.
  • Reflection: API para inspecionar e manipular classes, métodos e construtores em tempo de execução.
  • DTO (Data Transfer Object): objeto só com os dados necessários para transferir entre camadas ou sistemas.
  • Code review: revisão do código por outro desenvolvedor antes de ir para produção.
