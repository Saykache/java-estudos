Resumo

268 · PreparedStatement pt 01: SQL injection

O professor mostra o ataque primeiro. Com o findByName montado com formatted (sem LIKE, com name = '%s'), ele passa algo como x' OR 'x'='x. O SQL vira ... WHERE name = 'x' OR 'x'='x', e a consulta devolve a tabela inteira. "É uma coisa simples, mas o Yahoo pagou um preço alto por uma besteira dessa."

public static List<Producer> findByNamePreparedStatement(String name) {
    List<Producer> producers = new ArrayList<>();
    try (Connection conn = ConnectionFactory.getConnection();
         PreparedStatement ps = preparedStatementFindByName(conn, name);   // criado fora
         ResultSet rs = ps.executeQuery()) {                                // sem SQL aqui!
        while (rs.next()) {
            producers.add(Producer.builder().id(rs.getInt("id")).name(rs.getString("name")).build());
        }
    } catch (SQLException e) {
        log.error("Error while trying to find all producers", e);
    }
    return producers;
}

private static PreparedStatement preparedStatementFindByName(Connection conn, String name) throws SQLException {
    String sql = "SELECT * FROM anime_store.producer where name like ?;";   // ? = placeholder
    PreparedStatement ps = conn.prepareStatement(sql);
    ps.setString(1, String.format("%%%s%%", name));                        // índice começa em 1
    return ps;
}
  • Duas vantagens, segundo o professor: desempenho, porque o SQL é pré-compilado (o banco valida tabela, colunas e sintaxe uma vez e reaproveita), e proteção contra SQL injection, porque o valor é tratado como dado, nunca como parte do comando. O mesmo ataque não devolve nada.
  • ? marca onde entra cada valor, e os setString(índice, valor), setInt... preenchem, com índice a partir de 1. No LIKE, o % vai no valor, não no SQL: "%" + name + "%".
  • O SQL vai no conn.prepareStatement(sql). Depois é ps.executeQuery() / ps.executeUpdate() sem argumento. (O professor estranhou que o executeQuery(sql) herdado do Statement ainda compila; extra: no PreparedStatement ele lança exceção se chamado.)
  • Problema de estrutura: os setXxx precisam rodar entre criar o PreparedStatement e executar a consulta, e dentro dos parênteses do try-with-resources não cabem instruções. A solução é extrair um método que cria e preenche o PreparedStatement e devolvê-lo ao try, que continua fechando tudo.

269 · PreparedStatement pt 02: UPDATE

public static void updatePreparedStatement(Producer producer) {
    try (Connection conn = ConnectionFactory.getConnection();
         PreparedStatement ps = preparedStatementUpdate(conn, producer)) {
        int rowsAffected = ps.executeUpdate();
        log.info("Updated producer '{}', rows affected '{}' ", producer.getId(), rowsAffected);
    } catch (SQLException e) {
        log.error("Error while trying to update producer '{}'", producer.getId(), e);
    }
}

private static PreparedStatement preparedStatementUpdate(Connection conn, Producer producer) throws SQLException {
    String sql = "UPDATE `anime_store`.`producer` SET `name` = ? WHERE (`id` = ?);";
    PreparedStatement ps = conn.prepareStatement(sql);
    ps.setString(1, producer.getName());    // 1º ?
    ps.setInt(2, producer.getId());         // 2º ?
    return ps;
}
  • Cada ? tem seu índice, na ordem em que aparece. '%s' com aspas vira só ?, sem aspas: o driver cuida disso. Isso resolve de quebra o espaço extra do UPDATE da aula 260 e o nome com apóstrofo.
  • O professor também descobre que o %%%s%% com String.format funcionava (no vídeo anterior ele tinha errado outra coisa).

270 · CallableStatement e stored procedure

Um CallableStatement é um PreparedStatement especializado em executar procedures e functions guardadas no banco. A diferença entre as duas: a function obrigatoriamente retorna um valor; a procedure pode ou não retornar. O professor conta que por volta de 2006 a 2008 se usava muito, mas hoje ele quase não vê: a lógica dentro do banco fica difícil de manter. Um uso da época era limitar o acesso: as pessoas só podiam consultar certas colunas através da procedure.

DELIMITER $$
CREATE PROCEDURE `anime_store`.`sp_get_producer_by_name`(IN p_name VARCHAR(100))
BEGIN
    SELECT * FROM anime_store.producer WHERE name LIKE p_name;
END$$
DELIMITER ;

CALL anime_store.sp_get_producer_by_name('%NHK%');
private static CallableStatement callableStatementFindByName(Connection conn, String name) throws SQLException {
    String sql = "CALL `anime_store`.`sp_get_producer_by_name`(?);";
    CallableStatement cs = conn.prepareCall(sql);            // prepareCall, não prepareStatement
    cs.setString(1, String.format("%%%s%%", name));
    return cs;
}
// o resto é igual ao findByNamePreparedStatement: executeQuery e while (rs.next())
  • DELIMITER $$: o corpo da procedure tem ; no meio, e sem trocar o delimitador o cliente cortaria o comando ali. No fim, volta-se para ;.
  • Pegadinha do vídeo: com o parâmetro chamado name, igual à coluna, o WHERE name LIKE name compara a coluna com ela mesma e devolve todo mundo. Dê outro nome ao parâmetro (p_name).
  • No Workbench, a procedure aparece em Stored Procedures do schema e pode ser chamada com CALL.
  • Extra: parâmetros de saída (OUT) são lidos com cs.registerOutParameter(2, Types.INTEGER) antes de executar e cs.getInt(2) depois.

271 · JdbcRowSet pt 01: RowSet conectado

O RowSet é "uma versão tunada do ResultSet":

  • O ResultSet sempre mantém a conexão; um RowSet pode ficar conectado (JdbcRowSet) ou desconectado (CachedRowSet).
  • O ResultSet não é serializável; o RowSet é, e dá para mandá-lo pela rede.
  • O RowSet é um JavaBean (propriedades com setters) e é, por padrão, rolável e atualizável.
  • Ele é criado por uma fábrica: RowSetProvider.newFactory().
public static JdbcRowSet getJdbcRowSet() throws SQLException {           // na ConnectionFactory
    JdbcRowSet jdbcRowSet = RowSetProvider.newFactory().createJdbcRowSet();
    jdbcRowSet.setUrl("jdbc:mysql://localhost:3306/anime_store");         // atenção: setUrl, u minúsculo
    jdbcRowSet.setUsername("root");
    jdbcRowSet.setPassword("root");
    return jdbcRowSet;
}

public static List<Producer> findByNameJdbcRowSet(String name) {
    String sql = "SELECT * FROM anime_store.producer where name like ?;";
    List<Producer> producers = new ArrayList<>();
    try (JdbcRowSet jrs = ConnectionFactory.getJdbcRowSet()) {
        jrs.setCommand(sql);                                   // o SQL
        jrs.setString(1, String.format("%%%s%%", name));       // parâmetros, como no PreparedStatement
        jrs.execute();                                         // abre a conexão e executa
        while (jrs.next()) {                                   // e ele mesmo é o "ResultSet"
            producers.add(Producer.builder().id(jrs.getInt("id")).name(jrs.getString("name")).build());
        }
    } catch (SQLException e) {
        e.printStackTrace();
    }
    return producers;
}
  • Uma classe só faz o papel de Connection + PreparedStatement + ResultSet: simplifica bastante, e o try-with-resources fica com um recurso só.
  • O execute() do RowSet é para buscar dados. Para gravar, veja a aula 272.
  • O código ganhou classes separadas (ProducerRepositoryRowSet, ProducerServiceRowSet) porque o repositório "já estava muito grande".

272 · JdbcRowSet pt 02: update e listener

// NÃO funciona: execute() de um RowSet espera um SELECT
// jrs.setCommand("UPDATE ... SET name = ? WHERE id = ?"); jrs.execute();   → exceção

public static void updateJdbcRowSet(Producer producer) {
    String sql = "SELECT * FROM anime_store.producer WHERE (`id` = ?);";   // busca a linha...
    try (JdbcRowSet jrs = ConnectionFactory.getJdbcRowSet()) {
        jrs.addRowSetListener(new CustomRowSetListener());
        jrs.setCommand(sql);
        jrs.setInt(1, producer.getId());
        jrs.execute();
        if (!jrs.next()) return;
        jrs.updateString("name", producer.getName());                    // ...e altera por ela
        jrs.updateRow();
    } catch (SQLException e) {
        e.printStackTrace();
    }
}

@Log4j2
public class CustomRowSetListener implements RowSetListener {
    @Override
    public void rowSetChanged(RowSetEvent event) { log.info("Command execute triggered"); }  // execute()

    @Override
    public void rowChanged(RowSetEvent event) {                         // insert/update/delete
        log.info("Row inserted, updated or deleted");
        if (event.getSource() instanceof RowSet) {
            try {
                ((RowSet) event.getSource()).execute();                 // recarrega os dados
            } catch (SQLException e) {
                e.printStackTrace();
            }
        }
    }

    @Override
    public void cursorMoved(RowSetEvent event) { log.info("Cursor moved"); }   // next(), previous()...
}
  • Para alterar, o jeito é o mesmo do ResultSet atualizável (aula 266): um SELECT que traz a linha, updateString e updateRow.
  • Listener: uma classe que "fica escutando" o RowSet. Três métodos são chamados sozinhos, graças ao polimorfismo: rowSetChanged quando o comando é executado, cursorMoved a cada movimento do cursor e rowChanged quando uma linha é inserida, atualizada ou apagada. No exemplo, o rowChanged chama execute() de novo para recarregar o RowSet, algo que o ResultSet não faz sozinho.
  • O professor mostra o @SneakyThrows do Lombok, que "esconde" a exceção checked (o código compilado ganha um try/catch). "Para estudo tudo bem, mas em produção, pelo amor de Deus": você perde o tratamento da exceção.

273 · CachedRowSet: RowSet desconectado

O CachedRowSet pega os dados e desconecta: tudo fica na memória, você trabalha nela e, no fim, manda as alterações de volta.

public static CachedRowSet getCachedRowSet() throws SQLException {        // na ConnectionFactory
    return RowSetProvider.newFactory().createCachedRowSet();
}

public static void updateCachedRowSet(Producer producer) {
    String sql = "SELECT * FROM producer WHERE (`id` = ?);";               // sem "anime_store."!
    try (CachedRowSet crs = ConnectionFactory.getCachedRowSet();
         Connection connection = ConnectionFactory.getConnection()) {
        connection.setAutoCommit(false);                                   // obrigatório aqui
        crs.setCommand(sql);
        crs.setInt(1, producer.getId());
        crs.execute(connection);                                           // usa esta conexão
        if (!crs.next()) return;
        crs.updateString("name", producer.getName());
        crs.updateRow();                                                   // só na memória!
        TimeUnit.SECONDS.sleep(10);                                        // teste de conflito
        crs.acceptChanges();                                               // agora grava no banco
    } catch (SQLException | InterruptedException e) {
        e.printStackTrace();
    }
}
  • updateRow() não basta: altera só a cópia em memória. É o acceptChanges() que manda para o banco.
  • A saga da depuração (o professor passou "uma hora e meia" nisso e mostra o caminho):
    • Primeiro erro, sintaxe SQL: seguindo a pilha com breakpoints e F8 até dentro da implementação (CachedRowSetWriter), ele achou o UPDATE gerado com o nome da tabela errado por causa do anime_store. no SELECT. A solução foi escrever só FROM producer (o banco já está na URL).
    • Segundo erro, auto-commit: o acceptChanges faz o próprio commit e não funciona com a conexão em auto-commit. A solução foi passar uma Connection com setAutoCommit(false) para crs.execute(connection).
    A lição dele: "é o tipo de coisa que vai acontecer na vida profissional", e o Google nem sempre tem a resposta. Aprenda a depurar dentro das bibliotecas.
  • Conflito: com o sleep de 10 s, ele alterou o mesmo registro no Workbench antes do acceptChanges. Resultado: SyncProviderException, porque os dados originais mudaram no banco enquanto o CachedRowSet estava desconectado. Resolver conflitos é possível, mas "não é o foco do curso, graças a Deus".
  • Vantagem: pode ser muito mais rápido trabalhar na memória do que ir ao banco a cada operação. O preço são essas "treta" de sincronização.

274 · Transação

Transação é atomicidade no banco: ou executa tudo, ou não executa nada. Exemplo: numa compra, o pagamento é registrado e o monitor sai do estoque. Se um dos passos falhar, os outros precisam voltar ao estado original.

public static void saveTransaction(List<Producer> producers) {
    try (Connection conn = ConnectionFactory.getConnection()) {
        conn.setAutoCommit(false);                        // "eu decido quando gravar"
        preparedStatementSaveTransaction(conn, producers);
        conn.commit();                                    // grava tudo de uma vez
        conn.setAutoCommit(true);
    } catch (SQLException e) {
        log.error("Error while trying to save producers '{}'", producers, e);
    }
}

private static void preparedStatementSaveTransaction(Connection conn, List<Producer> producers) throws SQLException {
    String sql = "INSERT INTO `anime_store`.`producer` (`name`) VALUES ( ? );";
    boolean shouldRollback = false;
    for (Producer p : producers) {
        try (PreparedStatement ps = conn.prepareStatement(sql)) {   // um PreparedStatement por item,
            log.info("Saving producer '{}'", p.getName());          // a MESMA conexão para todos
            ps.setString(1, p.getName());
//          if (p.getName().equals("White fox")) throw new SQLException("Can't save white fox");
            ps.execute();
        } catch (SQLException e) {
            e.printStackTrace();
            shouldRollback = true;
        }
    }
    if (shouldRollback) {
        log.warn("Transaction is going be rollback");
        conn.rollback();                                  // desfaz tudo desde o início
    }
}

ProducerService.saveTransaction(List.of(
        Producer.builder().name("Toei Animation").build(),
        Producer.builder().name("White fox").build(),
        Producer.builder().name("Studio Ghibli").build()));
  • Auto-commit: por padrão, o MySQL grava cada comando assim que ele executa. Com três inserts A, B e C, se o C falhar, A e B já estão salvos. conn.setAutoCommit(false) muda isso: nada fica permanente até o conn.commit().
  • O professor mostra os estados: sem o commit(), o log diz "salvo" mas o banco está vazio. Com o commit(), os três aparecem. Forçando erro no "White fox", ficam dois gravados, porque a exceção foi pega dentro do laço e o commit gravou o resto.
  • A correção é o rollback() depois do laço, controlado pela variável shouldRollback. Um rollback dentro do catch de cada item não resolveria, e no catch externo a conexão já estaria fechada pelo try-with-resources. Com o rollback, nenhum dos três é gravado.
  • A mesma conexão precisa ser usada em toda a transação (não abra uma por item). O professor comenta que, na vida real, conexões vêm de um pool, e frameworks como o Spring cuidam da transação automaticamente.
  • Lembre de voltar o auto-commit (setAutoCommit(true)) se a conexão for reaproveitada.

Atenção

  • Use PreparedStatement sempre que houver valor vindo de fora. Statement com concatenação é SQL injection esperando para acontecer.
  • O ? substitui valores, não nomes de tabela/coluna nem palavras-chave. ORDER BY ? não funciona como você espera (extra).
  • Índices dos parâmetros começam em 1 e seguem a ordem dos ?.
  • Parâmetro de procedure com o mesmo nome da coluna faz o WHERE comparar a coluna com ela mesma.
  • RowSet.execute() é para SELECT. Para alterar, busque e use updateXxx + updateRow (e, no CachedRowSet, acceptChanges).
  • @SneakyThrows não é para produção.
  • Transação: setAutoCommit(false), a mesma conexão, commit() no sucesso e rollback() na falha. Extra: a forma mais comum é try { ...; conn.commit(); } catch (SQLException e) { conn.rollback(); throw e; }, deixando a exceção interromper tudo; o laço do professor continua inserindo depois do erro e só no fim desfaz.
  • Extra: para muitos inserts, addBatch()/executeBatch() manda tudo numa ida ao banco, e combina bem com a transação.
  • Extra: tabelas precisam ser InnoDB (o padrão do MySQL 8) para ter transação; MyISAM ignora o rollback.

Paralelo com PHP

  • PreparedStatement ≈ $pdo->prepare(): $stmt = $pdo->prepare('SELECT * FROM producer WHERE name LIKE ?'); $stmt->execute(["%$nome%"]); (ou :nome com bindValue). É exatamente o mesmo mecanismo e a mesma proteção. O Eloquent e o Query Builder já usam bindings por baixo (where('name', 'like', "%$nome%")), e o perigo volta com DB::raw/whereRaw concatenando texto: use whereRaw('name like ?', ["%$nome%"]).
  • CallableStatement ≈ $pdo->prepare('CALL sp_get_producer_by_name(?)') ou DB::select('CALL sp_...(?)', [$nome]). No Laravel, a lógica geralmente fica no PHP (Eloquent, Services), e não em procedures, pelo mesmo motivo que o professor cita.
  • RowSet não tem equivalente direto. O mais parecido com o CachedRowSet é trabalhar com uma Collection de models na memória e depois salvar, e os "conflitos" são o problema de optimistic locking (comparar uma coluna updated_at/version antes de gravar). Os model events/observers do Eloquent (updated, created) lembram o RowSetListener.
  • Transação ≈ DB::transaction(function () { ... }): se qualquer exceção sair da closure, o Laravel faz rollback; se não, commit. É o padrão try/commit/catch/rollback da seção "Atenção", pronto. No PDO: $pdo->beginTransaction(), commit(), rollBack().

public class JdbcAvancadoPraticaTest01 {
    static final String URL = "jdbc:mysql://localhost:3306/anime_store";

    static List<Producer> read(ResultSet rs) throws SQLException {
        List<Producer> list = new ArrayList<>();

        }

        List<String> nomes = List.of("Toei Animation", "White fox", "Studio Ghibli");
        System.out.println("com falha: " + saveTransaction(nomes, "White fox") + " | total: " + findByName("").size()); // ?
        System.out.println("sem falha: " + saveTransaction(nomes, null) + " | total: " + findByName("").size());        // ?
        System.out.println("final: " + findByName(""));                                                            // ?
    }

    static String saveTransaction(List<String> nomes, String nomeQueFalha) throws SQLException {
        try (Connection conn = ConnectionFactory.getConnection()) {
            conn.setAutoCommit(false);
            try (PreparedStatement ps = conn.prepareStatement("INSERT INTO producer (name) VALUES (?)")) {
                for (String nome : nomes) {
                    if (nome.equals(nomeQueFalha)) throw new SQLException("Can't save " + nome);
                    ps.setString(1, nome);
                    ps.executeUpdate();
                }
                conn.commit();
                return "commit";
            } catch (SQLException e) {
                conn.rollback();
                return "rollback (" + e.getMessage() + ")";
            } finally {
                conn.setAutoCommit(true);
            }
        }
    }
}

Glossário

  • SQL injection: entrada do usuário que altera o SQL executado.
  • PreparedStatement: SQL pré-compilado com ?; valores passados à parte (setXxx).
  • Placeholder: o ? que marca onde entra um valor.
  • Stored procedure / function: rotina guardada no banco; a function sempre retorna um valor.
  • CallableStatement: executa procedures e functions (prepareCall).
  • DELIMITER: troca o terminador de comandos do cliente MySQL para escrever blocos com ;.
  • RowSet: ResultSet JavaBean, serializável, rolável e atualizável.
  • JdbcRowSet: RowSet conectado ao banco.
  • CachedRowSet: RowSet desconectado; trabalha na memória e sincroniza com acceptChanges.
  • RowSetListener: ouvinte de eventos de um RowSet.
  • @SneakyThrows: anotação do Lombok que esconde exceções checked.
  • Transação: conjunto de operações que é gravado inteiro ou desfeito inteiro.
  • Auto-commit: modo em que cada comando é gravado imediatamente.
  • Commit / rollback: confirmar / desfazer as operações da transação.
