Resumo

Serialização é transformar um objeto da memória num array de bytes para gravá-lo (num arquivo, por exemplo) e depois recriá-lo. Muitos frameworks fazem isso por baixo dos panos. Depois começam as Coleções: "praticamente tudo na sua vida de desenvolvedor retorna mais de um objeto". Antes das listas, é preciso ensinar ao Java quando dois objetos são logicamente iguais (equals) e dar a eles um número de endereçamento (hashCode). A aula 165 fecha com a teoria: ordenado × sorted e a complexidade Big-O.

159 · Serializable, ObjectOutputStream e ObjectInputStream

public class Aluno implements Serializable {       // interface de MARCAÇÃO: não tem métodos
    private Long id;
    private String nome;
    private String password;
    public Aluno(Long id, String nome, String password) {
        System.out.println("Dentro do construtor");
        ...
    }
}

private static void serializar(Aluno aluno) {
    Path path = Paths.get("pasta/aluno.ser");
    try (ObjectOutputStream oos = new ObjectOutputStream(Files.newOutputStream(path))) {
        oos.writeObject(aluno);                       // objeto → bytes no arquivo
    } catch (IOException e) {
        e.printStackTrace();
    }
}

private static void deserializar() {
    Path path = Paths.get("pasta/aluno.ser");
    try (ObjectInputStream ois = new ObjectInputStream(Files.newInputStream(path))) {
        Aluno aluno = (Aluno) ois.readObject();       // bytes → objeto (devolve Object: cast)
        System.out.println(aluno);
    } catch (IOException | ClassNotFoundException e) {
        e.printStackTrace();
    }
}
  • É trabalho de baixo nível (bytes), então usa as classes Stream: ObjectOutputStream para escrever (output) e ObjectInputStream para ler (input), encadeadas com o stream do arquivo (Files.newOutputStream/newInputStream).
  • Sem implements Serializable, o writeObject lança NotSerializableException. Serializable é uma interface de marcação: não tem métodos e só serve para o objeto passar no teste "é um".
  • O arquivo .ser aberto num editor parece "código de máquina": só a JVM entende.
  • readObject() devolve Object, então precisa de cast, e lança também ClassNotFoundException (a classe pode não existir no classpath). Daí o multi-catch.
  • Na desserialização, o construtor NÃO é executado. "Dentro do construtor" só aparece no new. O objeto é reconstruído a partir dos bytes. Isso complica com herança: a primeira superclasse não serializável tem o construtor executado (extra).

160 · transient, serialVersionUID, static e writeObject/readObject

public class Aluno implements Serializable {
    private static final long serialVersionUID = 739959230178355186L;   // a "versão" da classe
    private Long id;
    private String nome;
    private transient String password;                     // NÃO é serializado → volta null
    private static final String NOME_ESCOLA = "DevDojo Viradão no Jiraya";  // static: é da classe
    private transient Turma turma;                         // Turma NÃO é Serializable

    private void writeObject(ObjectOutputStream oos) {     // private, assinatura exata
        try {
            oos.defaultWriteObject();                      // 1º: o padrão (id, nome)
            oos.writeUTF(turma.getNome());                 // 2º: o que você quer a mais
        } catch (IOException e) { e.printStackTrace(); }
    }

    private void readObject(ObjectInputStream ois) {
        try {
            ois.defaultReadObject();                       // lê na MESMA ordem
            String nomeTurma = ois.readUTF();
            turma = new Turma(nomeTurma);                  // reconstrói o objeto
        } catch (IOException | ClassNotFoundException e) { e.printStackTrace(); }
    }
}
// Aluno{id=1, nome='Suane', password='null', NOME_ESCOLA='DevDojo Viradão no Jiraya',
//       Turma='Turma{nome='Maratona Java Virado no Jiraya em Breve Ricos'}'}
  • transient: o atributo é ignorado na serialização (senha, dados sensíveis). Ao ler, ele volta com o valor padrão (null, 0).
  • serialVersionUID: se você não declarar, o Java gera um (uma espécie de hash da classe). Qualquer mudança na classe (como pôr transient) muda esse número, e ler um arquivo antigo dá InvalidClassException (versão incompatível). Declarando um fixo, mudanças compatíveis continuam funcionando. A IDE gera o número.
  • Atributos static não são serializados: pertencem à classe, não ao objeto. O NOME_ESCOLA aparece porque vem da classe carregada, não do arquivo.
  • Associação com classe não serializável (Turma, que pode ser de uma biblioteca que você não pode alterar): marque como transient e escreva você mesmo nos métodos private void writeObject(ObjectOutputStream) e private void readObject(ObjectInputStream). O Java os chama automaticamente: é uma "sobrescrita sem ser sobrescrita", com assinatura exata e sem @Override.
  • A ordem importa: leia na mesma ordem em que escreveu (primeiro o default..., depois cada atributo extra).
  • O @Serial (Java 14) apareceu na aula 160 e foi removido na 161, porque o projeto usa language level 8. Ele só documenta esses membros especiais.

161 · equals: igualdade lógica

String nome = "William Suane";
String nome2 = "William Suane";
System.out.println(nome == nome2);            // true: mesmo objeto do pool (aula 108)
String nome3 = new String("William Suane");
System.out.println(nome == nome3);            // false: objetos diferentes
System.out.println(nome.equals(nome3));       // true: String sobrescreve equals e compara o conteúdo

Smartphone s1 = new Smartphone("1ABC1", "iPhone");
Smartphone s2 = new Smartphone("1ABC1", "iPhone");
System.out.println(s1.equals(s2));            // false! o equals herdado de Object é: this == obj
  • == compara referências: as duas variáveis apontam para o mesmo objeto?
  • Todo objeto herda equals de Object, que por padrão faz this == obj, ou seja, o mesmo que ==. A String sobrescreve e compara os caracteres. O Smartphone, sem sobrescrever, dá false mesmo com os mesmos dados.
  • Desenhando: duas variáveis (s1, s2) e dois objetos na memória. Com s2 = s1, as duas apontam para o mesmo, e aí dá true.
  • Para nós, dois smartphones são o mesmo se o número de série for igual. Essa regra de negócio você ensina sobrescrevendo equals.

162 · Sobrescrevendo equals (e o contrato)

// Reflexivo: x.equals(x) tem que ser true para tudo que for diferente de null
// Simétrico: para x e y diferentes de null, se x.equals(y) == true, então y.equals(x) == true
// Transitivo: se x.equals(y) e y.equals(z) são true, então x.equals(z) == true
// Consistente: x.equals(y) retorna sempre o mesmo resultado se nada mudou
// Para x diferente de null, x.equals(null) tem que retornar false
@Override
public boolean equals(Object obj) {
    if (obj == null) return false;                           // nada é igual a null
    if (this == obj) return true;                            // mesmo objeto: atalho
    if (this.getClass() != obj.getClass()) return false;     // classes diferentes: não compara
    Smartphone smartphone = (Smartphone) obj;                // aqui já é seguro
    return serialNumber != null && serialNumber.equals(smartphone.serialNumber);
}

Smartphone s1 = new Smartphone("1ABC1", "iPhone");
Smartphone s2 = new Smartphone("1ABC1", "Pixel");
System.out.println(s1.equals(s2));    // true: só o serialNumber decide
  • A assinatura é equals(Object obj). equals(Smartphone) seria sobrecarga (aulas 54–57), e as coleções continuariam chamando o de Object. O @Override pega esse erro.
  • O roteiro: null → mesma referência → mesma classe → cast → comparar os atributos que definem a identidade.
  • Quais atributos comparar é regra de negócio. Aqui é só serialNumber, então um iPhone e um Pixel com o mesmo serial são "iguais". Se a marca também importar, ela entra no equals.
  • serialNumber != null && evita NullPointerException. E o equals da String devolve false se o outro serial for null.

163 · O que é hash

Nome   letras (a=1, b=2...)         soma = "hash"
Alex   1 + 12 + 5 + 24               42
Bob    2 + 15 + 2                    19
Dirk   4 + 9 + 18 + 11               42   ← COLISÃO com Alex

Tabela hash ("baldes"):
[19] → Bob
[42] → Alex, Dirk   ← mesmo hash: aí o Java usa o equals para achar o certo
  • Buscar um nome num array de 70 milhões de posições exige olhar uma por uma. Com um hash, que é um número calculado a partir do valor, você vai direto ao "balde" daquele número: tão rápido com 10 elementos quanto com 70 milhões.
  • O exemplo da soma de letras é didático (existem "teses de doutorado" sobre boas funções de hash). A ideia é: mesmo valor → mesmo hash.
  • Colisão: valores diferentes podem ter o mesmo hash (Alex e Dirk = 42). Dentro do balde, o Java usa o equals para achar o elemento certo. Quanto menos colisões, melhor o desempenho.
  • Por isso quem sobrescreve equals sobrescreve hashCode (e vice-versa). As coleções com "Hash" no nome (HashSet, HashMap) dependem dos dois.

164 · Sobrescrevendo hashCode (e o contrato)

// se x.equals(y) == true, então y.hashCode() == x.hashCode()
// y.hashCode() == x.hashCode() NÃO obriga y.equals(x) a ser true (colisão)
// se y.hashCode() != x.hashCode(), então x.equals(y) tem que ser false
@Override
public int hashCode() {
    return serialNumber == null ? 0 : this.serialNumber.hashCode();   // o hashCode da String
}
  • O hashCode de Object é native: implementado fora do Java (em C/C++) e em geral ligado à identidade do objeto. Ou seja, dois Smartphone "iguais" teriam hashes diferentes.
  • Regra de ouro: equals e hashCode em sintonia. Use os mesmos atributos nos dois. Se o equals usa serialNumber, o hashCode também usa. Ter dois atributos num e um no outro quebra a regra.
  • Não precisa inventar o algoritmo: aproveite o hashCode da String (feito pelos arquitetos do Java). Trate o null com o ternário (0).
  • O ideal é um hash o mais único possível entre os objetos. Repetidos não quebram nada, só pioram o desempenho.

165 · Coleções: ordenado × sorted e Big-O

             Collection (interface)                 Map (NÃO é Collection)
         ┌────────┼────────┐                  ┌──────────┼──────────┐
       List      Set      Queue            HashMap  LinkedHashMap  TreeMap
   ArrayList  HashSet   PriorityQueue
   LinkedList LinkedHashSet
   Vector     TreeSet
Collections (com s) = classe utilitária (sort, shuffle...)

Big-O (do melhor ao pior):  O(1) · O(log n) · O(n) · O(n log n) · O(n²) · O(2ⁿ) · O(n!)
ArrayList.get(i) → O(1)         ArrayList.contains(x) → O(n) (equals em cada um)
HashSet.contains(x) → O(1)      (usa hashCode, mas não aceita repetidos)
  • Ordenado (ordered): a coleção lembra a ordem em que você inseriu, como um array (posições 0, 1, 2...). Sorted (o William chama de "sortido"): a coleção se reorganiza por uma regra (ordem alfabética, por exemplo) a cada inserção.
  • As coleções são altamente coesas (cada uma tem um propósito) e você trabalha orientado a interface (List<String> l = new ArrayList<>(), aula 94).
  • "Coleção" em sentido geral × Collection, a interface: um Map é uma estrutura de dados, mas não é uma Collection (não passa no teste "é um"). E Collections (com s) é a classe utilitária.
  • Big-O descreve como o tempo de uma operação cresce com o número de elementos (geralmente no pior caso). Vale para qualquer linguagem: em arrays, acessar por índice é O(1), mas buscar e inserir no meio não é bom.
  • Escolha pela operação mais frequente: muito contains? HashSet (O(1)) é melhor que ArrayList (O(n)), mas o Set não guarda repetidos (10 nomes com 2 iguais viram 9). Consulte a tabela de complexidade de cada coleção (o site Big-O Cheat Sheet, por exemplo).

Atenção

  • Desserializar não chama o construtor. Validações e inicializações do construtor não rodam.
  • transient × static: nenhum dos dois vai para o arquivo. transient volta com o valor padrão, e static vem da classe.
  • Sempre declare o serialVersionUID em classes Serializable que você persiste.
  • Extra: segurança. Desserializar dados de fonte não confiável é uma falha grave conhecida (execução de código). Hoje, para trocar dados, prefere-se JSON (Jackson, Gson).
  • equals sem hashCode quebra o HashSet/HashMap: dois objetos "iguais" caem em baldes diferentes e o set fica com "duplicados" (veja na prática).
  • Extra: Objects.equals(a, b) e Objects.hash(a, b, c) tratam o null e simplificam os dois métodos. A IDE também gera ambos (Alt+Insert). A partir do Java 16, os records já vêm com equals/hashCode prontos.
  • Extra: instanceof × getClass() no equals: getClass() (como na aula) não considera uma subclasse igual à classe mãe, o que respeita a simetria. instanceof aceita subclasses e pode quebrar a simetria.

Paralelo com PHP

  • Serialização: serialize($obj)/unserialize($str) ≈ writeObject/readObject, só que em texto. O transient + writeObject/readObject do Java equivale ao __serialize()/__unserialize() (ou __sleep/__wakeup) do PHP, onde você escolhe o que entra. O mesmo alerta vale: nunca use unserialize com dados do usuário (injeção de objetos).
  • Laravel: os jobs na fila são serializados (SerializesModels guarda só o id do model e o recarrega ao desserializar, que é a mesma ideia do writeObject/readObject da aula 160). O $hidden do Model é o "transient" para JSON.
  • Igualdade: no PHP, == entre objetos compara atributos (mesma classe e mesmos valores) e === compara a identidade (a mesma instância). No Java, == é o === do PHP, e o "== do PHP" você implementa no equals, escolhendo os atributos. O Eloquent tem $model->is($outro), que compara chave e tabela, bem parecido com o equals por serialNumber.
  • hashCode: o array do PHP já é uma tabela hash por dentro, com chaves int/string. Objetos como chave exigem SplObjectStorage ou spl_object_id (identidade). O PHP não tem um contrato equals/hashCode para os seus objetos. É isso que o Java usa para as coleções (aulas 166+).
  • Big-O: in_array é O(n) e isset($arr[$chave])/array_key_exists é O(1). Por isso o truque de usar os valores como chaves (array_flip) para buscas rápidas, que é o HashSet do PHP.

package academy.devdojo.maratonajava.javacore.Ycolecoes.dominio;

public class Smartphone {
    private String serialNumber;
    private String marca;

    public Smartphone(String serialNumber, String marca) {
        this.serialNumber = serialNumber;
        this.marca = marca;
    }

    @Override
    public boolean equals(Object obj) {
        if (obj == null) return false;
        if (this == obj) return true;
        if (this.getClass() != obj.getClass()) return false;
        Smartphone smartphone = (Smartphone) obj;
        return serialNumber != null && serialNumber.equals(smartphone.serialNumber);
    }

    @Override
    public int hashCode() {
        return serialNumber == null ? 0 : this.serialNumber.hashCode();
    }
}

Glossário

  • Serialização / desserialização: objeto → bytes (para gravar ou enviar) / bytes → objeto.
  • Interface de marcação: interface sem métodos que só "marca" a classe (Serializable).
  • transient: atributo ignorado na serialização.
  • serialVersionUID: número de versão da classe serializável; precisa bater para desserializar.
  • Igualdade de referência × lógica: mesmo objeto (==) × mesmo significado pela regra de negócio (equals).
  • Hash: número calculado a partir do valor, usado para endereçar direto numa tabela.
  • Colisão: valores diferentes com o mesmo hash.
  • Ordered × sorted: mantém a ordem de inserção × reordena por um critério.
  • Big-O: notação de como o custo de uma operação cresce com o número de elementos.
  • native: método implementado fora do Java (C/C++), como o hashCode de Object.
