Resumo

Nas aulas de threads, tudo foi feito "no braço" com synchronized, wait e notify, o jeito "mais pedreiro", nas palavras do professor. O pacote java.util.concurrent é uma camada de abstração por cima disso: contadores atômicos, locks com mais recursos e coleções já feitas para várias threads. Ele avisa que o pacote não dispensa entender threads: é preciso saber o que é sincronismo, lock, wait/notifyAll, para usar bem o que vem pronto.

229 · AtomicInteger

A situação de um jogo: uma thread cria monstros no mapa e a thread do jogador os mata, e as duas mexem no mesmo contador. Para simplificar: duas threads incrementam o mesmo contador 10 000 vezes cada. O esperado seria 20 000.

class Counter {
    private int count;
    private AtomicInteger atomicInteger = new AtomicInteger();

    void increment() {
        count++;                              // NÃO é atômico
        atomicInteger.incrementAndGet();      // atômico
    }
    public int getCount() { return count; }
    public AtomicInteger getAtomicInteger() { return atomicInteger; }
}

Counter counter = new Counter();
Runnable r = () -> {
    for (int i = 0; i < 10000; i++) counter.increment();
};
Thread t1 = new Thread(r);
Thread t2 = new Thread(r);
t1.start(); t2.start();
t1.join(); t2.join();                         // a main espera as duas
System.out.println(counter.getCount());       // algo como 13587: varia e quase nunca dá 20000
System.out.println(counter.getAtomicInteger()); // 20000, sempre
  • count++ parece uma instrução, mas não é: na linguagem de máquina vira ler o valor, somar 1 e gravar. Duas threads leem o mesmo valor, somam e gravam, e um incremento se perde.
  • Uma solução é o synchronized no método, que funciona mas custa desempenho (uma thread por vez).
  • AtomicInteger faz a conta de forma atômica sem lock, usando CAS (compare-and-swap): lê o valor, calcula o novo e só grava se o valor na memória ainda for o que foi lido. Se outra thread mudou no meio, tenta de novo. "É bem mais complicado do que eu tô explicando", mas o resultado é sempre correto.
  • incrementAndGet() ≈ ++x (incrementa e devolve o novo); getAndIncrement() ≈ x++ (devolve o antigo); get() lê.
  • Existe a família toda: AtomicLong, AtomicBoolean, AtomicIntegerArray, AtomicLongArray, AtomicReference... (O professor cita um "AtomicDouble", que não existe no JDK.)

230 · Lock e ReentrantLock

Lock (interface) e ReentrantLock (implementação) fazem o que o synchronized faz, mas com o lock explícito: você pega e você solta.

private Lock lock = new ReentrantLock(true);   // true = "fair"
void increment() {
    lock.lock();
    try {
        count++;
        atomicInteger.incrementAndGet();
    } finally {
        lock.unlock();                         // SEMPRE no finally
    }
}

Vantagens sobre o synchronized, segundo a aula:

  • Fairness (new ReentrantLock(true)): ao liberar, tenta dar o lock à thread que espera há mais tempo. Com synchronized não há isso. Não é garantido, mas tende a ser respeitado.
  • tryLock() e tryLock(2, TimeUnit.SECONDS): tenta pegar o lock (ou espera até um tempo) e, se não conseguir, segue a vida em vez de ficar bloqueada para sempre.
  • Dá para interromper uma thread que está esperando o lock (lockInterruptibly()).

Desvantagem: o código fica mais feio e a responsabilidade é sua. Se uma exceção acontecer entre lock() e unlock() sem finally, a thread fica com o lock para sempre e as outras travam. Por isso é sempre lock() + try + finally { unlock() }. A opinião do professor: se você não precisa de fairness, tryLock ou interrupção, use synchronized. "Muita gente usa Lock porque parece avançado, mas desenvolvedores realmente avançados tentam manter o código o mais simples possível."

class Worker implements Runnable {
    private String name;
    private ReentrantLock lock;
    public Worker(String name, ReentrantLock lock) { this.name = name; this.lock = lock; }

    @Override
    public void run() {
        lock.lock();
        try {
            System.out.printf("Thread %s entrou em uma sessão crítica%n", name);
            System.out.printf("%d Threads esperando na fila%n", lock.getQueueLength());
            System.out.printf("Thread %s vai esperar 2s%n", name);
            Thread.sleep(2000);
            System.out.printf("Thread %s finalizou a espera%n", name);
        } catch (InterruptedException e) {
            e.printStackTrace();
        } finally {
            lock.unlock();
        }
    }
}

ReentrantLock lock = new ReentrantLock(true);
new Thread(new Worker("A", lock)).start();
// ... B, C, D, E, F, G
// Thread A entrou em uma sessão crítica
// 6 Threads esperando na fila
// ... cada uma entra, espera 2 s e sai; a fila vai diminuindo
  • printf aparece pela primeira vez no curso: %s é substituído por texto, %d por inteiro, %f por decimal e %n é a quebra de linha.
  • getQueueLength() estima quantas threads esperam o lock; isHeldByCurrentThread() diz se a thread atual está segurando o lock (por isso ele troca a variável de Lock para ReentrantLock: esses métodos não estão na interface).
  • Sem fairness, a thread G costumava ser sempre a última; com fairness a ordem mudou, mas o professor reforça que não é garantido.
  • "Reentrant" (extra): a mesma thread pode pegar o lock de novo sem travar em si mesma (e precisa soltar o mesmo número de vezes). O synchronized também é reentrante.

231 · Conditions

Primeiro, uma pegadinha do tryLock: se a thread não conseguiu o lock e mesmo assim chama unlock() no finally, estoura IllegalMonitorStateException (não dá para soltar o que não se tem). A correção:

try {
    lock.tryLock(2, TimeUnit.SECONDS);
    ...
} finally {
    if (lock.isHeldByCurrentThread()) lock.unlock();
}

Depois, o equivalente a wait/notify para quem usa Lock: a Condition, obtida do próprio lock. O sistema de e-mails da aula 228 foi reescrito com ela:

public class Members {
    private final Queue<String> emails = new ArrayBlockingQueue<>(10);
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition condition = lock.newCondition();
    private boolean open = true;

    public void addMemberEmail(String email) {
        lock.lock();
        try {
            System.out.println(Thread.currentThread().getName() + " Adicionou email na lista");
            this.emails.add(email);
            condition.signalAll();                 // era emails.notifyAll()
        } finally {
            lock.unlock();
        }
    }

    public String retrieveEmail() throws InterruptedException {
        lock.lock();
        try {
            while (this.emails.size() == 0) {
                if (!open) return null;
                condition.await();                 // era emails.wait()
            }
            return this.emails.poll();
        } finally {
            lock.unlock();
        }
    }

    public void close() {
        open = false;
        lock.lock();
        try {
            System.out.println(Thread.currentThread().getName() + " Notificando todo mundo que não estamos mais pegando emails");
            condition.signalAll();                 // acorda quem espera para ver que fechou
        } finally {
            lock.unlock();
        }
    }
}
  • Troca direta: synchronized (obj) → lock.lock()/unlock(); obj.wait() → condition.await(); obj.notify() → condition.signal(); obj.notifyAll() → condition.signalAll().
  • A condição é criada com lock.newCondition(). Um mesmo lock pode ter várias condições (ex.: "fila não vazia" e "fila não cheia"), o que o wait/notify de um objeto não permite.
  • O comportamento ficou igual ao da aula 228, mas o código ficou "mais nervoso" (um try/finally em cada método). A opinião do professor continua: meça, e na dúvida, fique com o código mais limpo (synchronized).
  • A correção da aula 228: durante a gravação o programa não terminava ao fechar a caixinha. Ele percebeu que faltava avisar todo mundo no close(), acrescentou o signalAll() aqui e também corrigiu o close() antigo do pacote de threads, com this.emails.notifyAll(). "Um pedacinho que você esquece e o programa fica travado."

232 · ReentrantReadWriteLock

Um lock com dois modos: leitura e escrita. Vários podem ler ao mesmo tempo, mas enquanto alguém escreve, ninguém lê nem escreve, para não ler um valor pela metade.

class MapReadWrite {
    private final Map<String, String> map = new LinkedHashMap<>();
    private final ReentrantReadWriteLock rwl;
    public MapReadWrite(ReentrantReadWriteLock rwl) { this.rwl = rwl; }

    public void put(String key, String value) {
        rwl.writeLock().lock();                    // exclusivo
        try {
            if (rwl.isWriteLocked()) {
                System.out.printf("%s obteve o WRITE lock%n", Thread.currentThread().getName());
            }
            map.put(key, value);
            Thread.sleep(500);                     // simula processamento
        } catch (InterruptedException e) {
            e.printStackTrace();
        } finally {
            rwl.writeLock().unlock();
        }
    }

    public Set<String> allKeys() {
        rwl.readLock().lock();                     // compartilhado
        try {
            return map.keySet();
        } finally {
            rwl.readLock().unlock();
        }
    }
}

Runnable writer = () -> {
    for (int i = 0; i < 20; i++) mapReadWrite.put(String.valueOf(i), String.valueOf(i));
};
Runnable reader = () -> {
    if (rwl.isWriteLocked()) System.out.println("WRITE LOCKED!");
    rwl.readLock().lock();
    System.out.println("FINALLY I GOT THE DAMN LOCK");
    try {
        System.out.println(Thread.currentThread().getName() + " " + mapReadWrite.allKeys());
    } finally {
        rwl.readLock().unlock();
    }
};
// t1 = writer, t2 e t3 = reader
  • Na execução, a escritora pega o write lock, as leitoras veem "WRITE LOCKED!" e esperam. Quando a escrita termina, as duas leitoras pegam o read lock juntas e imprimem as chaves 0 a 19.
  • O read lock é reentrante: a leitora pega no reader e de novo dentro do allKeys(), sem travar.
  • Dependendo do scheduler, uma leitora pode pegar o read lock antes da escrita começar e imprimir o mapa vazio ou parcial. O professor mostra isso acontecendo, e conta que num teste com 100 mil valores "deu capim na palheta".

233 · CopyOnWriteArrayList

Antes, uma explicação de imutabilidade, a forma preferida de compartilhar dados entre threads: uma classe final, com atributos final, só construtor e getters (sem setters). Para "mudar" um objeto imutável, você cria outro. Se ninguém pode alterar, várias threads podem ler à vontade.

A CopyOnWriteArrayList segue essa ideia: toda escrita (add, remove, set) copia o array inteiro e troca a referência. Quem estava lendo continua com a versão antiga, intacta. O custo é óbvio: escrever muito fica caro. É para listas muito lidas e pouco alteradas. (Também existe a CopyOnWriteArraySet.)

List<Integer> list = new CopyOnWriteArrayList<>();
for (int i = 0; i < 2000; i++) list.add(i);

Runnable runnableIterator = () -> {
    Iterator<Integer> iterator = list.iterator();   // "foto" da lista neste momento
    try {
        TimeUnit.SECONDS.sleep(2);                  // outra forma de sleep
        iterator.forEachRemaining(System.out::println); // imprime os 2000, mesmo após remoções
    } catch (InterruptedException e) {
        e.printStackTrace();
    }
};
Runnable runnableRemover = () -> {
    for (int i = 0; i < 500; i++) {
        System.out.printf("%s removed %d%n", Thread.currentThread().getName(), i);
    }
};
new Thread(runnableIterator).start();
new Thread(runnableIterator).start();
new Thread(runnableRemover).start();
  • O iterador é um snapshot: guarda o array do momento da criação. Enquanto as duas iteradoras dormem, a outra thread remove 500 elementos, e mesmo assim elas imprimem os 2000 valores originais, sem ConcurrentModificationException.
  • O iterador dela não aceita remove() (UnsupportedOperationException): ele é só leitura.
  • A lista é thread safe, os objetos dentro dela não necessariamente: se ela guardar objetos mutáveis (um Anime com setName), threads diferentes ainda podem alterá-los. Inteiros são imutáveis, então no exemplo não há problema.
  • TimeUnit.SECONDS.sleep(2) é o mesmo que Thread.sleep(2000), mais legível.
  • Correção: no repositório, a thread removedora só imprime "removed" e não chama remove. Para ver o efeito, acrescente a remoção no for. Cuidado: list.remove(i) com int remove pela posição, e como os elementos "andam" a cada remoção, remove(0), remove(1), remove(2)... tiram 0, 2, 4, ... (os pares). Para remover os valores 0 a 499, use list.remove(Integer.valueOf(i)).

234 · ArrayBlockingQueue

O pacote de coleções concorrentes tem várias classes feitas para threads, e a BlockingQueue é especial por dois motivos: pode ter capacidade limitada (bounded), e as operações bloqueiam a thread quando não dá para prosseguir.

BlockingQueue<String> bq = new ArrayBlockingQueue<>(1);   // capacidade 1
bq.put("William");
System.out.printf("%s added the value %s%n", Thread.currentThread().getName(), bq.peek());
System.out.println("Trying to add another value");
new Thread(new RemoveFromQueue(bq)).start();
bq.put("Suane");                   // fila cheia: a main BLOQUEIA aqui...
System.out.printf("%s added the value %s%n", Thread.currentThread().getName(), bq.peek());

static class RemoveFromQueue implements Runnable {
    private final BlockingQueue<String> bq;
    public RemoveFromQueue(BlockingQueue<String> bq) { this.bq = bq; }
    @Override
    public void run() {
        System.out.printf("%s going to sleep for 5s %n", Thread.currentThread().getName());
        try {
            TimeUnit.SECONDS.sleep(5);
            System.out.printf("%s removing value from queue %s%n",
                    Thread.currentThread().getName(), bq.take());   // ...até alguém tirar
        } catch (InterruptedException e) {
            e.printStackTrace();
        }
    }
}
// main added the value William
// Trying to add another value
// Thread-0 going to sleep for 5s
// (5 segundos)
// Thread-0 removing value from queue William
// main added the value Suane
  • put(x): insere; se a fila está cheia, bloqueia até abrir espaço.
  • take(): tira e devolve o primeiro; se está vazia, bloqueia até alguém colocar.
  • peek(): mostra o primeiro sem remover (ou null se vazia).
  • É exatamente o que o sistema de e-mails fazia na mão com wait/notifyAll: put/take já fazem a espera e o aviso por dentro.

235 · LinkedTransferQueue

Introduzida no Java 7, junta as funcionalidades de três filas: ConcurrentLinkedQueue (fila concorrente sem bloqueio), SynchronousQueue (entrega direta a um consumidor) e LinkedBlockingQueue (fila que bloqueia). Ela implementa a interface TransferQueue. A dica do professor: em coleções concorrentes, prefira as mais novas, porque quem as escreveu levou em conta o que aprendeu com as anteriores.

TransferQueue<Object> tq = new LinkedTransferQueue<>();
System.out.println(tq.add("william"));                          // true (ou IllegalStateException se sem espaço)
System.out.println(tq.offer("william"));                        // true (ou false se sem espaço)
System.out.println(tq.offer("william", 10, TimeUnit.SECONDS));  // true (espera até 10 s por espaço)
tq.put("DevDojo");                                              // insere; bloquearia se cheia
if (tq.hasWaitingConsumer()) {
    tq.transfer("Devojo");                                      // bloqueia até um consumidor pegar
}
System.out.println(tq.tryTransfer("Academy"));                  // false: ninguém esperando
System.out.println(tq.tryTransfer("Academy", 5, TimeUnit.SECONDS)); // false, depois de esperar 5 s
System.out.println(tq.element());   // william (primeiro, sem remover; exceção se vazia)
System.out.println(tq.peek());      // william (primeiro, sem remover; null se vazia)
System.out.println(tq.poll());      // william (remove; null se vazia)
System.out.println(tq.remove());    // william (remove; exceção se vazia)
System.out.println(tq.take());      // william (remove; BLOQUEIA se vazia)
System.out.println(tq.remainingCapacity()); // 2147483647 (Integer.MAX_VALUE: sem limite)
  • Inserir: add (exceção se não couber), offer (false se não couber), offer(x, tempo) (espera um tempo), put (bloqueia). Esta fila é ilimitada, então todos sempre conseguem.
  • transfer(x): produtor/consumidor em mãos. Coloca e bloqueia até um consumidor receber. Sem ninguém consumindo, trava o programa (o professor mostrou isso). Por isso o hasWaitingConsumer() antes.
  • tryTransfer(x): entrega só se já houver um consumidor esperando; senão devolve false e não coloca na fila. Com tempo, espera até lá.
  • Ler/remover: element e peek olham o primeiro (exceção × null se vazia); remove e poll tiram o primeiro (exceção × null); take tira ou espera.
  • Os quatro primeiros "william" vêm das três inserções: poll, remove e take tiram um cada (o element e o peek só olham). O take devolve o terceiro "william", não "DevDojo", que continua na fila.

Atenção

  • count++ não é atômico: use AtomicInteger (ou synchronized/Lock).
  • lock() sempre com try/finally { unlock() }. Esquecer o unlock trava as outras threads para sempre.
  • unlock() sem segurar o lock → IllegalMonitorStateException. Com tryLock, confira com isHeldByCurrentThread() (ou use o boolean que o tryLock devolve).
  • Fairness e prioridade não são garantias: são tendências.
  • await/signal só com o lock na mão, como wait/notify só dentro de synchronized. E o await fica num while.
  • Read lock é compartilhado, write lock é exclusivo.
  • Extra: allKeys() devolve map.keySet(), uma visão ao vivo do mapa, e não uma cópia. Quem imprime a visão depois de soltar o lock pode ler enquanto a escritora altera (ConcurrentModificationException, o "capim na palheta" com 100 mil valores). Devolva uma cópia dentro do lock: return new ArrayList<>(map.keySet()); (ou Set.copyOf).
  • CopyOnWrite é caro para escrever: cada escrita copia tudo. Use em listas muito lidas e raramente alteradas (ex.: lista de listeners).
  • transfer sem consumidor bloqueia para sempre; tryTransfer devolve false e descarta o elemento.
  • Pares de métodos das filas: exceção × valor especial × bloqueia × espera com tempo, ou seja add/offer/put/offer(t) e remove/poll/take/poll(t). Para olhar sem remover: element/peek.

Paralelo com PHP

  • AtomicInteger ≈ incremento atômico no banco/cache: $post->increment('views') gera UPDATE ... SET views = views + 1, atômico no banco. Cache::increment('contador') (Redis INCR) também. Fazer $post->views++; $post->save(); em dois requests simultâneos perde incrementos, o count++ da aula 229.
  • Lock/tryLock ≈ Cache::lock(): $lock = Cache::lock('relatorio', 10); if ($lock->get()) { try { ... } finally { $lock->release(); } } é o tryLock() + finally unlock(); $lock->block(5, fn() => ...) é o tryLock(5, SECONDS). E o release() fica no finally pelo mesmo motivo.
  • ReadWriteLock ≈ locks do banco: ->sharedLock() (LOCK IN SHARE MODE/FOR SHARE: vários leem, ninguém altera) × ->lockForUpdate() (FOR UPDATE: exclusivo). Mesma ideia: leitura compartilhada, escrita exclusiva.
  • Copy-on-write é o jeito do PHP tratar arrays: $b = $a; não copia nada até alguém alterar um dos dois, e o foreach ($a as $v) percorre o array como estava no início, mesmo que você altere $a no meio. É o snapshot do iterador da aula 233, embutido na linguagem.
  • BlockingQueue ≈ filas: o worker do Laravel (queue:work) com Redis usa BLPOP, um take() que bloqueia até chegar um job. O limite de capacidade e o put bloqueante não têm equivalente direto (em Laravel você controla com rate limiting ou WithoutOverlapping).

Glossário

  • java.util.concurrent: pacote de utilitários de concorrência (atômicos, locks, filas, executores).
  • Operação atômica: acontece inteira, sem outra thread no meio.
  • CAS (compare-and-swap): grava o novo valor só se o atual ainda for o esperado; senão tenta de novo.
  • ReentrantLock: lock explícito; a mesma thread pode adquiri-lo várias vezes.
  • Fairness: política de dar o lock a quem espera há mais tempo.
  • tryLock: tenta pegar o lock sem bloquear (ou por um tempo máximo).
  • Condition: fila de espera ligada a um Lock; await/signal/signalAll.
  • Read/write lock: leitura compartilhada, escrita exclusiva.
  • Imutável: objeto que não muda depois de criado (classe e atributos final, sem setters).
  • Copy-on-write: cada alteração cria uma cópia; leitores continuam com a versão antiga.
  • Snapshot: fotografia dos dados num instante.
  • BlockingQueue: fila cujas operações podem bloquear (cheia no put, vazia no take).
  • Bounded: com capacidade máxima definida.
  • TransferQueue: fila em que o produtor pode esperar o consumidor receber (transfer).
