Resumo

Até agora o curso seguiu o fluxo feliz. Exceções são as condições anormais do programa. Algumas estão sob seu controle: idade negativa, divisão por zero. Outras estão fora dele: o arquivo mudou de lugar ou perdeu a permissão, a internet caiu, o banco saiu do ar. Em Java, como tudo é objeto, o que é "lançado" (thrown) é um objeto de uma subclasse de Throwable.

                 Throwable
                /         \
           Error           Exception ─────────────── checked (IOException, ...)
     (StackOverflowError,       \
      OutOfMemoryError)          RuntimeException ─── unchecked
                                 (NullPointerException, ArrayIndexOutOfBoundsException,
                                  ClassCastException, ArithmeticException,
                                  IllegalArgumentException, NumberFormatException)

95 · Error: não tem conserto em tempo de execução

package academy.devdojo.maratonajava.javacore.Oexception.error.test;

public class StackOverflowTest01 {
    public static void main(String[] args) {
        recursividade();
    }

    public static void recursividade() {
        recursividade();          // chama a si mesmo para sempre
    }
}
// Exception in thread "main" java.lang.StackOverflowError
  • Error são situações de que não dá para se recuperar: acabou a memória (OutOfMemoryError) ou estourou a pilha (StackOverflowError). Normalmente a JVM para. Você corrige o código e roda de novo.
  • A pilha (stack): cada chamada de método (main → calcularImposto → produto.calcularImposto...) ocupa memória na pilha, que cresce na chamada e é limpa quando o método volta.
  • Recursão sem condição de parada empilha chamadas até a memória acabar: StackOverflowError. A solução é consertar o código (colocar um limite ou tirar a recursão).
  • StackOverflowError estende VirtualMachineError, que estende Error.

96 · RuntimeException: unchecked

package academy.devdojo.maratonajava.javacore.Oexception.runtime.test;

public class RuntimeExceptionTest01 {
    public static void main(String[] args) {
        // Checked e Unchecked
        int[] nums = {1, 2};
        System.out.println(nums[2]);   // ArrayIndexOutOfBoundsException
    }
}

Object o = null;
o.toString();                          // NullPointerException
  • Vocabulário técnico (certificação): "aconteceu um erro" = o que foi lançado é subclasse de Error. "Aconteceu uma exceção" = subclasse de Exception.
  • Checked (checadas): filhas de Exception que não são RuntimeException. Se não forem tratadas, o código não compila. Exemplo: IOException (entrada e saída, arquivos).
  • Unchecked (não checadas): RuntimeException e as filhas dela. O tratamento é opcional e o código compila sem ele.
  • Quando o próprio Java lança uma unchecked, em quase 100% dos casos o problema é o seu código: acessar posição que não existe, chamar método em referência null, cast inválido (aula 93), converter "abc" em número. "Você, como desenvolvedor, deveria ter tomado cuidado."
  • Você não precisa decorar todas as RuntimeExceptions da documentação, mas conhecer as principais ajuda em entrevista e certificação.

97 · Exception: checked, try/catch e printStackTrace

package academy.devdojo.maratonajava.javacore.Oexception.exception.test;

import java.io.File;
import java.io.IOException;

public class ExceptionTest01 {
    public static void main(String[] args) {
        criarNovoArquivo();
    }

    private static void criarNovoArquivo() {
        File file = new File("arquivo\\teste.txt");      // \\ = uma barra invertida (Windows)
        try {
            boolean isCriado = file.createNewFile();      // assinatura: throws IOException
            System.out.println("Arquivo criado " + isCriado);
        } catch (IOException e) {
            e.printStackTrace();                          // NUNCA deixe o catch vazio
        }
    }
}
  • Na documentação, File.createNewFile() declara throws IOException. Como IOException é filha direta de Exception (checked), chamar o método sem tratar não compila. É "uma camada de segurança": você não controla o disco.
  • try = "tenta executar". catch (IOException e) = "se der essa exceção, pega". O Java cria o objeto da exceção e o referencia em e.
  • Fluxo: se a linha do createNewFile der certo, a próxima linha roda e o catch é pulado. Se falhar, o resto do try é pulado e a execução vai direto para o catch.
  • Não dá para ter catch de uma exceção checked que nada no try pode lançar (erro de compilação). A exceção é Exception, porque ela também engloba as RuntimeExceptions.
  • Prefira a exceção mais específica. Com catch (Exception e) você não sabe se o problema foi no arquivo ou na conversão de número, e o tratamento fica pior.
  • "Nem que a vaca tussa" deixe o catch em branco. Isso engole o problema sem avisar ninguém. O William diz que, numa entrevista, ignora o resto do teste de quem faz isso. No mínimo, e.printStackTrace().
  • Não coloque regra de negócio no catch. Ele serve para lidar com a exceção.
  • Stack trace: a exceção "sobe" a pilha até alguém tratar. Se ninguém tratar, o programa para. O trace mostra a sequência (linha 8 chamou a 14, que chamou File.createNewFile, que chamou um método nativo...). O William deixa uma dica de carreira: aprenda a ler o stack trace e pesquise a mensagem antes de perguntar. Quase certamente alguém já passou por isso.
  • Na aula, ele tira a permissão de escrita da pasta e o resultado é IOException: Acesso negado. A linha "Arquivo criado" nunca roda.

98 · Lançando exceção unchecked: throw

public class RuntimeExceptionTest02 {
    public static void main(String[] args) {
        divisao(1, 0);
        System.out.println("Código finalizado");   // não imprime: ninguém tratou a exceção
    }

    /**
     * @param a
     * @param b não pode ser zero
     * @return
     * @throws IllegalArgumentException caso b seja zero
     */
    private static int divisao(int a, int b) {
        if (b == 0) {
            throw new IllegalArgumentException("Argumento ilegal, não pode ser 0");
        }
        return a / b;
    }
}
  • 1 / 0 com inteiros lança ArithmeticException (unchecked). Dá para tratar com catch (ArithmeticException e) ou, por polimorfismo, catch (RuntimeException e).
  • O problema do return 0 no catch: o método precisa retornar algo em todos os caminhos. Retornar 0 "funciona", mas 0 é um resultado inválido que finge ser válido.
  • Jeito certo: validar e lançar. throw new IllegalArgumentException("...") interrompe o método na hora, e o código abaixo do if não roda. Use a exceção mais específica possível, para quem usa o seu método entender o que houve.
  • throw (sem s) lança um objeto de exceção. throws (com s), na assinatura, avisa que o método pode lançar.
  • Para unchecked, o throws IllegalArgumentException na assinatura é opcional (com ou sem ele, o resultado é o mesmo). O comum é documentar no Javadoc com @throws, que aparece para quem chama (Ctrl+Q no IntelliJ).
  • Idade negativa, idade acima de 150... Toda validação de argumento se trata com exceção, não com um retorno "mágico" (0, -1).
  • Se o método declarar throws IOException (checked), quem chama é obrigado a tratar ou repassar. Se o main repassar, não sobra ninguém para capturar e a JVM para.

99 · Lançando exceção checked: tratar, repassar ou os dois

public class ExceptionTest02 {
    public static void main(String[] args) throws IOException {   // main repassa: se estourar, a JVM para
        criarNovoArquivo();
    }

    public static void criarNovoArquivo() throws IOException {
        File file = new File("arquivo\\teste.txt");
        try {
            boolean isCriado = file.createNewFile();
            System.out.println("Arquivo criado " + isCriado);
        } catch (IOException e) {
            e.printStackTrace();   // faz a parte dele (log)...
            throw e;               // ...e relança para quem chamou decidir
        }
    }
}
  • Três caminhos para uma checked:
    1. Tratar com try/catch: o código não explode, mas quem chamou não fica sabendo.
    2. Repassar com throws IOException, sem try/catch: a "batata quente" vai para quem chamou, que é obrigado a tratar ou repassar também.
    3. Híbrido: catch + log + throw e;. Como relança uma checked, precisa do throws na assinatura.
  • Por que repassar? Se o createNewFile do Java tratasse a exceção por dentro, você não teria como decidir nada (mandar e-mail, tentar de novo...). Quem chama pode ter uma visão diferente de como tratar.
  • Regra prática do William: método private (só a sua classe chama): tende a tratar ali mesmo. Método public (qualquer um chama): tende a declarar throws e deixar quem chama decidir. "Depende de projeto para projeto". O mais importante é manter o mesmo padrão no sistema todo.
  • Exemplo real do híbrido: o pagamento falhou. Você registra no log e relança para quem chamou oferecer uma nova tentativa ao cliente. A nova tentativa não fica dentro do catch (loop infinito): a falha é guardada para outro processo tentar depois.
  • Também dá para lançar outra exceção no catch: throw new RuntimeException("Problema na hora de criar o arquivo");. Aí quem chama não é mais obrigado a tratar, mas ainda pode.
  • Programação defensiva: num back-end, devolva uma mensagem clara ("dado ilegal") em vez de um valor especial.

Atenção

  • Checked × unchecked é decidido pela hierarquia, não pela gravidade: filha de RuntimeException = unchecked; outra filha de Exception = checked. Error também é unchecked.
  • throw ≠ throws. throw new X() no corpo lança; throws X na assinatura avisa.
  • throw e; de uma checked dentro do catch exige throws na assinatura. Relançar como RuntimeException não exige.
  • Extra: 1.0 / 0 não lança exceção: com double dá Infinity. Só a divisão inteira por zero lança ArithmeticException.
  • Extra: ao embrulhar, guarde a causa: throw new RuntimeException("Problema ao criar o arquivo", e);. Sem o e, o stack trace original se perde.
  • Extra: e.getMessage() devolve só a mensagem ("Argumento ilegal, não pode ser 0"), sem o trace.
  • Extra: em código real, em vez de printStackTrace() usa-se um logger (SLF4J/Logback), que vem mais à frente no ecossistema.

Paralelo com PHP

  • A hierarquia é parecida: Throwable → Error (TypeError, DivisionByZeroError...) e Exception (RuntimeException, InvalidArgumentException...). try/catch, throw new e getMessage() funcionam igual.
  • O PHP não tem exceções checked. Nada obriga você a tratar ou declarar. O @throws do PHPDoc é só documentação, que o PHPStan pode verificar. No Java, o compilador cobra as checked.
  • IllegalArgumentException ≈ InvalidArgumentException. ArithmeticException ≈ DivisionByZeroError (no PHP 8, 1 / 0 já lança).
  • Repassar é o padrão no Laravel: exceções sobem até o Handler (bootstrap/app.php → withExceptions), que decide log e resposta. É o "main que não trata", só que com um tratador global. report($e) é o "loga e segue" do híbrido.
  • Stack trace: é a mesma habilidade da tela do Ignition/Whoops. Leia de cima para baixo e procure a primeira linha que é do seu código.
  • Catch vazio é tão ruim quanto no PHP. O @ (supressão de erro) é o primo dele.

Glossário

  • Exceção: condição anormal na execução; em Java, um objeto lançado.
  • Throwable: superclasse de tudo que pode ser lançado (Error e Exception).
  • Error: problema grave da JVM, geralmente irrecuperável.
  • Checked: exceção que o compilador obriga a tratar ou declarar (filha de Exception, fora de RuntimeException).
  • Unchecked: RuntimeException e filhas (e os Errors); o tratamento é opcional.
  • Stack (pilha de chamadas): memória onde ficam as chamadas de método em andamento.
  • Stack trace: a lista de chamadas impressa quando uma exceção ocorre, da mais recente à mais antiga.
  • throw / throws: lançar uma exceção / declarar na assinatura que o método pode lançá-la.
  • Relançar: capturar no catch e lançar de novo (a mesma ou outra exceção).
  • Programação defensiva: validar entradas e falhar de forma clara, em vez de devolver valores "mágicos".
