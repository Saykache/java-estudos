Resumo

Até aqui, as classes se relacionavam por associação: uma pessoa tem um endereço. Herança é outro tipo de relação: um funcionário é uma pessoa. Com extends, a classe filha recebe tudo o que a mãe tem (atributos e métodos) e acrescenta o que é específico dela. É poderosa, mas acopla fortemente as classes, e o próprio William diz que evita usá-la ao máximo.

Antes de começar, a aula 71 corrige o exercício da aula 70: o requisito dizia que o seminário deve ter um local, mas havia construtores sem ele. Agora os construtores exigem o Local.

71 · extends: "é um"

public class Endereco {          // classe independente, reaproveitável
    private String rua;
    private String cep;
    // getters e setters
}

public class Pessoa {
    private String nome;
    private String cpf;
    private Endereco endereco;    // Pessoa TEM UM endereço (associação)

    public void imprime() {
        System.out.println(this.nome);
        System.out.println(this.cpf);
        System.out.println(this.endereco.getRua() + " " + this.endereco.getCep());
    }
    // getters e setters
}

public class Funcionario extends Pessoa {   // Funcionario É UMA Pessoa
    private double salario;                  // só o que é específico
    // getSalario / setSalario
}

// HerancaTest01
Funcionario funcionario = new Funcionario();
funcionario.setNome("Oda Nobunaga");   // herdado de Pessoa
funcionario.setCpf("22222");           // herdado
funcionario.setEndereco(endereco);     // herdado
funcionario.setSalario(20000);         // próprio
funcionario.imprime();                 // herdado: imprime nome, cpf e endereço, mas NÃO o salário
  • O cenário: o gerente pede uma classe Funcionario com nome, CPF, endereço e salário. Você começa a escrever e percebe que três atributos são os mesmos de Pessoa. Na vida real, um funcionário é uma pessoa.
  • "Tem um" × "é um": associação é "tem um" (uma pessoa tem um endereço, um professor tem seminários). Herança é "é um": o funcionário é tudo o que uma pessoa é, e mais alguma coisa.
  • class Funcionario extends Pessoa: "funcionário estende as funcionalidades de pessoa". Os atributos e métodos de Pessoa passam a existir em todo Funcionario, mesmo sem aparecer no código dele (nem no .class compilado).
  • Quanto mais para baixo, mais especializado: Pessoa (genérica) → Funcionario → Gerente. A classe de cima é a superclasse (mãe) e a de baixo é a subclasse (filha).
  • Por que Endereco não conhece Pessoa: sem a relação de volta, o endereço fica desacoplado e pode ser reutilizado em outras classes e até em outros sistemas.
  • O alerta: herança acopla fortemente. Qualquer mudança em Pessoa afeta Funcionario e todas as outras filhas. Use em dois casos: para estender uma classe ou para usar polimorfismo (aulas 90–94).
  • O imprime() herdado não mostra o salário, porque Pessoa nem sabe que salário existe. O IntelliJ mostra um ícone ao lado de Pessoa indicando que ela tem subclasses.

72 · Sobrescrita e super

public class Funcionario extends Pessoa {
    private double salario;

    public void imprime() {            // MESMA assinatura do imprime() de Pessoa: sobrescrita
        super.imprime();               // executa o imprime() da superclasse...
        System.out.println(this.salario);   // ...e acrescenta o específico
    }
}
  • Cada new cria um objeto separado: a pessoa e o funcionario têm cada um os seus nome, cpf e endereco. Dentro do imprime(), o this é o objeto que está executando, e por isso cada um imprime os próprios dados.
  • Sobrescrita (override): declarar na subclasse um método com a mesma assinatura de um método da superclasse. Ele passa a ser o comportamento dos objetos da subclasse. O IntelliJ mostra o ícone de "overrides".
  • Se o imprime() do funcionário tiver só o salário, só o salário sai: o método da mãe foi substituído.
  • imprime2() não seria sobrescrita. Com outro nome, é um método novo, e o imprime() herdado continua valendo.
  • super se refere à parte da superclasse do objeto. super.imprime() executa o método como foi escrito em Pessoa, mas no objeto funcionário: o this.nome lá dentro é o nome do funcionário. A sobrescrita garante que o funcionário tem todos os atributos da mãe. Já a mãe nunca enxerga o salario.

73 · Herança simples e protected

public class Pessoa {
    protected String nome;       // visível para as subclasses (e para o pacote)
    protected String cpf;
    protected Endereco endereco;
}

public class Funcionario extends Pessoa {
    public void relatorioPagamento() {
        System.out.println("Eu " + this.nome + " recebi o salário de " + this.salario);
    }
}
  • Não existe herança múltipla de classes em Java: class Funcionario extends Pessoa, Aluno não compila. Uma classe estende uma só. As interfaces (aulas 87–89) dão uma alternativa.
  • O problema: com nome private em Pessoa, o Funcionario não consegue escrever this.nome, mesmo o atributo existindo no objeto. Dá para usar getNome() (público), mas não é o ideal.
  • protected dá acesso direto, como se o atributo fosse da própria classe:
    • para todas as subclasses, em qualquer pacote;
    • para todas as classes do mesmo pacote, sejam subclasses ou não. No exemplo da aula, Endereco, que está no mesmo pacote dominio, consegue fazer p.nome = "...".
  • Uma classe de outro pacote que não é subclasse (o HerancaTest01, em test) não enxerga pessoa.nome. Uma subclasse em outro pacote enxerga, como o Funcionario2 extends Pessoa criado em test.

74 · Construtores na herança

public class Pessoa {
    protected String nome;
    public Pessoa(String nome) {
        this.nome = nome;
    }
}

public class Funcionario extends Pessoa {
    public Funcionario(String nome) {
        super(nome);           // chama o construtor de Pessoa — primeira linha, obrigatório aqui
    }
}

// HerancaTest01
Pessoa pessoa = new Pessoa("Toyohisa Shimazu");
Funcionario funcionario = new Funcionario("Oda Nobunaga");
  • Todo construtor começa chamando um construtor da superclasse. Se você não escrever nada, o compilador coloca super();, sem argumentos, na primeira linha, inclusive no construtor padrão.
  • Quando Pessoa passa a ter só Pessoa(String nome), o super() implícito de Funcionario não encontra um construtor vazio, e Funcionario para de compilar. A regra: se a mãe exige o nome, a filha também tem que exigir.
  • A solução é declarar um construtor na filha que receba o nome e chame super(nome). Com vários construtores na mãe, o super(...) escolhe pela lista de argumentos, como o this(...).
  • super(...) tem a mesma regra do this(...): primeira instrução do construtor. Por isso não dá para ter os dois no mesmo construtor.
  • Toda classe estende Object (de java.lang), direta ou indiretamente. Pessoa é um Object, Funcionario é uma Pessoa, e portanto Object é o "avô" de Funcionario. É daí que vêm métodos que você nunca escreveu, como toString(), equals() e hashCode(). Não se escreve extends Object: é implícito.
  • Herança múltipla não existe, mas herança em vários níveis (pai, avô, bisavô...) sim.
  • Ctrl+O (Override Methods) lista o que pode ser sobrescrito, inclusive os métodos de Object.

75 · A sequência de inicialização com herança

// Pessoa e Funcionario ganham: 1 bloco static, 2 blocos de instância e um println no construtor
new Funcionario("Jiraya");
Dentro do bloco de inicialização estático de pessoa         ← 0
Dentro do bloco de inicialização estático de Funcionario    ← 1
Dentro do bloco inicialização de pessoa 1                   ← 4
Dentro do bloco inicialização de pessoa 2                   ← 4
Dentro do construtor de pessoa                              ← 5
Dentro do bloco inicialização de Funcionario 1              ← 8
Dentro do bloco inicialização de Funcionario 2              ← 8
Dentro do construtor de funcionário                         ← 9

A lista do professor (comentário do HerancaTest02):

0 - Bloco estático da SUPERCLASSE (quando a JVM carrega a classe pai)
1 - Bloco estático da SUBCLASSE (quando a JVM carrega a classe filha)
2 - Espaço em memória para o objeto
3 - Atributos da superclasse: valores padrão ou os declarados
4 - Blocos de inicialização da superclasse, na ordem em que aparecem
5 - Construtor da superclasse
6 - (parte da subclasse no objeto)
7 - Atributos da subclasse: valores padrão ou os declarados
8 - Blocos de inicialização da subclasse, na ordem em que aparecem
9 - Construtor da subclasse
  • A regra: o pai sempre vem primeiro. Para carregar Funcionario, a JVM precisa antes carregar Pessoa. Por isso os estáticos vão do pai para o filho (e rodam uma vez só).
  • Depois vem a parte de objeto: primeiro a da mãe (atributos, blocos, construtor) e só então a da filha. A filha só termina de ser construída quando a mãe já está pronta.
  • Com mais níveis (um Gerente extends Funcionario), a sequência só ganha mais passos, sempre de cima para baixo.
  • O William avisa que é um tema que você "provavelmente não vai ligar no dia a dia", mas cai em prova de certificação e é um diferencial saber.

Atenção

  • Herança é "é um". Se a frase "X é um Y" soa estranha (um Carro é um Motor?), é associação ("tem um"), não herança.
  • Construtores não são herdados. Mesmo com Pessoa(String nome), new Funcionario("x") só existe se Funcionario declarar esse construtor.
  • private existe no objeto, mas a filha não acessa. O nome privado de Pessoa está dentro de todo Funcionario, só que o código de Funcionario não enxerga. Use protected ou getters.
  • protected abre para o pacote inteiro, não só para as filhas. É mais aberto do que parece.
  • Extra: @Override. Coloque a anotação em cima do método sobrescrito. Se você errar a assinatura (imprimir() em vez de imprime()), o compilador avisa, em vez de você criar um método novo sem perceber. O IntelliJ já gera com ela.
  • Extra: o objeto é um só. O comentário do professor fala em "espaço para o objeto da superclasse" e "da subclasse", mas a JVM aloca um único objeto contendo os atributos das duas classes. O que segue a ordem pai → filho é a inicialização.
  • Extra: prefira composição. "Composição em vez de herança" é um princípio clássico: quando a relação é "tem um" ou você só quer reaproveitar código, um atributo (como o Endereco) acopla menos que extends. Uma classe final nem pode ser estendida (aulas 77–79).

Paralelo com PHP

  • Igual: extends, herança simples (uma classe mãe só), sobrescrita e parent::imprime(), que equivale a super.imprime().
  • A grande diferença, construtores: no PHP o __construct é herdado: se a filha não declara um, usa o da mãe. Em Java, construtores não são herdados, e se a mãe exige argumentos, a filha precisa declarar o seu e chamar super(...). O parent::__construct($nome) equivale ao super(nome), com a diferença de que em Java ele é obrigatório e tem que ser a primeira linha.
  • protected: no PHP vale só para a hierarquia (mãe e filhas). Em Java vale também para o pacote inteiro. O PHP não tem visibilidade por pacote/namespace.
  • Raiz comum: em Java tudo estende Object. No PHP não existe classe-base universal (stdClass não é mãe das suas classes).
  • Reuso sem herança: o PHP tem traits. Em Java, o mais próximo são interfaces com métodos default (aulas 87–89) ou composição.
  • Anotação de sobrescrita: o PHP 8.3 ganhou #[\Override], que é a mesma ideia do @Override do Java.

Glossário

  • Herança: relação "é um", em que a subclasse recebe atributos e métodos da superclasse.
  • Superclasse / subclasse: classe mãe (mais genérica) / classe filha (mais especializada).
  • extends: palavra que declara a herança.
  • Sobrescrita (override): método da filha com a mesma assinatura de um da mãe, que substitui o comportamento.
  • super: referência à parte da superclasse (super.metodo()) ou chamada do construtor da mãe (super(...)).
  • protected: visível para subclasses (qualquer pacote) e para o mesmo pacote.
  • Object: classe raiz de todas as classes Java.
  • Acoplamento forte: dependência grande entre classes. A herança é o caso mais forte.
