Resumo

Comentários são trechos de texto no código que não afetam a execução. Eles servem só para informar outro desenvolvedor (ou você mesmo no futuro). O compilador ignora os comentários: eles nem entram no bytecode. Na aula, o William abre o .class para mostrar que não sobrou nada deles.

Os três tipos

  • Uma linha: //. Tudo o que vem à direita das barras, até o fim da linha, é comentário.
  • Múltiplas linhas: começa com /* e termina com */. Tudo o que está entre os dois é ignorado. Os * no começo de cada linha do meio são opcionais, só estética. Dá para usar numa linha só, mas para isso o indicado é o //.
  • Javadoc: começa com /** e termina com */. É o comentário "oficial", que descreve classes e métodos para quem vai usar o seu código. Aceita HTML e tags como @param e {@link ...}.
// comentário de uma linha

/*
 * comentário de
 * múltiplas linhas
 */

/**
 * Javadoc: descreve a classe ou o método para quem vai usá-lo.
 * Aceita <b>HTML</b> e tags como @param.
 */

Javadoc no IntelliJ

  • Digite /** e Enter acima de um método: a IDE monta o bloco, já com os @param.
  • Ctrl+Alt+Q alterna a visualização renderizada do Javadoc no editor, com o HTML formatado.
  • Ctrl+Q (Quick Documentation) com o cursor em println abre a documentação do método ali mesmo.
  • Ctrl+B (ou Ctrl+clique) vai até a declaração. Abrindo a classe String, você vê Javadoc "para todo lado": o mundo inteiro precisa entender o que cada método faz.

Devo comentar meu código?

  • Javadoc, sim. O conselho do William: todo método público deve ter Javadoc, porque é a documentação que quem usa sua classe vai ler.
  • Os outros tipos, evite ao máximo. O livro Clean Code (Código Limpo) defende que, se você precisa de um comentário para explicar o código, o código não está claro. Melhore os nomes e a estrutura.
  • Nada de comentário óbvio. // imprime algo em cima de um System.out.println não acrescenta nada.
  • A exceção são as decisões que não dá para deduzir do código, como regras de negócio ou decisões que vieram da gerência. Exemplo da aula: aceitar data de nascimento negativa não faz sentido, mas se uma regra de negócio exige isso, um comentário de uma linha explica o porquê para a próxima pessoa.
  • Enquanto está aprendendo, pode comentar à vontade. No trabalho, segure a mão.

Atenção

  • Comentário mente. Quando alguém muda o código e esquece de atualizar o comentário, ele passa a explicar algo errado. Por isso algumas empresas nem gostam de Javadoc.
  • /* ... */ não pode ser aninhado. O primeiro */ fecha o comentário, e o que sobra vira erro de compilação.
  • /* e /** são diferentes. Só o segundo é Javadoc e aparece na documentação (Ctrl+Q, ferramenta javadoc).
  • O Javadoc vale quando está logo acima de uma declaração (classe, método, atributo). Solto no meio de um método, é só um comentário comum.
  • "// isto" dentro de uma String não é comentário, é texto.
  • Comentários podem vir antes do package. Era esse o "detalhe" que a aula 08 deixou para depois.
  • Em PHP, # também é comentário. Em Java, não: dá erro.

Paralelo com PHP

É quase idêntico. PHP também tem //, /* */ e o PHPDoc (/** */), que se inspirou justamente no Javadoc: @param, @return e @throws funcionam igual. Duas diferenças:

  • No PHP, o docblock muitas vezes serve para tipar o que a linguagem não tipava (@var Collection<User>) e é lido por PHPStan e Psalm. Em Java o tipo já está na assinatura, então o Javadoc fica focado em explicar o comportamento.
  • Java tem uma ferramenta oficial, a javadoc, que vem na JDK e gera um site HTML de documentação. No PHP isso depende de ferramentas externas, como o phpDocumentor.

Prática no seu WSL (10 minutos)

Prove que os comentários não vão para o bytecode e gere um site de documentação:

mkdir -p ~/java-lab/src/academy/devdojo/maratonajava/introducao
cd ~/java-lab

cat > src/academy/devdojo/maratonajava/introducao/Calculadora.java <<'EOF'
// Comentário antes do package: permitido.
package academy.devdojo.maratonajava.introducao;

/**
 * Operações matemáticas <b>simples</b>.
 */
public class Calculadora {

    /**
     * Soma dois números inteiros.
     *
     * @param a primeiro número
     * @param b segundo número
     * @return a soma de a e b
     */
    public static int somar(int a, int b) {
        /* comentário de
           múltiplas linhas */
        return a + b; // comentário de uma linha
    }

    public static void main(String[] args) {
        System.out.println(somar(2, 3));
    }
}
EOF

# 1. Compilar e executar
javac -d out src/academy/devdojo/maratonajava/introducao/Calculadora.java
java -cp out academy.devdojo.maratonajava.introducao.Calculadora

# 2. Desmontar o bytecode: nenhum comentário aparece
javap -c -cp out academy.devdojo.maratonajava.introducao.Calculadora

# 3. Gerar o site de documentação a partir do Javadoc
javadoc -d docs -sourcepath src academy.devdojo.maratonajava.introducao
explorer.exe "$(wslpath -w docs/index.html)"   # abre no navegador do Windows

Desafio: coloque um /* */ dentro de outro e compile. Leia o erro e explique por que ele acontece.

Glossário

  • Comentário: texto ignorado pelo compilador, só para leitura humana.
  • Javadoc: comentário /** */ que documenta classes e métodos. É também o nome da ferramenta da JDK que gera HTML a partir dele.
  • Tag Javadoc: marcação como @param, @return, @throws ou {@link}.
  • Clean Code: livro de Robert C. Martin sobre código legível. Defende que o código se explique sozinho.
  • Regra de negócio: decisão do domínio (da empresa), que o código sozinho não explica.
  • javap: ferramenta da JDK que mostra o conteúdo de um .class.
