280 · Testes unitários com jUnit pt 01

Por que testar: o professor gravou as aulas de introdução há mais de seis meses e "não lembra mais" como Carro ou Estudante deveriam se comportar. No trabalho é igual: você dá manutenção em código antigo, outras pessoas mexem no mesmo repositório, e alguém precisa garantir que o comportamento não mudou sem querer. Existem vários tipos de teste (integração, componente, comportamento...), e o unitário é o mais básico: testa uma unidade, geralmente um método. "90% das pessoas que eu rejeito em entrevista são pessoas que não escrevem testes unitários."

@Data @AllArgsConstructor
public class Person {
    private int age;
}

public class PersonService {
    public boolean isAdult(Person person) {
        Objects.requireNonNull(person, "Person can't be null");
        return person.getAge() >= 18;
    }
}

// o jeito "antigo": um main e o olho no console
Person person = new Person(15);
log.info("Is Adult? '{}'", new PersonService().isAdult(person));   // false

O problema do main: se alguém trocar o 18 por 21 ("nos Estados Unidos é 21"), o main com 15 anos continua imprimindo false e ninguém percebe. O teste automático percebe.

<dependency>
    <groupId>org.junit.jupiter</groupId>
    <artifactId>junit-jupiter-api</artifactId>
    <version>5.7.2</version>
    <scope>test</scope>                   <!-- só existe para os testes -->
</dependency>

// src/test/java/.../ZZKjunit/service/PersonServiceTest.java (mesmo pacote da classe testada)
class PersonServiceTest {
    @Test
    @DisplayName("A person should be not adult when age is lower than 18")
    void isAdult_ReturnFalse_WhenAgeIsLowerThan18() {
        Person person = new Person(15);
        PersonService personService = new PersonService();
        Assertions.assertFalse(personService.isAdult(person));
    }
}
  • JUnit 5 (o módulo se chama Jupiter) é a biblioteca de testes mais famosa. Evite versões -M1/-RC (milestone, ainda em desenvolvimento), e o scope test deixa a dependência fora do código de produção.
  • Onde ficam: em src/test/java, no mesmo pacote da classe testada, com o nome ClasseTest. No IntelliJ: Alt+Enter (ou Ctrl+Shift+T) na classe, Create Test, escolher JUnit 5 e os métodos.
  • O que testar: o professor foca na camada de negócio (o PersonService), e não em getters e setters.
  • Assertivas (Assertions): "tem que ser assim, se não for, falhou". assertEquals(esperado, obtido), assertTrue, assertFalse, assertThrows... Dá para importar estaticamente (import static org.junit.jupiter.api.Assertions.*) e escrever só assertFalse(...).
  • Nome do teste: não há uma convenção única. A do professor é metodo_OQueDeveFazer_QuandoCondicao (isAdult_ReturnFalse_WhenAgeIsLowerThan18), com underscore separando as partes. Se preferir um texto livre, use @DisplayName("...").
  • Os testes rodam a cada push no servidor (integração contínua), e é aí que um nome descritivo faz diferença: você não tem o código na frente, só o relatório. "Hoje em dia muito difícil uma empresa que não faz isso."

281 · Testes unitários com jUnit pt 02

class PersonServiceTest {
    private Person adult;
    private Person notAdult;
    private PersonService personService;

    @BeforeEach                                   // roda ANTES de CADA @Test
    public void setUp() {
        adult = new Person(18);
        notAdult = new Person(15);
        personService = new PersonService();
    }

    @Test
    @DisplayName("A person should be not adult when age is lower than 18")
    void isAdult_ReturnFalse_WhenAgeIsLowerThan18() {
        Assertions.assertFalse(personService.isAdult(notAdult));
    }

    @Test
    @DisplayName("A person should be adult when age is greater or equal than 18")
    void isAdult_ReturnTrue_WhenAgeIsGreaterOrEqualsThan18() {
        Assertions.assertTrue(personService.isAdult(adult));
    }

    @Test
    @DisplayName("Should throw NullPointerException with message when person is null")
    void isAdult_ThrowException_WhenPersonIsNull() {
        Assertions.assertThrows(IllegalArgumentException.class,
                () -> personService.isAdult(null), "Person can't be null");
    }

    @Test
    @DisplayName("Should return list with only adults")
    void filterRemovingNotAdult_ReturnListWithAdultOnly_WhenListOfPersonWithAdultIsPassed() {
        List<Person> personList = List.of(new Person(17), new Person(18), new Person(21));
        Assertions.assertEquals(2, personService.filterRemovingNotAdult(personList).size());
    }
}

// PersonService ganhou:
public List<Person> filterRemovingNotAdult(List<Person> personList) {
    return personList.stream().filter(this::isAdult).collect(Collectors.toList());
}
  • Cobertura (Run with Coverage): mostra quantas linhas os testes executaram. O primeiro teste já dava 100%, e mesmo assim "os testes estão uma bosta": não havia teste para maior de 18 nem para null. Cobertura alta não é teste bom; o que vale é cobrir os casos, principalmente os que não são óbvios. É isso que chama a atenção de quem avalia seu código.
  • @BeforeEach (o nome setUp é convenção): roda antes de cada teste e recria os objetos. Parece o mesmo que inicializar no atributo, mas garante a independência: um teste que altera um objeto não afeta o próximo. Com milhares de testes, isso importa.
  • O teste pegando a mudança: trocando o 18 por 21 no serviço, o teste "deveria ser adulto com 18" falha na hora. Às vezes a mudança é necessária (um requisito do product owner), mas agora você sabe que ela impacta outros lugares. Mais testes, mais chances de pegar o problema antes do usuário.
  • assertThrows(TipoDaExceção.class, () -> código): o código dentro da lambda (um Executable) tem que lançar aquela exceção. Quando alguém trocou o requireNonNull (que lança NullPointerException) por if (person == null) throw new IllegalArgumentException(), o teste que esperava NullPointerException falhou, como deveria. Mudar o tipo de exceção pode quebrar quem depende dela (um front-end que mostra uma mensagem conforme o erro, ou um 404 que vira 500).
  • O professor descobre na gravação que o terceiro argumento do assertThrows não é a mensagem esperada da exceção: é a mensagem exibida se o teste falhar.

282 · Atualizando o JDK

  • O curso começou no Java 15; aqui passa para o 16. Se você está vendo depois, "provavelmente já tem uma versão superior".
  • Instalar: baixar o JDK (Windows x64), next, next, install. Não precisa desinstalar o anterior. Atualizar a variável de ambiente (o JAVA_HOME/Path) e conferir com java -version e mvn -version.
  • No IntelliJ: F4 no projeto (Project Structure) → SDK 16 e language level 16 (tem a opção "16 preview", mas ele usa a 16 normal), e o mesmo nos módulos. No pom.xml, maven.compiler.source e target para 16, porque o Maven "manda" no build.
  • Antes de recompilar, o clean do Maven apaga a pasta target. Depois, rode os testes para ver se nada quebrou. Como o projeto quase não tem testes, "não tem como saber se o resto das classes teve algum problema": outra vantagem de ter testes unitários.
  • Na aula 283 aparece mais um lugar: Settings, Build, Compiler, Java Compiler, onde o target bytecode ainda estava 15.

283 · Record Class

Preview no Java 14, segundo preview no 15 e definitivo no 16. É um novo tipo de classe que faz "o mesmo que o @Value do Lombok": uma classe imutável de dados.

public record Manga(String name, int episodes) {        // os componentes vão no "cabeçalho"

    public Manga {                                        // construtor COMPACTO: só validação
        Objects.requireNonNull(name);
    }
}

// o que o compilador gera (javap Manga.class):
// public final class Manga extends java.lang.Record {
//     private final String name;  private final int episodes;
//     public Manga(String, int);
//     public String name();  public int episodes();      ← accessors, sem "get"
//     equals, hashCode, toString
// }

new Manga("Kimetsu no Yaiba", 24).name();              // "Kimetsu no Yaiba"
new Manga("Kimetsu no Yaiba", 24).toString();          // Manga[name=Kimetsu no Yaiba, episodes=24]
class MangaTest {
    private Manga manga1;
    private Manga manga2;

    @BeforeEach
    public void setUp() {
        manga1 = new Manga("Kimetsu no Yaiba", 24);
        manga2 = new Manga("Kimetsu no Yaiba", 24);
    }

    @Test public void accessors_ReturnData_WhenInitialized() {
        Assertions.assertEquals("Kimetsu no Yaiba", manga1.name());
        Assertions.assertEquals(24, manga1.episodes());
    }
    @Test public void equals_ReturnTrue_WhenObjectsAreTheSame() { Assertions.assertEquals(manga1, manga2); }
    @Test public void hashCode_ReturnTrue_WhenObjectsAreTheSame() { Assertions.assertEquals(manga1.hashCode(), manga2.hashCode()); }
    @Test public void constructor_ThrowNullPointerException_WhenNameIsNull() {
        Assertions.assertThrows(NullPointerException.class, () -> new Manga(null, 12));
    }
    @Test public void isRecord_ReturnTrue_WhenCalledFromManga() { Assertions.assertTrue(Manga.class.isRecord()); }
}
  • O que o compilador gera (o professor mostra com javap no .class): classe final que estende java.lang.Record, atributos private final, um construtor com todos os componentes, accessors com o nome do componente (name(), não getName()), equals, hashCode e toString. Não há setters. "Todo mundo falava que o Java é verboso", e o record veio para resolver isso.
  • Restrições: não pode declarar atributos de instância nem blocos de inicialização de instância além dos componentes; static pode (atributos e blocos). Pode ter métodos, implementar interfaces e usar generics (record Par<T>(T a, T b)). Não pode estender outra classe (já estende Record).
  • Construtores: o IntelliJ oferece o canônico (repete todos os parâmetros e atribuições, que não é recomendado) e o compacto (public Manga { ... }, sem parênteses), ideal para validações. As atribuições acontecem sozinhas depois dele.
  • Manga.class.isRecord(): o professor testa isso porque, se alguém trocar o record por uma class comum, a imutabilidade em que o sistema confiava some, e o teste avisa.
  • Dá para declarar records aninhados dentro de outra classe (são implicitamente static). Quem conhece Kotlin vai achar parecido com as data class.

284 · Pattern matching para instanceof

Também definitivo no 16 (preview no 14 e 15). Resolve a repetição do polimorfismo (aula 94): testar o tipo com instanceof e logo em seguida fazer o cast para o mesmo tipo.

public class Employee {
    private String id;
    public Employee(String id) { this.id = id; }
    public String getId() { return id; }
}
public class Developer extends Employee {
    private String mainLanguage;
    public Developer(String id, String mainLanguage) { super(id); this.mainLanguage = mainLanguage; }
    public String getMainLanguage() { return mainLanguage; }
}

@Test
public void instanceOf_ExecutesChildClassMethod_WhenObjectIsOfChildType() {
    Employee employeeDeveloper = new Developer("1", "Java");

    if (employeeDeveloper instanceof Developer) {                 // antes
        Developer developer = (Developer) employeeDeveloper;       // cast repetido
        Assertions.assertEquals("Java", developer.getMainLanguage());
    }

    if (employeeDeveloper instanceof Developer developer) {       // Java 16: testa E declara
        Assertions.assertEquals("Java", developer.getMainLanguage());
    }
}
  • objeto instanceof Tipo variavel: se o teste der true, a variável já existe com o cast feito. Uma linha a menos e nenhum cast manual.
  • A variável só existe onde o teste é verdadeiro (dentro do if, ou depois dele num if (!(x instanceof T t)) return;).
  • A pegadinha que o professor mostra: trocando o objeto por um new Employee("1"), nenhum if entra, nenhuma assertiva roda, e o teste passa mesmo assim (no debug, os breakpoints dentro dos if nunca são atingidos). Um teste sem assertiva executada não testa nada.

Atenção

  • Cobertura de 100% não significa bons testes: teste os casos (limite, maior, menor, null, lista vazia).
  • Testes independentes: use @BeforeEach para recriar o estado; não dependa da ordem de execução.
  • Correção: o @DisplayName do teste de null diz "Should throw NullPointerException", mas o teste espera IllegalArgumentException (o serviço foi alterado no meio da aula). Nome e verificação devem contar a mesma história.
  • O terceiro argumento do assertThrows é a mensagem de falha, e não a mensagem esperada da exceção. Extra: para verificar a mensagem, use o retorno: var e = assertThrows(IllegalArgumentException.class, () -> ...); assertEquals("Person can't be null", e.getMessage());
  • Extra: if (x instanceof T t) { assert... } passa em silêncio quando o if não entra (a pegadinha da aula 284). Em teste, prefira Developer d = assertInstanceOf(Developer.class, employee); (JUnit 5.8+), que falha se o tipo não bater.
  • Extra: junit-jupiter-api sozinho só compila os testes. Para o mvn test executá-los é preciso o motor (junit-jupiter-engine, ou o agregador junit-jupiter) e um maven-surefire-plugin recente (2.22+). No IntelliJ funciona porque a IDE traz o motor. A prática abaixo já vem configurada.
  • Record não é setter-friendly: não há setName. Para "mudar", crie outro record. Accessor é name(), não getName().
  • Extra: Java 16 não é LTS. Hoje o recomendado é uma versão LTS: 17, 21 ou 25. Tudo das aulas funciona nelas, e o Java 21 ainda estende o pattern matching ao switch e aos record patterns.

Paralelo com PHP

  • JUnit ≈ PHPUnit / Pest: class PersonServiceTest extends TestCase com métodos test_... ou #[Test]; $this->assertFalse(...), assertEquals, $this->expectException(InvalidArgumentException::class) (≈ assertThrows); setUp() ≈ @BeforeEach; --coverage ≈ Run with Coverage. No Pest: it('is not adult when age < 18', fn() => expect($service->isAdult(new Person(15)))->toBeFalse());, e o texto do it faz o papel do @DisplayName. php artisan test ≈ mvn test.
  • Atualizar a versão ≈ subir o PHP: mudar o "php": "^8.3" do composer.json (≈ maven.compiler.source), a versão no Docker/Sail e rodar a suíte de testes para ver o que quebrou. É a mesma lição da aula 282.
  • Record ≈ classe readonly do PHP 8.2: final readonly class Manga { public function __construct(public string $name, public int $episodes) {} }. No PHP não há equals/hashCode gerados (compara-se com ==), e acessa-se $manga->name direto.
  • Pattern matching ≈ PHP sem cast: no PHP, if ($employee instanceof Developer) { $employee->getMainLanguage(); } já funciona sem cast, porque a tipagem é dinâmica (e o PHPStan/IDE entende o tipo dentro do if). O Java 16 chega nessa ergonomia mantendo a checagem em tempo de compilação.

Glossário

  • Teste unitário: teste automático de uma unidade (geralmente um método), isolada.
  • JUnit 5 (Jupiter): biblioteca de testes do Java; a API é org.junit.jupiter.api.
  • Assertiva: verificação que faz o teste falhar se não for verdadeira (assertEquals, assertTrue...).
  • @BeforeEach: método executado antes de cada teste (preparação).
  • @DisplayName: nome legível do teste nos relatórios.
  • Cobertura de código: percentual de linhas executadas pelos testes.
  • Integração contínua (CI): servidor que compila e roda os testes a cada push.
  • Maven Surefire: plugin que executa os testes no mvn test.
  • LTS: versão do Java com suporte longo (17, 21, 25).
  • record: classe final e imutável de dados, com construtor, accessors, equals, hashCode e toString gerados.
  • Accessor: método de leitura do componente do record, com o mesmo nome (name()).
  • Construtor compacto: construtor do record sem parâmetros declarados, usado para validar.
  • Pattern matching para instanceof: x instanceof T t testa o tipo e declara t já convertido.
