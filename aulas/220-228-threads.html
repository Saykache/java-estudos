Resumo

Uma thread é uma linha de execução: um "trabalhador" que executa código. Todo programa Java já começa com uma, a thread main, e você pode criar outras para fazer coisas ao mesmo tempo. O preço é a imprevisibilidade: quem decide qual thread roda, quando e por quanto tempo é a JVM (o scheduler), e o professor repete durante o bloco inteiro que quase nada é garantido no mundo das threads. A segunda metade trata do problema clássico: duas threads mexendo no mesmo objeto (condição de corrida) e as ferramentas para controlar isso (synchronized, wait/notify) sem cair num deadlock.

Runnable tarefa = () -> System.out.println(Thread.currentThread().getName());
Thread t = new Thread(tarefa, "T1");   // 220 · criar (NEW)
t.start();                             // 220 · nova linha de execução (RUNNABLE)
Thread.sleep(2000);                    // 222 · dormir (garantido!)
t.join();                              // 223 · esperar t terminar
synchronized (conta) { ... }           // 225 · uma thread por vez
lista.wait(); lista.notifyAll();       // 228 · esperar / avisar

220 · Introdução: Thread e Runnable

  • "Thread" tem dois sentidos: um objeto da classe java.lang.Thread e um processo, a linha de execução que divide a carga de trabalho de um programa. No Gerenciador de Tarefas, na aba de desempenho, dá para ver milhares de threads rodando em poucas centenas de processos.
  • O processador tem núcleos e processadores lógicos (normalmente o dobro): a máquina do professor tem 4 núcleos e 8 processadores lógicos, então 8 threads podem rodar realmente em paralelo. As demais se revezam.
  • Daemon × user: o Java encerra o programa quando todas as threads user terminam, mesmo que ainda haja threads daemon rodando. A daemon tem menos prioridade, e o exemplo é a thread do garbage collector.
  • Thread.currentThread().getName() devolve o nome da thread atual; a que inicia o programa se chama main.
class ThreadExample extends Thread {          // forma 1: herdar de Thread (não recomendada)
    private final char c;
    public ThreadExample(char c) { this.c = c; }
    @Override
    public void run() {                         // o código que a nova thread executa
        System.out.println(Thread.currentThread().getName());
        for (int i = 0; i < 500; i++) {
            System.out.print(c);
            if (i % 100 == 0) System.out.println();
        }
    }
}

class ThreadExampleRunnable implements Runnable { // forma 2: implementar Runnable (recomendada)
    private final char c;
    public ThreadExampleRunnable(char c) { this.c = c; }
    @Override
    public void run() { /* o mesmo código */ }
}

// Daemon x User
public class ThreadTest01 {
    public static void main(String[] args) {
        Thread t1 = new Thread(new ThreadExampleRunnable('A'));
        Thread t2 = new Thread(new ThreadExampleRunnable('B'));
        Thread t3 = new Thread(new ThreadExampleRunnable('C'));
        Thread t4 = new Thread(new ThreadExampleRunnable('D'));
        t1.start();
        t2.start();
        t3.start();
        t4.start();
    }
}
  • run() × start(): chamar t1.run() é uma chamada de método comum, executada pela própria main: imprime todos os A, depois todos os B, na ordem. Só start() pede à JVM uma nova thread, e aí as letras saem misturadas, numa ordem diferente a cada execução.
  • Herdar de Thread não é o recomendado: herança é para especializar, e você não está especializando uma thread. Implementar Runnable diz "esta classe é uma tarefa executável" e deixa a classe livre para herdar de outra. A tarefa é passada no construtor new Thread(Runnable).
  • Uma curiosidade do fim do vídeo: new Thread(new ThreadExample('A')) também compila, porque Thread implementa Runnable.

221 · Estados das threads

A legenda desta aula veio em romeno, então o texto abaixo junta o código e o que o professor fala sobre estados nas aulas 222–223. O código só acrescentou esta linha no fim do main:

t1.start(); t2.start(); t3.start(); t4.start();
System.out.println("############################# " + Thread.currentThread().getName());
// a linha da main costuma sair antes (ou no meio) das letras: start() não espera a thread rodar
          start()                scheduler escolhe
  NOVA ──────────▶ RUNNABLE ◀───────────────────▶ RUNNING ──── run() acabou ───▶ MORTA
  (new)           (pronta p/ rodar)   yield()        │                             (dead)
                        ▲                            │ sleep(), join(), wait(),
                        │                            │ esperar um lock
                        └──── acabou a espera ── BLOQUEADA / ESPERANDO ◀─┘
  • Nova: o objeto Thread existe, mas start() ainda não foi chamado.
  • Runnable: pronta para rodar, esperando o scheduler escolhê-la. Running: executando de fato. Quem decide a troca entre as duas é o scheduler, não você.
  • Bloqueada/esperando: dormindo (sleep), esperando outra terminar (join), esperando aviso (wait) ou esperando um lock. Quando a espera acaba, ela volta para runnable (não direto para running).
  • Morta: o run() terminou. Uma thread morta não pode ser iniciada de novo (start() outra vez lança IllegalThreadStateException).
  • Extra: no código, t.getState() devolve o enum Thread.State: NEW, RUNNABLE (junta "pronta" e "rodando"), BLOCKED (esperando um lock), WAITING (join/wait sem tempo), TIMED_WAITING (sleep, wait(ms)) e TERMINATED.

222 · Prioridade e sleep

Thread t1 = new Thread(new ThreadExampleRunnable('A'), "T1A");  // nome no construtor
Thread t2 = new Thread(new ThreadExampleRunnable('B'), "T2B");
Thread t3 = new Thread(new ThreadExampleRunnable('C'), "T3C");
Thread t4 = new Thread(new ThreadExampleRunnable('D'), "T4D");
t4.setPriority(Thread.MAX_PRIORITY);   // 10 · MIN_PRIORITY = 1 · NORM_PRIORITY = 5

// dentro do for do run():
try {
    Thread.sleep(2000);                // 2000 ms = 2 segundos
} catch (InterruptedException e) {
    e.printStackTrace();
}
  • Nome: o construtor new Thread(runnable, "nome") define o nome que aparece no getName().
  • Prioridade vai de 1 a 10, e o aconselhado é usar as constantes MIN_PRIORITY, NORM_PRIORITY e MAX_PRIORITY. É só uma indicação ao scheduler: a JVM é uma especificação com várias implementações, e em algumas a prioridade não muda quase nada. No teste, T4D tinha prioridade máxima, mas a T1A começou primeiro. Nunca escreva código que dependa de prioridade.
  • Thread.sleep(ms) é estático: faz dormir a thread atual (nenhuma thread manda outra dormir). Uso típico: um loop que consulta uma API ou um estoque a cada X segundos, sem ficar martelando a conexão.
  • É uma das poucas garantias: a thread realmente fica pelo menos esse tempo parada. Ela sai de running, fica bloqueada e, ao fim do tempo, volta para runnable.
  • sleep lança InterruptedException (checked), e o run() não pode declarar throws porque o método da interface não declara (regra da sobrescrita, aula 105). Por isso vai num try/catch.
  • Com o sleep dentro do for, a saída sai "de quatro em quatro" (A, B, C, D, uma letra de cada, a cada 2 segundos), mas a ordem dentro de cada grupo continua sem garantia.

223 · Yield e join

Antes, o professor mostra que o Runnable pode ser uma classe anônima ou uma lambda (Runnable é interface funcional, aula 195), guardada numa variável, como Runnable r = () -> { ... }; e new Thread(r).start();. Mas quando a tarefa precisa receber algo no construtor (a letra), a classe continua útil:

public class ThreadTest02 {
    public static void main(String[] args) throws InterruptedException {
        Thread t1 = new Thread(new ThreadExampleRunnable2("KA"));
        Thread t2 = new Thread(new ThreadExampleRunnable2("ME"));
        t1.setPriority(Thread.MAX_PRIORITY);
        t1.start();
        t1.join();      // a main PARA aqui até t1 terminar
        t2.start();     // só então t2 começa: KAKAKA... depois MEMEME...
    }
}
  • Thread.yield(): a thread atual "sugere" ceder a vez, voltando de running para runnable para outras rodarem. É só uma dica, que o scheduler pode ignorar. "Pouca coisa é garantida na vida; em threads, pior ainda." O professor diz que é bom saber o que é, para quando alguém perguntar no café.
  • t1.join(): a thread que chama (aqui, a main) fica bloqueada até t1 terminar. Ou seja, "junte-se a t1": a main não prossegue, e a linha t2.start() não roda enquanto t1 não acabar. Sem o join, KA e ME saem misturados.
  • join também lança InterruptedException; no main ele declarou throws.

224 · Sincronismo pt 01: condição de corrida

O exemplo "mais famoso de todas as aulas de threads": uma conta bancária compartilhada.

public class Account {
    private int balance = 50;
    public void withdrawal(int amount) { this.balance = this.balance - amount; }
    public int getBalance() { return balance; }
}

public class ThreadAccountTest01 implements Runnable {
    private Account account = new Account();          // UMA conta

    public static void main(String[] args) {
        ThreadAccountTest01 threadAccountTest01 = new ThreadAccountTest01();
        Thread t1 = new Thread(threadAccountTest01, "Hestia");      // duas threads,
        Thread t2 = new Thread(threadAccountTest01, "Bell Cranel"); // o MESMO objeto
        t1.start();
        t2.start();
    }

    @Override
    public void run() {
        for (int i = 0; i < 5; i++) {
            withdrawal(10);
            if (account.getBalance() < 0) {
                System.out.println("FODEO");          // saldo negativo: deu problema
            }
        }
    }

    private void withdrawal(int amount) {
        if (account.getBalance() >= amount) {                 // 1. verifica
            System.out.println(getThreadName() + " está indo sacar dinheiro");
            account.withdrawal(amount);                       // 2. saca
            System.out.println(getThreadName() + " completou o saque, valor atual da conta " + account.getBalance());
        } else {
            System.out.println("Sem dinheiro para " + getThreadName() + " efetuar o saque " + account.getBalance());
        }
    }
}

Saldo 50, duas threads, cada uma tenta sacar 10 cinco vezes (100 no total). O if deveria impedir o saldo negativo, mas às vezes ele fica −10. Com 10 na conta, Bell Cranel passa pelo if (10 ≥ 10) e, antes de sacar, o scheduler dá a vez à Hestia, que também passa pelo if, porque o saldo ainda é 10. As duas sacam. Isso é uma condição de corrida (race condition): o resultado depende da ordem em que as threads são intercaladas. Às vezes a execução sai certa, e é isso que torna esse bug terrível: "é difícil de reproduzir e vai te dar cabelo branco".

225 · Sincronismo pt 02: synchronized

O trecho "verificar e sacar" precisa ser atômico: a thread que começa tem que terminar antes de outra entrar. Para isso existe o lock (trava, ou "chave"): todo objeto tem um, e só uma thread por vez pode segurá-lo.

private final Account account = new Account();   // final: o lock não pode trocar de objeto

// opção 1: método sincronizado → lock do próprio objeto (this, o ThreadAccountTest01)
private synchronized void withdrawal(int amount) { ... }

// opção 2: bloco sincronizado → lock só do objeto account, só no trecho crítico
private void withdrawal(int amount) {
    System.out.println(getThreadName() + " #### fora do synchronized");
    synchronized (account) {
        System.out.println(getThreadName() + " **** dentro do synchronized");
        if (account.getBalance() >= amount) {
            ...
        }
    }
}
  • Método synchronized: a thread precisa do lock do objeto (this) para entrar. Como as duas threads usam o mesmo ThreadAccountTest01, só uma entra por vez, e o saldo nunca fica negativo. A ordem continua sem garantia: o garantido é que quem começa o método termina antes de outra entrar.
  • Thread.sleep não solta o lock: com um sleep de 10 s dentro do método sincronizado, a outra thread fica esperando os 10 s. Ao terminar, o lock é liberado, e qual thread pega em seguida é decisão do scheduler.
  • Bloco synchronized (objeto): trava só o trecho crítico, usando o lock do objeto indicado. O que está fora roda livremente em paralelo, e na saída "fora do synchronized" das duas threads aparece misturado, enquanto "dentro" aparece uma de cada vez.
  • A referência do lock deve ser final: se alguém fizer account = new Account(), as threads passam a travar objetos diferentes e a proteção some.
  • Método static synchronized usa o lock da classe, o mesmo que synchronized (ThreadAccountTest01.class) { ... }. O professor diz que isso aparece pouco; o comum é sincronizar métodos ou blocos.
  • A thread que não consegue o lock fica bloqueada até ele ser liberado.

226 · Sincronismo pt 03: classes thread safe

Uma classe é thread safe quando seus métodos de acesso são sincronizados. Exemplos: StringBuffer (a versão sincronizada do StringBuilder, aula 111) e as listas de Collections.synchronizedList(new ArrayList<>()). O professor mostra a pegadinha: usar uma coleção thread safe não deixa o seu código thread safe.

class ThreadSafeNames {
    private final List<String> names = Collections.synchronizedList(new ArrayList<>()); // no vídeo

    public void add(String name) { names.add(name); }

    public void removeFirst() {
        if (names.size() > 0) {                   // 1. verifica  (sincronizado sozinho)
            System.out.println(Thread.currentThread().getName());
            System.out.println(names.remove(0));  // 2. remove    (sincronizado sozinho)
        }
    }
}

ThreadSafeNames threadSafeNames = new ThreadSafeNames();
threadSafeNames.add("Junkrat");                   // um nome só
Runnable r = threadSafeNames::removeFirst;       // method reference como Runnable
new Thread(r).start();
new Thread(r).start();
// às vezes: IndexOutOfBoundsException — as duas passaram pelo size() > 0

Cada chamada (size, remove) é sincronizada, mas o conjunto "verifica e depois remove" não é: as duas threads podem ver size() == 1 e depois as duas tentarem remover. A solução é sincronizar o seu método também. Na versão final do repositório, os métodos add e removeFirst ficaram synchronized e a lista virou um ArrayList comum, que é seguro porque todo acesso passa por esses métodos. "Não adianta nada a classe ser thread safe se o seu código não for."

227 · Sincronismo pt 04: deadlock

Quando uma thread segura um lock, todas as outras que precisam dele esperam "de boa na lagoa". O deadlock acontece quando duas threads esperam, cada uma, um lock que a outra segura: Natsu segura A e precisa de B; Lucy segura B e precisa de A. Nenhuma solta e nenhuma avança, e o programa nunca termina. Não há o que fazer além de reiniciar a aplicação.

Object lock1 = new Object();
Object lock2 = new Object();
Runnable r1 = () -> {
    synchronized (lock1) {
        System.out.println("Thread 1: Segurando lock 1");
        System.out.println("Thread 1: Esperando lock 2");
        synchronized (lock2) {
            System.out.println("Thread 1: Segurando lock 2");
        }
    }
};
Runnable r2 = () -> {
    synchronized (lock2) {                 // ordem INVERTIDA: aqui mora a bomba
        System.out.println("Thread 2: Segurando lock 2");
        System.out.println("Thread 2: Esperando lock 1");
        synchronized (lock1) {
            System.out.println("Thread 2: Segurando lock 1");
        }
    }
};
new Thread(r1).start();
new Thread(r2).start();
  • Pode ser que não trave toda vez. Um Thread.sleep(10) entre os dois synchronized praticamente garante o deadlock.
  • A solução: todas as threads pegam os locks na mesma ordem. Com r2 também pegando lock1 e depois lock2, o deadlock nunca acontece.
  • É pergunta clássica de entrevista técnica ("o que é deadlock?"), com a piada do professor: "se eu te contratar eu te respondo".

228 · Sincronismo pt 05: wait, notify e notifyAll

wait(), notify() e notifyAll() são métodos da classe Object, então todo objeto tem. Servem para threads conversarem: uma espera até outra avisar que há trabalho. O exemplo é um sistema de e-mails: a main adiciona e-mails numa lista, e duas threads (Jiraya e Kakashi) pegam e "enviam". Sem e-mail na lista, as entregadoras não podem simplesmente terminar (morta não volta), e também não podem ficar num loop gastando CPU: elas precisam dormir até serem avisadas.

public class Members {
    private final Queue<String> emails = new ArrayBlockingQueue<>(10); // fila thread safe, capacidade 10
    private boolean open = true;                                         // "chave" para aceitar e-mails

    public boolean isOpen() { return open; }

    public int pendingEmails() {
        synchronized (emails) { return emails.size(); }
    }

    public void addMemberEmail(String email) {
        synchronized (this.emails) {
            System.out.println(Thread.currentThread().getName() + " Adicionou email na lista");
            this.emails.add(email);
            this.emails.notifyAll();                  // acorda TODAS as que esperam em emails
        }
    }

    public String retrieveEmail() throws InterruptedException {
        System.out.println(Thread.currentThread().getName() + " checking if there are emails");
        synchronized (this.emails) {
            while (this.emails.size() == 0) {
                if (!open) return null;
                System.out.println(Thread.currentThread().getName() + " Não tem email disponível na lista, entrando em modo de espera");
                this.emails.wait();                   // SOLTA o lock e dorme até um notify
            }
            return this.emails.poll();                // tira e devolve o primeiro
        }
    }

    public void close() {
        open = false;
        synchronized (this.emails) {
            System.out.println(Thread.currentThread().getName() + " Notificando todo mundo que não estamos mais pegando emails");
            // falta aqui: this.emails.notifyAll();   (veja o Atenção)
        }
    }
}

public class EmailDeliveryService implements Runnable {
    private final Members members;
    public EmailDeliveryService(Members members) { this.members = members; }

    @Override
    public void run() {
        String threadName = Thread.currentThread().getName();
        System.out.println(threadName + " starting to deliver emails...");
        while (members.isOpen() || members.pendingEmails() > 0) {
            try {
                String email = members.retrieveEmail();
                if (email == null) continue;
                System.out.println(threadName + " enviando email para " + email);
                Thread.sleep(2000);                   // simula a chamada a uma API de e-mail
                System.out.println(threadName + " enviou email com sucesso para " + email);
            } catch (InterruptedException e) {
                e.printStackTrace();
            }
        }
        System.out.println("Todos os emails foram enviados com sucesso!");
    }
}

// EmailDeliveryTest01.main
Members members = new Members();
Thread jiraya = new Thread(new EmailDeliveryService(members), "Jiraya");
Thread kakashi = new Thread(new EmailDeliveryService(members), "Kakashi");
jiraya.start();
kakashi.start();
while (true) {
    String email = JOptionPane.showInputDialog("Entre com seu email"); // caixinha do Swing
    if (email == null || email.isEmpty()) {
        members.close();
        break;
    }
    members.addMemberEmail(email);
}
  • wait() só pode ser chamado por quem tem o lock daquele objeto, então sempre dentro de synchronized (obj). O mesmo vale para notify e notifyAll. Fora dele, dá IllegalMonitorStateException. wait lança InterruptedException.
  • wait() solta o lock (ao contrário do sleep): é assim que Jiraya e Kakashi conseguem esperar ao mesmo tempo, e que a main consegue entrar no addMemberEmail.
  • notify() acorda uma thread que espera naquele objeto ("sabe Deus qual"); notifyAll() acorda todas, e elas disputam o lock. No teste, as duas acordaram, "o Kakashi não deu sorte dessa vez" e o Jiraya pegou o e-mail. O Kakashi voltou a esperar.
  • A espera fica num while, não num if: quem acorda precisa conferir de novo se ainda tem e-mail, porque outra thread pode ter pegado antes.
  • ArrayBlockingQueue é uma fila thread safe de tamanho fixo (o professor definiu 10); poll() tira e devolve o primeiro. Mesmo assim, o synchronized por cima continua necessário (a lição da aula 226).

Atenção

  • run() não cria thread; start() cria. E start() só pode ser chamado uma vez por objeto Thread.
  • Quase nada é garantido: ordem de execução, prioridade e yield são indicações. Garantidos: o sleep dorme pelo menos o tempo pedido, o join espera a outra terminar, e o synchronized deixa uma thread por vez.
  • sleep não solta o lock; wait solta.
  • wait/notify/notifyAll só dentro de synchronized do mesmo objeto, senão IllegalMonitorStateException.
  • Sincronize no mesmo objeto: duas threads que travam objetos diferentes não se bloqueiam. Por isso o lock deve ser final.
  • Coleção thread safe + "verificar e depois agir" ≠ thread safe: o conjunto precisa estar num synchronized.
  • Correção: no repositório, o close() da aula 228 não chama notifyAll(), embora o professor diga que o notifyAll precisa estar no contexto sincronizado. Sem ele, as threads que estão em wait() nunca acordam para ver que open virou false, e o programa não termina depois de fechar a caixinha. A linha que falta, dentro do synchronized do close, é this.emails.notifyAll();.
  • Extra: open deveria ser volatile (ou lido dentro do synchronized): sem isso, a JVM pode deixar uma thread enxergar um valor antigo de uma variável que outra thread alterou (visibilidade de memória).
  • Extra: ArrayBlockingQueue.add com a fila cheia (o 11º e-mail) lança IllegalStateException: Queue full. Os métodos próprios da fila bloqueante, put e take, esperam sozinhos e dispensam o wait/notify manual.
  • Extra: count++ não é atômico (ler, somar, gravar). Duas threads incrementando um int sem synchronized perdem incrementos. A prática abaixo mostra isso.

Paralelo com PHP

  • O PHP tradicional não tem threads na requisição: cada request roda num processo/worker isolado (PHP-FPM), sem memória compartilhada entre requests. Paralelismo vem de processos: filas do Laravel com vários workers (Horizon), Process::pool e Concurrency::run (Laravel 11+). Existem a extensão parallel e os Fibers (PHP 8.1), mas os Fibers são cooperativos, parecidos com o yield e sem paralelismo real.
  • A condição de corrida existe igual, só que entre requisições e no banco: dois requests sacando da mesma conta ao mesmo tempo é exatamente a aula 224. As soluções equivalentes ao synchronized: DB::transaction(fn() => Account::lockForUpdate()->find($id)...) (lock de linha no banco), Cache::lock('conta:'.$id)->block(5, fn() => ...) (lock atômico) ou um UPDATE accounts SET balance = balance - 10 WHERE id = ? AND balance >= 10, que é atômico por si.
  • Deadlock também existe no banco: duas transações travando linhas em ordens opostas. O MySQL detecta e aborta uma delas ("Deadlock found when trying to get lock"), e o DB::transaction($fn, 3) tenta de novo. A prevenção é a mesma da aula 227: travar sempre na mesma ordem.
  • O exemplo da aula 228 é uma fila de e-mails, o Mail::to($user)->queue(...) do Laravel: a main é quem despacha o job, e Jiraya e Kakashi são dois php artisan queue:work. O worker que "espera sem gastar CPU" usa um blocking pop no Redis (BLPOP), o equivalente ao wait/notify.
  • sleep(2) do PHP é em segundos; Thread.sleep(2000) é em milissegundos (usleep é em microssegundos).

    └── wait / notify / notifyAll (Object): dentro de synchronized, wait SOLTA o lock, while

    // versão enxuta do Members da aula 228, já com o notifyAll no close
    static class Caixa {
        private final Queue<String> emails = new ArrayDeque<>();
        private boolean open = true;

        void add(String email) {
            synchronized (emails) { emails.add(email); emails.notifyAll(); }
        }
        String retrieve() throws InterruptedException {
            synchronized (emails) {
                while (emails.isEmpty()) {
                    if (!open) return null;
                    emails.wait();
                }
                return emails.poll();
            }
        }
        void close() {
            synchronized (emails) { open = false; emails.notifyAll(); }
        }
    }

Glossário

  • Thread: linha de execução dentro de um processo; também a classe java.lang.Thread.
  • Runnable: interface funcional com void run(); a tarefa que a thread executa.
  • Scheduler: parte da JVM/SO que decide qual thread roda e por quanto tempo.
  • Daemon thread: thread de serviço; não impede o programa de terminar.
  • Prioridade: indicação de 1 a 10 ao scheduler, sem garantia.
  • sleep: pausa a thread atual por um tempo (não solta locks).
  • yield: sugestão para ceder o processador.
  • join: faz a thread atual esperar outra terminar.
  • Condição de corrida (race condition): resultado depende da intercalação das threads.
  • Operação atômica: executa inteira, sem outra thread no meio.
  • Lock (monitor): trava que todo objeto tem; synchronized usa ela.
  • Thread safe: seguro para uso por várias threads ao mesmo tempo.
  • Deadlock: threads esperando para sempre locks que umas seguram das outras.
  • wait/notify/notifyAll: métodos de Object para uma thread esperar (soltando o lock) e outra avisar.
