Resumo

Na empresa, ninguém é "só funcionário": a pessoa é desenvolvedor, gerente, supervisor, do RH... Funcionario é um molde (template) que junta o que todos têm em comum (nome, salário), mas não deveria virar objeto sozinho. A palavra abstract resolve esse problema de design de código: na classe, ela proíbe o new; no método, ela obriga as subclasses a implementar. O contrário de abstrato é concreto.

84 · Classe abstrata: não pode dar new

public abstract class Funcionario {
    protected String nome;
    protected double salario;

    public Funcionario(String nome, double salario) {   // abstrata TEM construtor
        this.nome = nome;
        this.salario = salario;
    }
}

public class Gerente extends Funcionario {
    public Gerente(String nome, double salario) {
        super(nome, salario);                            // herança normal (aulas 71–75)
    }
    @Override
    public String toString() { return "Gerente{nome='" + nome + "', salario=" + salario + "}"; }
}
// Desenvolvedor: igual, com "Desenvolvedor{...}"

Gerente gerente = new Gerente("Nami", 5000);
Desenvolvedor desenvolvedor = new Desenvolvedor("Touya", 12000);
// Funcionario f = new Funcionario("Tsubasa", 2000);   // NÃO compila: Funcionario é abstract
  • O problema: antes do abstract, dava para criar new Funcionario(...), um objeto que "não deveria existir" no exemplo da empresa.
  • public abstract class Funcionario transforma a classe num template: não pode ser instanciada. Só as subclasses concretas (Gerente, Desenvolvedor) viram objetos.
  • A classe abstrata continua tendo construtor, e a herança funciona igual: para criar um gerente você precisa de nome e salário, então o construtor do Gerente chama super(nome, salario).
  • Uma classe abstrata foi criada para ser estendida, ou seja, para ser superclasse.
  • abstract + final não combinam: um diz "tem que ser estendida", o outro "não pode ser estendida" (aulas 77–79). Não compila.
  • Os atributos são protected para as subclasses acessarem nome e salario direto no toString.

85 · Método abstrato: o contrato

Agora todo funcionário precisa de cálculo de bônus. Primeiro o William coloca um método concreto em Funcionario (10% para todos: Nami vai a 5500.0 e Touya a 13200.0) e sobrescreve em Desenvolvedor (5%). Funciona, mas o Gerente fica com os 10% "herdados" sem ninguém ter decidido isso: se entrar um cargo novo e alguém esquecer, ele ganha o bônus padrão calado. A versão final:

public abstract class Funcionario {
    protected String nome;
    protected double salario;

    public Funcionario(String nome, double salario) {
        this.nome = nome;
        this.salario = salario;
        calculaBonus();                      // quem executa é o OBJETO (Gerente/Desenvolvedor)
    }

    public abstract void calculaBonus();     // sem corpo: termina com ;
}

public class Gerente extends Funcionario {
    ...
    @Override
    public void calculaBonus() {
        this.salario = this.salario + this.salario * 0.2;     // 20%
    }
}

public class Desenvolvedor extends Funcionario {
    ...
    @Override
    public void calculaBonus() {
        this.salario = this.salario + this.salario * 0.05;    // 5%
    }
}
// Gerente{nome='Nami', salario=6000.0}
// Desenvolvedor{nome='Touya', salario=12600.0}
  • "O verdadeiro poder das classes abstratas" está nos métodos abstratos: um sinal (uma bandeira) dizendo "quem estender Funcionario precisa calcular o bônus".
  • Método abstrato não tem corpo. A subclasse concreta que não implementar não compila: o Gerente ficou com erro até ganhar o @Override.
  • Implementar com o corpo vazio também cumpre o contrato (compila). O Gerente fica com 5000, mas foi uma decisão explícita, não um esquecimento.
  • Quem executa é sempre o objeto: mesmo chamando calculaBonus() dentro do construtor de Funcionario, roda a versão do Desenvolvedor, porque o objeto é um Desenvolvedor. "Se não entendeu, desenhe o objeto."
  • Classe abstrata pode ter métodos abstratos e concretos ao mesmo tempo (ex.: toString em Funcionario). Um método concreto faz sentido quando a lógica é igual para todos, como "deletar funcionário"; a subclasse que precisar muda com sobrescrita.
  • Classe concreta não pode ter método abstrato. Tirar o abstract da classe Funcionario gera erro de compilação.

86 · Mais de um nível abstrato

public abstract class Pessoa {
    public abstract void imprime();
}

public abstract class Funcionario extends Pessoa {    // abstrata: NÃO é obrigada a implementar imprime
    ...
    @Override
    public void imprime() {                            // mas pode, e aí vale para todas as filhas
        System.out.println("Imprimindo...");
    }
}

gerente.imprime();         // Imprimindo...
desenvolvedor.imprime();   // Imprimindo...
  • Regra: uma classe abstrata que estende outra abstrata não é obrigada a implementar os métodos abstratos herdados.
  • A obrigação cai na primeira classe concreta da hierarquia. Sem a implementação em Funcionario, Gerente e Desenvolvedor davam erro: "precisa ser declarada abstrata ou implementar imprime()".
  • Basta implementar uma vez: como Funcionario implementou imprime(), as filhas herdam e o erro some.
  • Java não tem herança múltipla de classes, mas tem hierarquia: Gerente → pai Funcionario → avô Pessoa → bisavô Object. O Gerente é um Funcionario, é uma Pessoa e é um Object.
  • Próximo passo: interfaces (aulas 87–89), "uma versão mais robusta da classe abstrata".

Atenção

  • Método abstrato termina com ;, sem { }. Escrever public abstract void calculaBonus() { } não compila.
  • Classe abstrata não precisa ter método abstrato (a da aula 84 não tinha nenhum). Mas se tem método abstrato, a classe tem que ser abstrata.
  • Não dá new, mas dá para usar como tipo: Funcionario f = new Gerente("Nami", 5000); compila. É a base do polimorfismo (aulas 90–94).
  • Extra: método abstrato não pode ser private, static nem final, porque nesses três casos a subclasse não conseguiria sobrescrever.
  • Extra: cuidado ao chamar método sobrescrevível no construtor. Ele roda antes do corpo do construtor da subclasse e dos seus atributos serem inicializados. Aqui funciona porque salario está em Funcionario. Se o Gerente tivesse private double percentual = 0.2; e usasse no calculaBonus, o valor lido seria 0.0 (exercício 3).
  • Extra: o bônus é aplicado a cada new, porque está no construtor. Chamar calculaBonus() de novo depois aplica o bônus de novo (juros sobre juros).

Paralelo com PHP

  • É praticamente igual: abstract class Funcionario e abstract public function calculaBonus(): void;. new Funcionario() no PHP lança Error: Cannot instantiate abstract class, só que em tempo de execução. Em Java, o erro aparece na compilação.
  • A mesma regra da primeira classe concreta: no PHP, uma classe abstrata também pode deixar o método abstrato para as filhas, e a primeira concreta que não implementar dá Fatal error ao carregar a classe.
  • abstract final também é proibido no PHP.
  • Laravel está cheio disso: Illuminate\Database\Eloquent\Model é abstrata. Você nunca faz new Model, faz class User extends Model. Illuminate\Foundation\Http\FormRequest e muitos Command/Job seguem o mesmo contrato "estenda e implemente".
  • O construtor da abstrata chamando calculaBonus() é o padrão Template Method: a mãe define o fluxo e as filhas preenchem um passo. É o que o Model::boot() do Eloquent faz com booted() nas filhas.

Glossário

  • Classe abstrata: classe marcada com abstract; não pode ser instanciada, existe para ser estendida.
  • Classe concreta: classe normal, que pode virar objeto com new.
  • Método abstrato: assinatura sem corpo (; no fim) que obriga as subclasses concretas a implementar.
  • Método concreto: método com corpo; pode existir em classe abstrata.
  • Contrato: o conjunto de métodos que quem estende a classe se compromete a implementar.
  • Template: molde com o que é comum; o detalhe fica para as subclasses.
  • Template Method (extra): padrão em que a superclasse define o fluxo e chama métodos abstratos que as filhas implementam.
